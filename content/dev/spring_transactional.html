Spring Boot — @Transactional 완전 이해

Spring Boot @Transactional Propagation Isolation Rollback 2026-05-06

AOP 원리부터 Propagation · Isolation · Rollback 규칙까지 — 읽고 나면 직접 설명할 수 있다

1

@Transactional 이란

@Transactional은 횡단 관심사 중 하나인 DB 트랜잭션 관리를 AOP로 처리해주는 Spring의 어노테이션이다. 개발자가 직접 커넥션을 열고 커밋·롤백을 작성할 필요 없이, 어노테이션 하나로 Proxy가 이 모든 것을 대신 처리한다.

@Transactional 없이 직접 작성 
public void createOrder(OrderDto dto) {
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);
    try {
        orderRepo.save(dto.toOrder());
        inventoryRepo.decrease(dto.itemId);
        conn.commit();
    } catch (Exception e) {
        conn.rollback();   // 실패하면 전부 되돌림
        throw e;
    } finally {
        conn.close();
    }
}
@Transactional 사용 후 — Proxy가 위 코드를 대신 실행 
@Transactional
public void createOrder(OrderDto dto) {
    orderRepo.save(dto.toOrder());
    inventoryRepo.decrease(dto.itemId);
}
AOP 연결 고리 Spring은 @Transactional이 붙은 클래스를 CGLIB Proxy로 감싼다. 메서드 호출 시 Proxy가 먼저 트랜잭션을 시작하고, 메서드 완료 후 커밋 또는 예외 발생 시 롤백한다. 개발자가 직접 호출하는 것은 항상 Proxy 객체다.
Proxy 실행 흐름 
Controller
    ↓ orderService.createOrder()
Proxy (CGLIB)
    ↓ 트랜잭션 시작 (BEGIN)
진짜 OrderService.createOrder()
    ↓ orderRepo.save()  ↓ inventoryRepo.decrease()
Proxy (CGLIB)
    ↓ 정상 완료 → COMMIT
    ↓ 예외 발생 → ROLLBACK
2

Propagation — 트랜잭션 전파 방식

메서드 A가 트랜잭션 안에서 메서드 B를 호출할 때, B가 A의 트랜잭션에 어떻게 참여할지를 결정하는 설정이다.

REQUIRED (기본값)

트랜잭션 있으면 → 참여

트랜잭션 없으면 → 새로 생성

하나의 작업 단위로 묶을 때

REQUIRES_NEW

트랜잭션 있으면 → 일시 중단, 별도 생성

트랜잭션 없으면 → 새로 생성

실패해도 꼭 남겨야 할 기록

NESTED

트랜잭션 있으면 → savepoint 찍고 중첩

트랜잭션 없으면 → REQUIRED와 동일

실패해도 외부는 계속 진행

REQUIRED — 전부 하나로 묶기

OrderService.java — REQUIRED 
@Service
public class OrderService {

    @Transactional  // REQUIRED — 트랜잭션 A 시작
    public void createOrder(OrderDto dto) {
        orderRepo.save(dto.toOrder());       // 트랜잭션 A 안에서 실행
        inventoryRepo.decrease(dto.itemId);  // 트랜잭션 A 안에서 실행
        // inventoryRepo.decrease() 에서 예외 → order도 함께 롤백
    }
}
REQUIRED 실행 흐름 
트랜잭션 A 시작
    └─ orderRepo.save()         ← A 안에서
    └─ inventoryRepo.decrease() ← A 안에서
예외 발생!
트랜잭션 A 전체 롤백          ← order + inventory 둘 다 취소
언제 쓰나 주문 저장과 재고 차감처럼 반드시 함께 성공하거나 함께 실패해야 하는 작업

REQUIRES_NEW — 트랜잭션 분리하기

OrderService.java + AuditService.java — REQUIRES_NEW 
@Transactional  // 트랜잭션 A
public void createOrder(OrderDto dto) {
    orderRepo.save(dto.toOrder());
    auditService.log("주문 생성");    // REQUIRES_NEW 호출
    inventoryRepo.decrease(dto.itemId);
}

@Transactional(propagation = Propagation.REQUIRES_NEW)  // 트랜잭션 B (별도)
public void log(String message) {
    auditRepo.save(new AuditLog(message));
}
REQUIRES_NEW 실행 흐름 
트랜잭션 A 시작
    └─ orderRepo.save()              ← A 안에서
    └─ auditService.log() 진입
트랜잭션 A 일시 중단
트랜잭션 B 시작                   ← 별도 커넥션
    auditRepo.save()
트랜잭션 B 커밋                   ← A와 완전히 무관하게 독립 커밋
트랜잭션 A 재개
    └─ inventoryRepo.decrease()
트랜잭션 A 커밋

→ A가 나중에 롤백되더라도 B(감사 로그)는 이미 커밋됨 — 로그는 남는다

B 예외 발생 시 — A에게 미치는 영향

B는 독립 트랜잭션이라 B는 자동으로 롤백된다. 하지만 예외 객체 자체는 A로 전파된다. A가 그 예외를 어떻게 처리하느냐가 A의 운명을 결정한다.

Case 1 — A가 예외를 catch 하는 경우 
트랜잭션 A 시작
    └─ doA()                          ← INSERT 1
트랜잭션 A 일시 중단
트랜잭션 B 시작 (독립)
    └─ doB()                          ← INSERT 2
    └─ 예외 발생 → B 롤백            ← INSERT 2 취소
    └─ 예외 객체가 A 로 전파
트랜잭션 A 재개
    └─ catch(e) { ... }             ← A가 예외를 처리하고 계속 진행
    └─ doMore()
트랜잭션 A 커밋                   ← INSERT 1 반영, INSERT 2 는 취소된 상태
Case 2 — A가 예외를 catch 하지 않는 경우 
트랜잭션 A 시작
    └─ doA()                          ← INSERT 1
트랜잭션 A 일시 중단
트랜잭션 B 시작 (독립)
    └─ doB()                          ← INSERT 2
    └─ 예외 발생 → B 롤백            ← INSERT 2 취소
    └─ 예외 객체가 A 의 @Transactional 경계까지 전파
트랜잭션 A 롤백                   ← INSERT 1 도 취소
A의 예외 처리B 결과A 결과
catch 로 잡음롤백 (항상)커밋
catch 없이 전파롤백 (항상)롤백
핵심 B의 롤백은 자동이다. 그 예외 객체가 A까지 올라오므로, A의 롤백 여부는 A가 예외를 처리하느냐에 달려 있다. "B가 롤백됐다"가 "A도 롤백된다"를 의미하지는 않는다.
언제 쓰나 감사(Audit) 로그, 이메일 발송 기록처럼 메인 작업이 실패해도 기록은 반드시 남아야 할 때
주의 — 커넥션 풀 위험 REQUIRES_NEW는 DB 커넥션을 2개 동시에 연다. 커넥션 풀이 꽉 차 있으면 B가 커넥션을 얻으려다 대기 → A도 기다리는 데드락이 발생할 수 있다. 커넥션 풀 크기를 고려해서 사용해야 한다.

NESTED — 부분 롤백 (savepoint)

OrderService.java + CouponService.java — NESTED 
@Transactional  // 트랜잭션 A
public void createOrder(OrderDto dto) {
    orderRepo.save(dto.toOrder());

    try {
        couponService.applyCoupon(dto.couponId);  // NESTED 호출
    } catch (Exception e) {
        log.warn("쿠폰 적용 실패, 정가로 진행");
        // 예외를 잡아서 처리 → A는 계속 진행
    }

    inventoryRepo.decrease(dto.itemId);
}

@Transactional(propagation = Propagation.NESTED)
public void applyCoupon(Long couponId) {
    couponRepo.markUsed(couponId);
    discountRepo.apply(couponId);
}
NESTED 실행 흐름 — 내부 예외 발생 시 
트랜잭션 A 시작
    └─ orderRepo.save()        ← A에 기록
    └─ [SAVEPOINT 생성]         ← NESTED 진입 시점에 찍어둠
        couponRepo.markUsed()
        discountRepo.apply()
예외 발생!
    └─ SAVEPOINT 까지만 롤백   ← coupon 관련 작업만 취소
                                orderRepo.save() 는 살아있음
    └─ catch에서 예외 처리
    └─ inventoryRepo.decrease() ← 계속 실행
트랜잭션 A 커밋
언제 쓰나 쿠폰 적용, 포인트 사용처럼 실패해도 메인 흐름(주문)은 계속 진행해야 하는 부가 작업

NESTED — 반대 방향: 외부(A)가 롤백되면?

외부 트랜잭션 롤백 시 NESTED의 운명 
트랜잭션 A 시작
    └─ orderRepo.save()
    [SAVEPOINT]
    couponRepo.markUsed()      ← 커밋 안 됨, A 안에 포함
    inventoryRepo.decrease()   ← 예외 발생!

트랜잭션 A 전체 롤백
    ← SAVEPOINT 포함 전체 취소
    couponRepo.markUsed() 도 같이 사라짐
중요 — NESTED는 물리적으로 같은 트랜잭션 NESTED가 롤백해도 외부는 살 수 있지만, 반대로 외부(A)가 롤백되면 NESTED 작업도 전부 사라진다. REQUIRES_NEW는 이미 별도로 커밋됐으므로 외부 롤백의 영향을 받지 않는 것과 다른 점이다.

외부 A가 롤백되는 두 가지 경우

NESTED(B)가 정상 종료됐어도 A 전체가 롤백되는 경우가 있다.

Case 1 — B의 예외를 A가 catch 하지 않는 경우 
@Transactional
public void A() {
    doA();
    B();         // B 예외 발생 — catch 없음
    // 예외가 A의 @Transactional 까지 전파
}

────────────────────────────────────────────
트랜잭션 A 시작
    └─ doA()            ← INSERT 1
    [SAVEPOINT]
    └─ B() → 예외 발생 → savepoint까지 롤백
    └─ 예외가 A 경계까지 전파 (catch 없음)
트랜잭션 A 전체 롤백  ← INSERT 1 도 취소
Case 2 — B 성공 후 A의 다른 작업(C)에서 예외 발생 
@Transactional
public void A() {
    doA();
    B();         // NESTED — 정상 완료
    C();         // 여기서 예외 발생!
}

────────────────────────────────────────────
트랜잭션 A 시작
    └─ doA()            ← INSERT 1
    [SAVEPOINT 생성]
    └─ B() 실행
        └─ doB()        ← INSERT 2
    └─ B 정상 완료 → savepoint release
    └─ C() → 예외 발생!
트랜잭션 A 전체 롤백
    ← INSERT 1 취소
    ← INSERT 2 도 취소 ← B가 성공했어도 아직 커밋된 게 아님
B가 성공했어도 롤백되는 이유 NESTED의 savepoint release는 "B의 작업을 A 트랜잭션 안으로 합쳤다"는 뜻이다. DB에 최종 커밋된 것이 아니라, A 트랜잭션이 커밋되어야 비로소 영구 반영된다. 그러므로 A가 롤백되면 B의 INSERT 2 도 함께 사라진다. REQUIRES_NEW였다면 B는 이미 독립 커밋이 완료된 상태라 C 예외가 B에 영향을 줄 수 없다.
상황REQUIRES_NEWNESTED
B 예외, A catch OB 롤백 / A 커밋B→savepoint 롤백 / A 커밋
B 예외, A catch XB 롤백 / A 롤백A 전체 롤백
B 성공, A 자신(C)의 예외B 커밋 유지 / A만 롤백A 전체 롤백 (B 포함)

세 가지 비교 정리

상황REQUIREDREQUIRES_NEWNESTED
트랜잭션 있을 때기존에 참여기존 중단, 별도 생성savepoint 찍고 중첩
내부 예외 발생전체 롤백내부만 롤백 (외부 무관)savepoint까지만 롤백
외부 롤백 시함께 롤백영향 없음 (이미 커밋)함께 롤백 (같은 트랜잭션)
DB 커넥션1개2개 동시 사용1개
대표 사용처주문 + 재고감사 로그, 알림 기록쿠폰 적용, 포인트 사용
NESTED 외부에서 catch 필수 외부에서 예외를 잡지 않으면 예외가 A까지 전파되어 A 전체가 롤백된다. NESTED 호출부를 반드시 try-catch로 감싸야 "부분 롤백 후 계속 진행"이 가능하다.

Rollback 규칙 — Checked vs Unchecked Exception

@Transactional의 기본 롤백 규칙: RuntimeException과 Error만 자동 롤백, Checked Exception은 롤백하지 않는다.

Java 예외 계층 구조 — 이게 기준이다

Exception Hierarchy 
Throwable
├── Error                     ← 롤백 O  (OutOfMemoryError, StackOverflowError)
└── Exception
    ├── RuntimeException      ← 롤백 O  (Unchecked)
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   ├── IllegalStateException
    │   └── ...
    └── (그 외 Exception)    ← 롤백 X  (Checked)
        ├── IOException
        ├── SQLException
        └── ...

실용적 구분법 — 컴파일러가 강제하면 Checked

Checked vs Unchecked 
// Checked — 컴파일러가 try-catch 또는 throws를 강제한다
public void readFile() throws IOException {   // 안 쓰면 컴파일 에러
    Files.readAllBytes(Path.of("data.txt"));
}

// Unchecked — 컴파일러가 아무것도 강제하지 않는다
public void divide(int a, int b) {
    if (b == 0) throw new IllegalArgumentException("0으로 나눌 수 없음");
    return a / b;
}
왜 Checked는 기본 롤백이 아닌가? Checked Exception은 "예상 가능하고 복구 가능한 상황"으로 Java가 설계했다. 파일 없음, 네트워크 끊김 — 이런 상황은 롤백보다 재시도나 대체 처리가 맞을 수도 있다. 그래서 Spring은 개발자가 직접 판단하도록 기본값을 "롤백 안 함"으로 둔 것이다.

실무에서 자주 쓰는 설정

rollbackFor / noRollbackFor 
// Checked Exception도 롤백시키고 싶을 때
@Transactional(rollbackFor = Exception.class)
public void save() { ... }

// 특정 예외만 롤백 제외
@Transactional(noRollbackFor = IllegalArgumentException.class)
public void process() { ... }

자주 당하는 함정 — catch로 예외를 삼키는 경우

예외를 삼키면 롤백이 안 된다 
@Transactional
public void createOrder(OrderDto dto) {
    orderRepo.save(dto.toOrder());

    try {
        externalApi.call();   // RuntimeException 발생
    } catch (Exception e) {
        log.error("API 실패", e);
        // 여기서 예외를 삼키면 → Proxy는 예외를 인지하지 못함
        // → 롤백 트리거 자체가 없어짐 → orderRepo.save() 가 커밋됨!
    }
}
함정 catch로 예외를 삼키면 Proxy까지 예외가 전파되지 않는다. Proxy는 예외를 받아야 롤백을 실행하는데, 예외가 없으면 정상으로 간주하고 커밋한다. 롤백이 필요하면 예외를 다시 던지거나 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()를 호출해야 한다.
예외 종류기본 롤백 여부예시
RuntimeException롤백 ONullPointerException, IllegalArgumentException
Error롤백 OOutOfMemoryError, StackOverflowError
Checked Exception롤백 X (기본)IOException, SQLException
catch로 삼킨 예외롤백 XProxy가 예외를 인지하지 못해 커밋됨

Isolation — 격리 수준

여러 트랜잭션이 동시에 실행될 때, 한 트랜잭션의 변경 사항이 다른 트랜잭션에 얼마나 보이는지를 결정하는 설정이다. 격리 수준이 높을수록 데이터 정합성은 올라가지만, 잠금 경합이 늘어나 처리량(TPS)이 떨어진다.

이상 현상 1 — Dirty Read (커밋 안 된 데이터를 읽음)

트랜잭션 A가 커밋하지 않은 변경분을 트랜잭션 B가 읽는 현상이다. A가 롤백하면 B는 DB에 없는 데이터를 기준으로 처리한 셈이 된다.

Dirty Read 
트랜잭션 A: UPDATE 잔액 = 0              ← 아직 커밋 안 함
트랜잭션 B: SELECT 잔액 → 0 읽음   ← 없는 데이터를 기준으로 로직 실행!
트랜잭션 A: ROLLBACK                    ← 잔액은 원래 10,000이었음
트랜잭션 B: 0을 기준으로 이미 처리    ← 데이터 오염

이상 현상 2 — Non-repeatable Read (같은 row를 두 번 읽었는데 값이 달라짐)

한 트랜잭션 안에서 같은 row를 두 번 SELECT했을 때, 그 사이에 다른 트랜잭션이 해당 row를 UPDATE·커밋하여 값이 달라지는 현상이다.

Non-repeatable Read 
트랜잭션 A: SELECT 재고 → 10
트랜잭션 B: UPDATE 재고 = 0 + COMMIT
트랜잭션 A: SELECT 재고 → 0   ← 같은 쿼리인데 값이 달라짐
→ A가 재고를 10으로 믿고 계속 처리하면 데이터 불일치 발생

이상 현상 3 — Phantom Read (같은 조건으로 조회했는데 row 수가 달라짐)

한 트랜잭션 안에서 같은 WHERE 조건으로 두 번 SELECT했을 때, 그 사이에 다른 트랜잭션이 INSERT·커밋하여 결과 집합의 건수(row 수)가 달라지는 현상이다.

Phantom Read 
트랜잭션 A: SELECT * WHERE 금액 > 1000 → 3건
트랜잭션 B: INSERT 금액 = 5000 + COMMIT
트랜잭션 A: SELECT * WHERE 금액 > 1000 → 4건   ← 유령 row 등장
→ 건수를 기준으로 처리하는 로직이면 오류 발생
Non-repeatable Read vs Phantom Read Non-repeatable Read는 이미 존재하는 row의 값이 바뀌는 것이고, Phantom Read는 존재하지 않던 row가 추가되거나 삭제되는 것이다. 전자는 읽은 row에 공유 락을 걸면 되지만, 후자는 아직 존재하지 않는 row 범위까지 잠가야 하므로 Gap Lock이 필요하다.

4가지 격리 수준 — 이상 현상 차단 범위

격리 수준Dirty ReadNon-repeatable ReadPhantom Read성능
READ_UNCOMMITTED 발생발생발생 가장 빠름
READ_COMMITTED 차단발생발생 빠름
REPEATABLE_READ 차단차단 발생 (이론) 보통
SERIALIZABLE 차단차단차단 가장 느림

각 격리 수준의 동작 원리

격리 수준동작실무 사용
READ_UNCOMMITTED 커밋 여부와 관계없이 변경 중인 데이터를 그대로 읽는다. 잠금을 거의 사용하지 않아 가장 빠르지만 데이터 신뢰성이 없다. 실무 사용 없음
READ_COMMITTED SELECT 실행 시점에 커밋 완료된 최신 데이터를 읽는다 (Statement-level snapshot). 같은 쿼리를 두 번 실행하면 그 사이 커밋이 발생할 경우 다른 결과가 나올 수 있다. 대부분의 서비스 기본값
REPEATABLE_READ 트랜잭션 시작 시점의 스냅샷을 고정해서 읽는다 (MVCC). 트랜잭션 내에서 같은 row를 몇 번 읽어도 항상 동일한 값을 반환한다. MySQL InnoDB 기본값
SERIALIZABLE 읽기에도 공유 락(S-Lock)을 걸어 트랜잭션을 직렬처럼 실행한다. 모든 이상 현상을 차단하지만 동시 처리 성능이 급격히 떨어진다. 금융 · 극한 정합성 필요 시
MVCC (Multi-Version Concurrency Control) 란? 데이터를 수정할 때 기존 버전을 지우지 않고 새 버전을 추가하는 방식이다. 읽기 트랜잭션은 자신의 시작 시점 버전을 보고, 쓰기 트랜잭션은 새 버전을 만든다. 읽기와 쓰기가 서로를 차단하지 않으므로 잠금 없이 높은 동시성을 유지할 수 있다. MySQL InnoDB, PostgreSQL 모두 MVCC를 사용한다.

MySQL InnoDB의 REPEATABLE_READ — 이론과 실제가 다르다

SQL 표준 vs MySQL InnoDB 실제 
SQL 표준
  REPEATABLE_READ → Non-repeatable Read 차단, Phantom Read 발생 가능

MySQL InnoDB 실제
  REPEATABLE_READ → Non-repeatable Read 차단, Phantom Read 실질적 차단
  이유: 쓰기(UPDATE·DELETE) 시 Gap Lock + Next-Key Lock을 함께 사용하기 때문
Gap Lock / Next-Key Lock 이란? 일반 잠금은 존재하는 row에만 걸리지만, Gap Lock은 row와 row 사이의 빈 공간(gap)에 잠금을 건다. Next-Key Lock은 Gap Lock + 해당 row 잠금의 조합이다. 예를 들어 WHERE 금액 > 1000 조회 후 그 범위에 Next-Key Lock이 걸리면, 다른 트랜잭션이 해당 범위에 INSERT하지 못해 Phantom Read가 발생하지 않는다. 단, SELECT … FOR UPDATE 또는 UPDATE·DELETE 시에만 적용되며, 일반 SELECT(MVCC 스냅샷 읽기)는 Gap Lock 없이 스냅샷만 사용한다.

격리 수준 직접 지정 
// 격리 수준 직접 지정 — 반드시 DB가 해당 레벨을 지원해야 한다
@Transactional(isolation = Isolation.READ_COMMITTED)
public List<Product> getProducts() { ... }

// Spring의 DEFAULT는 DB 기본값을 따름
@Transactional(isolation = Isolation.DEFAULT)
public List<Product> getProducts() { ... }
실무 가이드 대부분의 경우 DB 기본값을 그대로 사용한다. 이상 현상이 실제 문제가 될 때는 격리 수준을 올리는 것보다 SELECT … FOR UPDATE(비관적 락)나 버전 컬럼 비교(낙관적 락)로 해결하는 것이 성능 영향이 적다. SERIALIZABLE은 읽기도 모두 잠그므로 특별한 이유가 없으면 피한다.

핵심 정리

  • @Transactional = AOP Proxy가 트랜잭션 시작/커밋/롤백을 대신 처리
  • REQUIRED: 하나로 묶기 (기본) — 실패하면 전체 롤백
  • REQUIRES_NEW: 완전 별도 트랜잭션 — 내부 커밋은 외부 롤백의 영향 없음, 커넥션 2개 주의
  • NESTED: savepoint 부분 롤백 — 외부 catch 필수, 외부 롤백 시 함께 사라짐
  • Rollback: RuntimeException/Error → 자동 롤백 / Checked Exception → 롤백 안 됨 (기본)
  • catch로 예외 삼키면 Proxy가 인지 못해 롤백 안 됨 — 함정
  • Isolation: 격리 강할수록 이상 현상 줄지만 성능 저하, 실무는 DB 기본값 사용

퀴즈 — 직접 확인해보자

Q1. REQUIRES_NEW로 실행된 내부 트랜잭션이 커밋된 후 외부 트랜잭션이 롤백되면?
A 내부 트랜잭션도 함께 롤백된다
B 두 트랜잭션 모두 롤백된다
C 내부 트랜잭션은 이미 커밋됐으므로 영향 없다
D 외부 트랜잭션도 커밋 강제된다
정답: C
REQUIRES_NEW는 완전히 별개의 트랜잭션이다. 내부가 먼저 커밋되면 외부 롤백과 무관하게 DB에 반영된 상태다. 이것이 감사 로그에 REQUIRES_NEW를 쓰는 이유 — 메인 작업이 실패해도 로그는 남아야 하기 때문이다.
Q2. NESTED 트랜잭션에서 예외가 발생했을 때 외부 트랜잭션이 계속 진행되려면?
A 아무 처리 없이 자동으로 부분 롤백 후 계속된다
B 외부에서 반드시 try-catch로 예외를 잡아야 한다
C NESTED 내부에서 예외를 삼켜야 한다
D rollbackFor 설정으로 제어할 수 있다
정답: B
NESTED가 예외를 던지면 그 예외가 외부 트랜잭션 A까지 전파된다. A가 예외를 받으면 A 전체를 롤백한다. 외부에서 try-catch로 예외를 잡아야만 "NESTED는 savepoint까지 롤백, A는 계속 진행"이 가능하다.
Q3. 다음 코드에서 orderRepo.save()는 어떻게 되는가?
OrderService.java 
@Transactional
public void createOrder() {
    orderRepo.save(order);
    try {
        throw new RuntimeException("실패");
    } catch (RuntimeException e) {
        log.error("에러 발생", e);  // 예외를 삼킴
    }
}
A RuntimeException이므로 롤백된다
B try-catch 내부이므로 롤백된다
C 트랜잭션 자체가 실패한다
D 커밋된다 (Proxy가 예외를 인지하지 못함)
정답: D
catch로 예외를 삼키면 Proxy까지 예외가 전파되지 않는다. Proxy는 예외를 받아야 롤백을 실행하는데, 메서드가 정상적으로 종료된 것처럼 보이므로 커밋한다. orderRepo.save()가 DB에 반영된다.
Q4. @Transactional 기본 설정에서 롤백이 발생하지 않는 경우는?
A IOException 이 throws 로 전파됨
B NullPointerException 이 throws 로 전파됨
C OutOfMemoryError 가 발생함
D IllegalStateException 이 throws 로 전파됨
정답: A
IOException은 Checked Exception이다. RuntimeException을 상속하지 않으므로 @Transactional 기본 설정에서는 롤백하지 않는다. rollbackFor = Exception.class를 명시해야 롤백된다. 나머지(NullPointerException, IllegalStateException)는 RuntimeException, OutOfMemoryError는 Error이므로 모두 기본 롤백 대상이다.
Q5. 트랜잭션 A(REQUIRED) 안에서 NESTED 트랜잭션 B가 실행됐다. B는 성공했고 이후 A에서 예외가 발생했다. 결과는?
A B는 이미 성공했으므로 B 작업은 커밋, A만 롤백
B A 전체 롤백 — B 작업도 함께 취소
C B는 NESTED이므로 항상 독립적으로 커밋 유지
D savepoint 덕분에 B는 커밋, A는 B 이후만 롤백
정답: B
NESTED는 물리적으로 같은 트랜잭션이다. B가 성공했더라도 아직 커밋된 것이 아니라 A와 함께 대기 중인 상태다. A가 롤백되면 savepoint를 포함한 모든 변경이 취소된다. REQUIRES_NEW와 달리 NESTED는 외부 롤백으로부터 보호받지 못한다.
