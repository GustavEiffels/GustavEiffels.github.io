순차 원격 호출 2회, CompletableFuture로 병렬화하기

Java Concurrency CompletableFuture ThreadPoolTaskExecutor 2026-07-13

서로 독립인 원격 호출을 순차로 실행하면 응답시간은 두 지연시간의 합이 된다. 병렬로 실행하면 max가 된다. 실측으로 확인하고, 되는 경우와 안 되는 경우를 정리한다.

1

발견 — 왜 병목인가

코드를 보다가 이런 패턴을 발견했다. 하나의 API 응답을 만들기 위해 레거시 시스템(외부 API)을 연속으로 두 번 호출하는 구조다.

순차 호출 — 리팩터링 전 
public ProductDetailResult getProductDetail(String productId) {
    // 호출 ① 상품 스펙 조회 (~500ms)
    LegacyResponse spec = legacyClient.call("PRODUCT_SPEC", productId);
    List<SpecDto> specs = parseSpec(spec);

    // 호출 ② 상품 리뷰 조회 (~400ms) — ①이 끝나야 시작됨
    LegacyResponse reviews = legacyClient.call("PRODUCT_REVIEWS", productId);
    List<ReviewDto> reviewList = parseReviews(reviews);

    return new ProductDetailResult(specs, reviewList);   // 총 ~900ms
}

여기서 중요한 관찰은 코드가 아니라 두 호출의 관계다:

  • ②는 ①의 결과를 전혀 사용하지 않는다 — 입력(productId)만 같고 서로 독립
  • 그런데 ②는 ①이 끝나기를 기다렸다가 시작한다
  • 따라서 응답시간 = ① + ② = 두 지연시간의 합

레거시 API라 두 호출을 하나로 합치는 수정(서버 쪽 변경)은 불가능한 상황. 그렇다면 남는 선택지는 동시에 실행하는 것이다. 이론상 응답시간은 합(900ms)에서 max(500ms)로 줄어든다.

2

해결 — 설계 결정 3가지

2-1. 제출은 일찍, join은 늦게

병렬화 후 — 제출과 join의 위치가 핵심 
public ProductDetailResult getProductDetail(String productId) {

    // [1] 제출은 가장 이른 지점 — 이 순간부터 ②가 풀 스레드에서 돌기 시작
    CompletableFuture<LegacyResponse> reviewsFuture = CompletableFuture.supplyAsync(
            () -> legacyClient.call("PRODUCT_REVIEWS", productId),
            legacyParallelExecutor);

    // [2] ①은 메인 스레드가 직접 실행 (②가 도는 동안)
    LegacyResponse spec = legacyClient.call("PRODUCT_SPEC", productId);

    // [3] ②를 기다리기 전에, 할 수 있는 일(①의 파싱)을 먼저 해둔다
    List<SpecDto> specs = parseSpec(spec);

    // [4] join은 결과가 필요한 지점 직전 — ②가 이미 끝났으면 대기 0
    LegacyResponse reviews;
    try {
        reviews = reviewsFuture.join();
    } catch (CompletionException e) {
        // 풀 스레드의 예외를 unwrap — 호출부의 기존 catch가 그대로 동작하도록
        if (e.getCause() instanceof RuntimeException re) throw re;
        throw e;
    }

    return new ProductDetailResult(specs, parseReviews(reviews));
}

supplyAsync의 위치가 곧 ②의 실행 시작 시점이다. 문법상 람다가 참조하는 변수들 선언 뒤여야 하고, 성능상 ① 실행 앞이어야 하므로 놓일 자리는 사실상 하나다. 반대로 join()은 메인 스레드가 결과를 기다리는 메서드이므로, 결과가 실제로 필요한 지점 직전까지 최대한 미룬다. 이 사이 구간이 길수록 메인 스레드가 "기다리는 대신 일하는" 시간이 늘어난다.

메인 스레드: [제출]──[① 실행 500ms]──[① 파싱]──[join ~0]──[② 파싱]──[리턴] │ ↑ ▼ │ 풀 스레드: [② 실행 400ms 완료 → future에 결과 저장] → 전체 ≈ max(①, ②) = 500ms

2-2. caller-runs — 하나는 메인 스레드가 직접

둘 다 supplyAsync로 던질 수도 있지만 그러면 메인 스레드는 join에서 놀기만 한다. 어차피 두 결과가 다 나올 때까지 리턴할 수 없다고 판단해서, 한쪽은 메인 스레드가 직접 실행하도록 했다. 전체 시간은 동일(max)인데 풀 스레드 소비는 절반으로 줄었다.

방식동원 스레드풀 스레드 소비전체 시간
둘 다 비동기3 (호출 1 + 풀 2)2max(①,②)
한쪽만 비동기2 (호출 1 + 풀 1)1max(①,②)

이 경험을 일반화해보면, N개를 병렬화할 때 N-1개만 풀에 던지고 1개는 직접 실행하는 쪽으로 하고 있다.

2-3. 포화 시 안전 강등 — CallerRunsPolicy

전용 executor는 작게 잡되, 가득 찼을 때의 동작을 명시적으로 설계했다.

ExecutorConfig.java 
@Bean
public ThreadPoolTaskExecutor legacyParallelExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setThreadNamePrefix("legacy-par-");
    executor.setCorePoolSize(0);          // 유휴 시 스레드 0 (60초 후 정리)
    executor.setMaxPoolSize(4);
    executor.setQueueCapacity(0);         // 큐에 쌓지 않음
    executor.setKeepAliveSeconds(60);
    // 풀 포화 시 메인 스레드가 직접 실행 → 순차 동작으로 강등될 뿐 실패/대기 없음
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}

큐를 두지 않는 이유: 큐에 쌓이면 join이 "앞선 요청들의 작업"까지 기다리게 되어 지연이 전파된다. 큐 없이 CallerRunsPolicy로 떨어뜨리면 최악의 경우가 병렬화 이전과 동일한 순차 실행이라 도입 리스크가 0에 수렴한다.

삽질 포인트 ① — @Primary가 이름 매칭을 이긴다

ThreadPoolTaskExecutor 빈이 여러 개인 프로젝트라, 필드 이름만 믿고 주입했다가 문제를 겪었다.

이름이 같으니 되겠지? — 안 된다 
private final ThreadPoolTaskExecutor legacyParallelExecutor;  // 이름이 같으니 되겠지?

Spring의 자동주입 우선순위는 @Primary > @Priority > 이름 매칭이다. 다른 executor에 @Primary가 붙어 있으면 이름과 무관하게 그쪽이 주입된다. 내 경우 1스레드짜리 웹 작업용 executor가 주입되어 병렬화가 조용히 무력화될 뻔했다. 게다가 lombok @RequiredArgsConstructor는 필드의 @Qualifier를 생성자 파라미터로 복사하지 않는다(lombok.config 설정 필요). 그래서 명시적 생성자 + @Qualifier로 바꿨다.

명시적 생성자 + @Qualifier 
public ProductService(@Qualifier("legacyParallelExecutor") ThreadPoolTaskExecutor executor) {
    this.legacyParallelExecutor = executor;
}

삽질 포인트 ② — 풀 스레드의 예외는 포장돼서 나온다

풀 스레드에서 던진 예외는 join()에서 CompletionException으로 감싸져서 나온다. 호출부에 catch (MyBusinessException e) 같은 기존 예외 처리가 있는데 unwrap을 안 했더니 전부 빗나갔다. 그래서 join을 try로 감싸 getCause()를 꺼내 rethrow하는 보일러플레이트를 추가했다.

3

검증 — 벤치마크와 정직한 해석

측정 설계

성능 비교는 측정 방법이 부실하면 숫자가 의미를 잃는다. 세 가지를 챙겼다:

  1. 워밍업 1회 제외 — 첫 호출은 커넥션 풀, 메타데이터 캐시, 서버 쪽 버퍼가 비어 있어 항상 느리다. 측정에 넣으면 결과가 왜곡된다.
  2. 순차/병렬 번갈아 실행 — 원격 서버의 부하 변동이 한쪽 결과에만 몰리지 않도록.
  3. 결과 동등성 검증 — 매 회차 순차/병렬 결과가 같은지 확인. 성능 이전에 "병렬화가 데이터를 깨뜨리지 않았다"는 증명이 먼저다.

성능 수치에는 assert를 두지 않았다. 네트워크 상황에 따라 역전될 수 있는 값에 assert를 걸면 CI에서 간헐적으로 깨지는 플레이키 테스트가 된다. 숫자는 로그로 판단한다.

실측 결과

회차별 (ms)평균비고
BEFORE (순차)63, 52, 62, 44, 4653.4ms① + ②
AFTER (병렬)26, 26, 25, 25, 2725.8ms≈ max(①,②)

51.7% 개선 — 두 호출이 각각 ~26ms로 비슷해서 이론값(합→max = 50%)에 정확히 수렴했다. 병렬 쪽의 편차가 더 작은 것(25~27ms)도 눈여겨볼 점.

정직한 해석

여기서 멈추면 반쪽짜리 결론이다.

개선율은 구조가 결정하고, 절대 이득은 호출이 느릴수록 커진다 개선율: 두 호출이 비슷하면 ~50%로 고정 (합→max의 구조적 결과). 절대 이득: 내 환경은 호출당 ~26ms라 27ms 단축에 그쳤다. 사용자가 체감할 수 있는 차이가 아니다. 같은 코드가 호출당 1초 걸리는 환경이었다면 1초를 아꼈을 것이다.

즉 이 패턴의 가치는 "얼마나 개선되는가(%)"가 아니라 "호출이 얼마나 느린가(ms)"에 비례한다고 봤다. 그래서 앞으로는 적용 전에 각 호출의 실제 소요시간부터 로그로 확인하려고 한다. 빠른 호출을 병렬화하면 "동작은 완벽한데 체감은 없는" 결과가 나올 것 같아서다.

4

일반화 — 언제 쓸지, 언제 안 쓸지 정리해봤다

내가 세운 판단 순서

⓪ 합칠 수 있으면 합치는 쪽을 먼저 생각했다 병렬화는 왕복 2회를 겹치는 것이고, 통합은 왕복을 1회로 줄이는 것이라 통합 쪽이 더 근본적인 해결이라고 봤다. DB 쿼리라면 JOIN/UNION, 자체 API라면 엔드포인트 통합을 먼저 고려했다. 병렬화는 합칠 수 없을 때(레거시·외부 시스템·남의 코드) 꺼내는 도구로 삼았다.

① 합칠 수 없다면, 다음 세 조건을 확인해보기로 했다:

조건확인 방법
상호 독립 — 한쪽 결과가 다른 쪽 입력이 아님호출 순서를 바꿔도 결과가 같은가
읽기 전용 + 트랜잭션 밖쓰기가 있으면 원자성 상실
개당 충분히 느림 (수십~수백 ms↑)각 호출의 elapsed 로그 실측

내가 적용하지 않기로 한 경우

  • 쓰기 트랜잭션 안: Spring의 @Transactional은 ThreadLocal에 바인딩되어 스레드를 넘어가지 않는다. 풀 스레드의 작업은 별도 커넥션·별도 트랜잭션으로 돌아서, 호출부가 롤백돼도 같이 롤백되지 않고, 호출부의 미커밋 데이터도 보지 못한다.
  • 빠른 호출: 수 ms짜리 호출 2개를 병렬화하면 수 ms 아끼자고 스레드 넘김 비용을 내는 꼴이다.
  • 커넥션 풀 여유가 없을 때: 병렬 스레드도 커넥션을 하나씩 잡는다. 요청당 커넥션 2개 × 동시 요청 수가 풀 최대치 안에 있어야 한다.

내가 생각한 이상적인 후보: 조회 전용 프로시저

DB 저장 프로시저 중 조회만 하는 것들이 이 패턴에 잘 맞는다고 생각했다.

  • 프로시저는 이미 굳어진 로직 덩어리라 합치기 어렵다 (⓪ 탈락 → 병렬화를 먼저 검토)
  • 무거운 집계 로직이 많아 개당 느린 경우가 흔했다
  • 조회 전용이라는 조건 하나로 3대 위험이 한꺼번에 사라진다고 판단했다: 트랜잭션 원자성 문제(쓸 게 없음), 숨은 의존성(쓴 데이터를 읽을 일 없음), 락 경합(읽기 락끼리는 충돌 안 함)

단, "이름은 조회용인데 내부에서 temp table에 INSERT하는" 프로시저를 본 적이 있어서 내부 확인은 한 번씩 해보고 있다.

내가 정리한 경험칙 느린 원격 호출은 병렬화를 검토하고, 느린 DB 쿼리는 쿼리부터 고치는 쪽으로 판단하고 있다.

요약

  • 서로 독립인 원격 호출의 순차 실행은 응답시간이 합 — 병렬화하면 max
  • 내가 잡은 구현 방향: 제출은 일찍, join은 늦게 + caller-runs(N-1개만 풀에) + CallerRunsPolicy(포화 시 순차로 안전 강등)
  • 겪은 함정: @Primary가 이름 매칭을 이긴다(@Qualifier 명시로 해결), 풀 스레드의 예외는 CompletionException으로 감싸진다(unwrap 처리 추가)
  • 실측 51.7% 개선 — 단 개선율은 구조가, 절대 이득은 호출 지연이 결정
  • 적용 조건으로 삼은 것: 합칠 수 없음 + 독립 + 읽기 전용 + 개당 느림 → 조회 전용 프로시저를 좋은 후보로 봤다
