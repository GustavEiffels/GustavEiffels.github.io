Frontend — 카드 리스트 렌더링 메모이제이션 최적화

Frontend React memo DOM 가상화 2026-07-15

클로저와 memo 무력화 · 비교 함수 설계 · DOM 가상화 — "계산"과 "그리기"를 분리해서 본다

대상 예시: 카드 리스트를 그리는 가상의 컴포넌트(실제 코드가 아닌 개념 설명용 analogy)

범위: 그리기(렌더링) 단계만 다룬다. 자료구조 계산 단계(부모-자식 맵 재사용, 방문 Set 공유 등)는 댓글 스레드 접기/펴기 계산 최적화 문서 참고. 이 문서는 그 계산이 끝난 이후, 결과를 화면에 반영하는 단계에서 벌어지는 문제를 다룬다.

0

배경 — "계산"과 "그리기"는 다른 단계

카드 100장을 리스트로 그리는 컴포넌트가 있다고 하자. 카드 하나를 클릭하면 그 카드의 상세 설명(detail)을 펼치거나 접는다. 계산 단계(어떤 카드가 펼쳐져 있는지 파악하는 로직)를 아무리 잘 최적화해도, 그 결과를 화면에 반영하는 단계에서 다시 병목이 생길 수 있다.

카드 클릭 │ ├─ [계산 단계] openIds(펼쳐진 카드 id 집합) 갱신 + 카드 배열 재생성(.map()) │ 자바스크립트 배열/객체를 새로 만드는 순수 연산. │ 매번 전체 재실행되는 게 정상 — 다른 카드도 같은 배열 안에서 함께 관리되므로 불가피. │ └─ [그리기 단계] React가 "이 컴포넌트를 실제로 다시 그릴지" 판단 + 브라우저가 DOM 갱신 여기가 이번 문서의 대상

"카드 배열을 매번 새로 만드는 것" 자체는 문제가 아니다. 문제는 "새 배열 = 카드 100장 전부 다시 그려야 한다"로 이어지는 부분이다.

1

React는 참조로만 비교한다

reference-equality.js 
const a = { name: 'X' };
const b = { name: 'X' };
a === b   // false — 내용이 같아도 다른 객체

카드 배열의 .map()은 펼침 상태가 바뀔 때마다 모든 카드의 props 객체를 새로 만든다. memo 없이는 React가 "새 참조 = 다시 그려야 함"이라고 판단해서, 내용이 하나도 안 바뀐 카드까지 전부 리렌더한다.

2

상황 재현 — Before 코드

카드 하나를 그리는 컴포넌트와, 그 카드들을 나열하는 리스트 컴포넌트를 실무에서 흔히 보이는 형태로 재현한다. (아래 이름 Card, openIds, onToggleDetail은 전부 예시용이며 실제 코드가 아니다.)

BEFORE
CardList.jsx (Before) 
// memo 없음 — 부모가 리렌더되면 무조건 같이 리렌더된다
function Card({ data }) {
  return (
    <div onClick={() => data.onToggleDetail()}>
      {data.title}
      {data.detailOpen && <p>{data.description}</p>}
    </div>
  );
}

const renderedCards = useMemo(
  () =>
    cards.map((c) => ({
      ...c,
      detailOpen: openIds.has(c.id),
      onToggleDetail: () => toggleDetail(c.id),   // ← 클로저 ①: 카드마다 매번 새 함수
    })),
  [cards, openIds, toggleDetail],
);

// 화면 밖 카드도 전부 DOM에 존재
<CardCanvas items={renderedCards} />
핵심 문제 3가지 ① Card에 memo 자체가 없어서 부모가 리렌더되면 무조건 다 같이 다시 그려진다. ② onToggleDetail이 매 렌더마다 카드별로 새 클로저를 만든다. ③ 화면 밖에 있는 카드도 DOM에 그대로 존재한다.
3

왜 클로저가 memo를 무력화시키는가

closure-identity.js 
const f1 = () => toggleDetail('c3');  // 1번째 렌더 때 생성
const f2 = () => toggleDetail('c3');  // 2번째 렌더 때 생성
f1 === f2   // false — 하는 일이 완전히 같은데도!

함수는 "내용이 같은가"를 비교할 방법이 원리적으로 없다(참조 비교만 가능하다). .toString()으로도 안 통한다 — 소스 텍스트는 모든 카드에서 완전히 똑같아서, 실제로 캡처된 값(c.id)은 텍스트로 안 보인다.

클로저를 쓴 것 자체가 문제는 아니다. Before/After 둘 다 "클로저는 렌더링 시점에 만들어지고, 실제 실행은 나중에 클릭했을 때"라는 패턴은 동일하다. 진짜 차이는 그 클로저가 어디서 만들어지고, memo가 비교하는 props 안에 들어가는가다.

BeforeAfter
클로저가 만들어지는 곳부모의 .map() — 보이는 카드 전체카드 자기 자신의 렌더 안 — 1개분만
memo가 비교하는 props에 들어가나들어감 → 비교 대상이 됨안 들어감 → 비교와 무관
몇 개 만들어지나토글 1번에 보이는 카드 전부(예: 100개)실제로 재렌더된 카드만(예: 1~2개)
정확한 원인 memo가 비교해야 하는 props라는 그릇 안에, 매번 새로 만들어지는 클로저를 넣어서 문제였다. 이 필드를 비교에 넣는 순간 비교 함수 전체가 항상 false를 리턴하게 되어 memo가 무력화된다.
4

수정 ① — 클로저 제거

BEFORE
Before 
data: { ...c, onToggleDetail: () => toggleDetail(c.id) }
AFTER
After 
data: { ...c, onToggleDetail: toggleDetail }   // 안정 참조 그대로 전달

const Card = memo(function Card({ id, data }) {
  return <div onClick={() => data.onToggleDetail(id)}>   // 호출 시점에 id를 인자로
    ...
  </div>;
}, cardPropsEqual);

toggleDetail은 useCallback(fn, [])로 만들어져서 컴포넌트가 살아있는 동안 항상 같은 함수 객체다. 카드 100개 모두 같은 참조를 공유하게 되어 비교할 필요조차 없어진다.

5

수정 ② — memo + 비교 함수

cardPropsEqual.js 
function cardPropsEqual(prev, next) {
  const a = prev.data;
  const b = next.data;
  return (
    prev.id === next.id &&
    a.title === b.title &&
    a.description === b.description &&
    !!a.detailOpen === !!b.detailOpen
    // onToggleDetail 은 의도적으로 제외 — 항상 안정 참조라 비교 불필요
  );
}

const Card = memo(function Card({ id, data }) { ... }, cardPropsEqual);

memo(function X(...) {...}, compareFn) 문법 — 컴포넌트 함수를 변수에 담기 전에 memo()의 인자로 먼저 통과시키는 패턴이다. 소스코드 어디에도 cardPropsEqual(a, b)를 직접 호출하는 줄은 없다. memo(...)로 등록해두면 React가 새 props를 내려줄 때마다 내부적으로 자동 호출한다.

shallow-copy.js 
const copy = { ...card };
copy === card                  // false (껍데기는 새 객체)
copy.description === card.description   // true! (원본 문자열/객체 참조는 그대로)

.map()이 만드는 건 data라는 껍데기뿐이고, 안의 필드는 원본 데이터의 참조를 그대로 물고 있다(얕은 복사). 그래서 얕은 === 비교만으로 충분하다.

6

전체 그림 — "일단 다 새로 만들고, 바뀐 것만 화면에 반영"

[1] .map() 이 카드 100장을 조건 없이 통째로 새로 생성 (Card/memo의 존재를 모름 — 전부 새 객체) │ (완전히 끝난 뒤, 별개의 단계로) ▼ [2] React가 이 배열로 <Card> 엘리먼트를 하나씩 순회 → 각 카드마다 cardPropsEqual(이전, 새것) 호출 → true(안 바뀜) → 화면에 그려져 있던 카드 그대로 유지 → false(바뀜) → 그 카드만 실제로 다시 그려짐
비유 서류(데이터)는 100장 전부 새로 인쇄하지만, 게시판(화면)에는 내용이 실제로 바뀐 서류만 뽑아서 갈아 끼우고 나머지는 그대로 둔다.
7

수정 ③ — 화면 밖 카드는 그리지 않는다 (DOM 가상화)

Chapter 4~5(memo)와는 완전히 다른 층위의 최적화다.

① ② (memo + cardPropsEqual) → DOM 노드 100장은 그대로 존재 → "내용이 안 바뀐 것"은 리렌더(JSX 재평가)를 건너뜀 → "다시 그리는 비용"을 줄임 ③ (가상화) → 애초에 DOM 노드 자체를 뷰포트에 보이는 ~15장만 만듦 → 화면 밖 85장은 존재 자체가 없음(mount 안 됨) → "존재하는 것 자체의 비용"을 줄임

브라우저에서 DOM 노드는 화면에 안 보여도 스타일 계산·레이아웃 계산·메모리를 차지한다. memo를 아무리 잘 써도 이 비용은 못 줄인다.

virtualization.jsx 
<CardCanvas items={renderedCards} renderOnlyVisible />
트레이드오프 스크롤 애니메이션 중 뷰포트가 움직이며 경계에서 mount/unmount가 반복될 수 있다. 카드 수가 적은 리스트에선 오히려 스크롤이 미세하게 덜 부드러울 수 있음 — 그 경우 이 옵션 한 줄만 빼면 된다.
8

이번 최적화와 무관한 부분 구분하기

같은 리스트 컴포넌트 안에 있어도 이번 최적화 대상이 아닌 상태가 섞여 있을 수 있다. 무엇이 대상이고 무엇이 아닌지 구분해두면, 나중에 코드를 다시 볼 때 "이건 왜 안 고쳤지?"라는 혼란을 막을 수 있다.

대상상태함수이번 최적화 대상?
카드 선택카드 하나 강조 표시selectedIdonSelectCard아님
상세 펼침카드 하나의 detail 내용openIdsonToggleDetail이번 문서 전체

onSelectCard는 .map() 안에서 카드마다 만들어지는 함수가 아니라 <CardCanvas onItemClick={onSelectCard} />처럼 리스트 전체에 하나만 연결되는 핸들러다. CardCanvas가 클릭된 카드 정보를 인자로 직접 넘겨주므로 클로저 문제 자체가 없다.

10

일반화 — 다른 코드에도 적용 가능한 패턴

  • 파생물 재계산 구조 + memo는 세트 — "매번 새 객체" 설계를 유지하려면 "내용 같으면 skip"을 memo로 별도 선언해야 한다.
  • memo 하려면 먼저 클로저부터 제거 — 항목별 () => handle(id)는 매번 새 함수라 어떤 비교도 무력화시킨다.
  • 클로저 자체가 아니라 "어디 있는가"가 문제 — memo가 비교하는 props 안에 있으면 위험하다.
  • 비교 함수엔 화면 반영 값 전부 — 하나라도 빼먹으면 stale 렌더 버그가 생긴다.
  • "다시 그리기 비용"과 "존재 비용"은 다른 문제 — memo는 전자만, DOM 가상화는 후자를 해결한다.

핵심 정리

  • 계산 결과가 매번 새 객체인 것 자체는 문제가 아니다 — "새 참조 = 무조건 다시 그림"으로 이어지는 게 문제다
  • 함수는 내용이 아니라 참조로만 비교된다 — 항목마다 만드는 인라인 콜백은 memo를 항상 깨뜨린다
  • 콜백을 상위에서 안정 참조로 내려주고, 호출 시점에 id를 인자로 넘기면 클로저 없이도 같은 동작을 유지할 수 있다
  • 비교 함수(compareFn)에는 화면에 실제로 반영되는 값만 넣고, 항상 같은 안정 참조인 콜백은 뺀다
  • "다시 그리는 비용"은 memo, "DOM에 존재하는 비용"은 가상화 — 서로 다른 층위의 최적화다

자료구조 계산 단계(부모-자식 맵 재사용, 방문 Set 공유, useMemo 캐싱)의 최적화는 댓글 스레드 접기/펴기 계산 최적화 문서 참고.
