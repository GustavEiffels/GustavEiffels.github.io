B 트리 & B+ 트리 완전 이해

디스크 I/O부터 세컨더리 인덱스까지 — DB 인덱스의 모든 것

CH 1

왜 B 트리가 필요한가

1

디스크는 RAM보다 수만 배 느리다

데이터베이스 성능의 핵심은 디스크를 몇 번 읽느냐다. 아무리 좋은 알고리즘도 디스크 접근이 많으면 느려진다.

접근 속도 비교 
RAM 접근:      ~100 나노초
SSD 접근:   ~100,000 나노초   (RAM의 1,000배)
HDD 접근: ~10,000,000 나노초  (RAM의 100,000배)
핵심 원칙 디스크 접근 횟수를 최소화하는 것 = DB 성능 최적화의 전부
2

이진 탐색 트리(BST)의 한계

BST는 노드 하나에 키 하나만 담는다. 1억 개 데이터를 찾으려면 최대 27번 디스크를 읽어야 한다.

BST 깊이 계산 
BST (1억 개, 균형 상태):
깊이 = log₂(100,000,000) ≈ 27

→ 디스크 접근 27회 × HDD 10ms = 270ms

더 심각한 문제는 순서대로 삽입하면 트리가 한쪽으로 쏠려 O(n)까지 악화된다.

순서 삽입 시 편향 
순서 삽입 1→2→3→4→5:

[1]
  \
  [2]        ← 사실상 연결 리스트
    \
    [3]       탐색: 최악 O(n)
      \
      [4]
        \
        [5]
3

B 트리의 핵심 아이디어

"노드 하나에 키를 수백 개 담아서, 트리를 납작하게 만들자"

BST vs B 트리 
BST   → 노드당 키 1개   → 깊이 27 → 디스크 27번
B트리 → 노드당 키 200개 → 깊이  4 → 디스크  4번

1억 개 데이터 기준, HDD:
BST   = 27 × 10ms = 270ms
B트리 =  4 × 10ms =  40ms   ← 약 7배 빠름
CH 2

로그(log)와 빅 O 표기법

1

log가 왜 등장하는가

트리에서 데이터를 찾는 것은 "n을 계속 절반으로 나눠 1이 될 때까지의 횟수"와 같다.

이진 탐색과 log 
8개 데이터를 이진 탐색으로:
8 → 4 → 2 → 1
   ÷2   ÷2   ÷2   = 3번 = log₂(8)

2^x = n  →  x = log₂(n)
2

왜 빅 O에서는 밑(base)을 안 쓰는가

log의 밑이 달라도 서로 상수배 차이에 불과하며, 빅 O는 상수를 버린다.

밑 변환 
log₂(n)  = log₁₀(n) / log₁₀(2)
          = 3.32 × log₁₀(n)

O(3.32 × log₁₀(n))
= O(log₁₀(n))     ← 3.32는 상수, 제거
= O(log₂(n))      ← 밑 변환도 상수배 차이뿐
= O(log n)        ← 밑을 생략
결론 log₂든 log₁₀₀이든 빅 O에서는 모두 O(log n). 단, 실제 성능은 밑이 클수록 트리가 납작해져 빠르다. B 트리가 빠른 이유가 바로 이것이다.
CH 3

이진 트리 vs 균형 트리

1

이진 트리 — 규칙이 적다

유일한 규칙: 자식이 최대 2개. 모양에 제한이 없어 한쪽으로 쏠려도 트리라 부른다.

항목이진 트리균형 트리
자식 수최대 2개최대 2개 (이진 기준)
정렬 규칙없음 (BST는 있음)있음
균형 보장없음항상 유지
최악 탐색O(n)O(log n)
삽입 복잡도단순복잡 (회전 필요)
2

균형을 맞추는 방법 — 회전(Rotation)

트리 회전 
불균형:           회전 후:

  [1]               [2]
    \               / \
    [2]    →→→   [1]  [3]
      \
      [3]

균형 트리의 종류: AVL 트리 Red-Black 트리 B 트리

CH 4

B 트리 구조

1

노드 구조와 규칙

B 트리 노드 구조 
차수 t 기준 노드:

┌──────────────────────────────────────────────────┐
│  p₀ | k₁,📍 | p₁ | k₂,📍 | p₂ | k₃,📍 | p₃   │
└──────────────────────────────────────────────────┘
  ↓              ↓              ↓
자식노드       자식노드       자식노드
주소           주소           주소

k = 키(PK),  📍 = 실제 데이터 위치,  p = 자식 노드 주소

B 트리는 모든 노드에 키 + 데이터 위치를 함께 저장한다.

규칙내용
정렬노드 안 키는 오름차순
자식 범위p₀의 모든 값 < k₁ < p₁의 모든 값 < k₂ ...
균형모든 리프 노드가 같은 깊이
최소 채움루트 제외 모든 노드는 최소 t-1개 키 보유
2

삽입과 노드 분할

노드가 꽉 차면 중간 키가 부모로 올라가고 노드가 둘로 분할된다.

노드 분할 예시 
삽입 전 (꽉 참):  [10 | 20 | 30]

25 삽입:
         [20]           ← 중간값이 부모로 올라감
        /    \
    [10]   [25|30]      ← 분할
CH 5

B+ 트리 구조

1

B 트리와의 결정적 차이

B 트리

모든 노드(내부 + 리프)에 키 + 데이터 위치 저장

내부 노드가 무거워 노드당 키 수가 적음

범위 검색 시 트리를 위아래로 반복 탐색

B+ 트리 (실제 DB)

내부 노드: 키만 저장 (가벼움)

리프 노드: 키 + 데이터 위치 저장

리프끼리 연결 리스트로 연결 → 범위 검색 빠름

2

B+ 트리 전체 그림

왜 내부 노드가 가벼우면 좋은가? 내부 노드에 데이터 위치가 없어서 같은 공간에 키를 더 많이 넣을 수 있다. 키가 많을수록 트리가 더 납작해지고, 디스크 접근이 더 줄어든다.
CH 6

B 트리 vs B+ 트리 완전 비교

1

구조 차이 — 노드에 뭐가 들어있나

가장 결정적인 차이는 내부 노드에 데이터를 저장하느냐다.

B 트리 vs B+ 트리 노드 비교 
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  B 트리 — 모든 노드에 키 + 데이터 위치 저장
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

           [20,📍 | 40,📍]           ← 내부 노드도 📍 보유
           ↙               ↘
  [10,📍|15,📍]    [30,📍|35,📍]    ← 리프 노드도 📍 보유

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  B+ 트리 — 내부 노드: 키만 / 리프 노드: 키 + 데이터 위치
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

           [ 20  |  40 ]             ← 내부 노드: 키만 (📍 없음)
          ↙       ↓       ↘
  [10,📍|15,📍] [20,📍|30,📍] [40,📍|50,📍]

  ※ 내부 노드의 키 20 = 두 번째 리프의 첫 키 복사본

  [10,📍|15,📍] →→ [20,📍|30,📍] →→ [40,📍|50,📍]
                                    ← 리프끼리 연결됨
2

내부 노드가 가벼우면 왜 좋은가

디스크는 블록 단위(보통 4KB~16KB)로 읽는다. 노드 크기 = 블록 크기로 맞춰두면 한 번 읽기에 담을 수 있는 키 수가 결정된다.

같은 4KB 블록에서 키 수 비교 
B 트리 내부 노드 (키 + 📍 같이 저장):
┌────────────────────────────────────────────────┐
│ [키+📍] [키+📍] [키+📍] [키+📍] [키+📍]      │  → 키 5개
└────────────────────────────────────────────────┘

B+ 트리 내부 노드 (키만 저장):
┌────────────────────────────────────────────────┐
│ [키] [키] [키] [키] [키] [키] [키] [키] [키]  │  → 키 9개
└────────────────────────────────────────────────┘

→ 같은 공간에 키가 더 많음
→ 자식 노드 수도 더 많음
→ 트리가 더 납작해짐
→ 디스크 접근 횟수 감소
3

동일한 값 탐색 비교 (PK=20 찾기)

단일 탐색 비교 
━━━ B 트리에서 PK=20 탐색 ━━━

           [20,📍 | 40,📍]
            ↓
         PK=20 발견!
         → 내부 노드에서 바로 📍 획득
         → 실제 데이터 읽기
         디스크 접근: 2번

━━━ B+ 트리에서 PK=20 탐색 ━━━

           [ 20  |  40 ]
           ↙      ↓      ↘
   [10|15]  [20,📍|30,📍]  [40,📍|50,📍]

         내부 노드에서 20 발견
         → 하지만 📍 없음 (경계값 복사본일 뿐)
         → 20 이상이므로 가운데 자식으로 내려감
         → 리프에서 PK=20 + 📍 획득
         → 실제 데이터 읽기
         디스크 접근: 3번 (항상 리프까지 내려감)
B 트리가 단일 탐색은 더 빠를 수 있다 운이 좋으면 내부 노드에서 바로 데이터를 찾을 수 있다. 하지만 실제 DB에서는 이 이점보다 B+ 트리의 다른 장점들이 훨씬 크다.
4

범위 탐색 비교 (PK 20~40 찾기)

범위 탐색 비교 
━━━ B 트리에서 20~40 범위 탐색 ━━━

              [30,📍]
              ↙      ↘
        [20,📍]    [40,📍]

  STEP 1: 루트에서 20 찾기 → 왼쪽 자식으로
  STEP 2: [20,📍] 발견 → 읽음
  STEP 3: 다음 값(30)을 찾으러 다시 루트로 올라가야 함
  STEP 4: [30,📍] 발견 → 읽음
  STEP 5: 다음 값(40)을 찾으러 다시 루트로 올라가야 함
  STEP 6: [40,📍] 발견 → 읽음
  → 값 하나 읽을 때마다 루트부터 다시 탐색 = 비효율

━━━ B+ 트리에서 20~40 범위 탐색 ━━━

              [ 20 | 40 ]
             ↙     ↓      ↘
    [10|15] [20,📍|30,📍] [40,📍|50,📍]

  STEP 1: 내부 노드에서 20 위치 파악 → 두 번째 리프로 이동
  STEP 2: [20,📍] → 읽음 → 오른쪽으로 이동 (연결 리스트)
          [30,📍] → 읽음 → 다음 리프로 이동
          [40,📍] → 읽음 → 범위 끝, 완료

  트리를 위아래로 오갈 필요 없이 리프를 옆으로 읽기만 하면 됨
B+ 트리가 DB에서 채택된 핵심 이유 DB는 범위 검색(BETWEEN, >, <, ORDER BY)이 매우 빈번하다. 리프가 연결 리스트로 이어진 B+ 트리는 범위 검색에서 압도적으로 유리하다.

항목B 트리B+ 트리

CH 7

노드 상세 — 무엇이 저장되나

1

"위치"에는 두 종류가 있다

이 부분이 가장 혼란스러운 지점이다. "위치"는 두 가지 완전히 다른 개념이다.

종류의미저장 위치
① 자식 노드 주소 다음에 읽을 트리 노드가 디스크 어디에 있는지 내부 노드 + 리프 이전까지
② 실제 데이터 주소 실제 row 데이터가 디스크 어디에 있는지 리프 노드에만
2

내부 노드 vs 리프 노드 저장 내용

노드별 저장 내용 
내부 노드:
┌──────────────────────────────────────────────────┐
│  자식주소① | PK=30 | 자식주소② | PK=70 | 자식주소③ │
│                                                  │
│  ✅ 자식 노드 주소 ①  (트리 탐색용)              │
│  ❌ 실제 데이터 주소 ② (없음)                    │
└──────────────────────────────────────────────────┘

리프 노드:
┌──────────────────────────────────────────────────┐
│  PK=10, 실제데이터주소②                          │
│  PK=20, 실제데이터주소②                          │
│                                                  │
│  ❌ 자식 노드 주소 ① (자식이 없으니까)            │
│  ✅ 실제 데이터 주소 ② (여기서만 row에 접근)     │
└──────────────────────────────────────────────────┘
결론 내부 노드도 "위치"를 저장한다. 단, 그것은 row 데이터 위치가 아닌 자식 노드 위치다. "위치"가 두 종류였던 것이 혼란의 원인이었다.
3

PK=40 탐색 흐름

탐색 단계별 디스크 접근 
1단계: 루트(내부 노드) 읽기
       40 > 30, 40 < 70
       → 자식 노드 주소② 로 이동   (디스크 1회)

2단계: 리프 노드 읽기
       PK=40 발견 → 실제 데이터 주소② 획득   (디스크 1회)

3단계: 실제 row 데이터 읽기
       { PK:40, name:"이영희", ... }   (디스크 1회)

총 디스크 접근 = 3번

세컨더리 인덱스 — PK가 아닌 컬럼으로 검색

1

인덱스가 없을 때 — Full Table Scan

인덱스 없는 name 검색

-- name에 인덱스 없음

리프 노드를 처음부터 끝까지 전부 읽음

[PK=1,📍] → [PK=2,📍] → [PK=3,📍] → ... → [PK=100만,📍]
    ↓            ↓            ↓
  row읽기      row읽기      row읽기
  name확인     name확인     name확인
  아니면패스   아니면패스   발견!

→ 최악 100만 번 디스크 접근
2

세컨더리 인덱스 — name 전용 B+ 트리 별도 생성

CREATE INDEX idx_name ON users(name); 실행 시 name 전용 B+ 트리가 따로 만들어진다.

name 인덱스 B+ 트리 
name 인덱스 B+ 트리 (세컨더리 인덱스):

           [김 | 이]
          ↙          ↘
   [강OO|김OO]     [이OO|홍OO]

   리프 노드 (name 오름차순 정렬):

   [강철수, PK=5 ]
   [김철수, PK=2 ]   ← 실제 row 없음, PK만 저장
   [이영희, PK=40]
   [홍길동, PK=1 ]
세컨더리 인덱스의 특징 리프 노드에 실제 데이터가 없고 PK만 있다. PK를 얻은 뒤 클러스터드 인덱스를 다시 탐색해야 한다.

인덱스를 건다는 것 = 그 컬럼 전용 B+ 트리를 하나 더 만드는 것이다.

영향내용
저장 공간인덱스 B+ 트리만큼 디스크 추가 사용

수정 속도인덱스 컬럼 수정 시 트리 재조정 발생

결론 조회가 많고 수정이 적은 컬럼에만 인덱스를 건다. 남발하면 쓰기 성능이 급격히 나빠진다.
CH 9

연결 리스트 관점에서 B 트리를 쓰는 이유

1

연결 리스트의 한계

연결 리스트 탐색 
[10] → [20] → [30] → [40] → [50] → null

장점: 삽입·삭제 O(1)  (포인터만 바꾸면 됨)
단점: 탐색 O(n)       (처음부터 하나씩 순서대로 봐야 함)

정렬된 연결 리스트로 40을 찾는다:
[10] → [20] → [30] → [40] ← 발견
  1번      2번      3번      4번 이동

→ 1억 개면 최악 1억 번 = O(n)
→ 이진 탐색 불가 (중간 노드로 바로 이동할 방법이 없음)
핵심 문제 정렬된 연결 리스트라도 원하는 값을 찾으려면 앞에서부터 하나씩 봐야 한다. 이진 탐색(Binary Search)이 불가능하다.
2

B 트리 = 연결 리스트 위에 "색인"을 얹은 것

B+ 트리의 발상은 간단하다. 리프 노드는 정렬된 연결 리스트로 두고, 그 위에 트리 색인을 얹어 시작점을 O(log n)에 찾는다.

B+ 트리 = 색인 + 연결 리스트 
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  트리 색인 (내부 노드) — O(log n)에 위치 탐색
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

              [ 30  |  60 ]
             ↙      ↓      ↘
        [15|20]  [40|50]  [70|80]

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  리프 노드 (= 정렬된 연결 리스트)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[10,📍]→[15,📍]→[20,📍]→[30,📍]→[40,📍]→[50,📍]→[70,📍]→[80,📍]

  단순 연결 리스트:  40 찾기 → 처음부터 4번 이동
  B+ 트리:          40 찾기 → 트리로 리프 위치 먼저 특정 → 바로 접근
3

범위 검색에서 연결 리스트가 빛난다

WHERE age BETWEEN 30 AND 60 같은 범위 검색에서 B+ 트리의 리프 연결 구조가 위력을 발휘한다.

범위 검색 흐름 
1단계: 트리로 30 위치를 O(log n)에 찾는다

2단계: 리프 연결 리스트를 오른쪽으로 쭉 읽는다

[30,📍] → [40,📍] → [50,📍] → [60,📍] → 끝
  ↓            ↓           ↓          ↓
읽기         읽기        읽기        읽기    → 완료!
B 트리와의 차이 B 트리는 리프끼리 연결이 없다. 30~60 범위를 찾으면 30 발견 → 트리 위로 올라감 → 40 찾음 → 위로 올라감 → 반복. B+ 트리는 리프가 연결되어 있어 한 방향으로 쭉 읽으면 끝난다.
4

자료구조별 성능 비교

자료구조탐색범위 검색삽입·삭제DB 적합성
연결 리스트 O(n) O(n) O(1) 부적합
이진 탐색 트리 O(log n) ~ O(n) O(log n) ~ O(n) O(log n) ~ O(n) 균형 보장 없음
B 트리 O(log n) 느림 (연결 없음) O(log n) 부분 적합
B+ 트리 O(log n) O(log n + k) O(log n) 최적

k = 범위 결과 개수

CH 10

B 트리 균형 유지 — 분할·병합 상세

1

B 트리는 회전을 쓰지 않는다

AVL 트리나 Red-Black 트리는 회전(Rotation)으로 균형을 잡는다. B 트리는 회전이 아닌 분할(Split)과 병합(Merge)으로 균형을 유지한다.

트리 종류균형 유지 방법언제 발생
AVL 트리회전 (Rotation)삽입·삭제 시 높이 차 1 초과
Red-Black 트리회전 + 색 변경삽입·삭제 시 규칙 위반
B 트리분할 + 병합·재분배노드가 꽉 참 / 너무 빔
2

삽입 — 노드 분할(Split)

차수 t=2 기준 (노드당 최대 3개 키). 노드가 꽉 차면 중간 키가 부모로 올라가고 노드가 둘로 쪼개진다.

예시: 빈 트리에 1, 2, 3, 4, 5, 6 순서로 삽입
노드 분할 단계 
Step 1 — 1, 2, 3 삽입 (노드가 꽉 참):
[ 1 | 2 | 3 ]   ← 최대치 도달

Step 2 — 4 삽입 시 분할 발생:
꽉 찬 상태에서 4를 넣으려 하면:
[ 1 | 2 | 3 | 4 ]  ← 오버플로!

중간값 2가 부모로 올라감:

        [2]           ← 중간값 부모로 상승
       /   \
    [1]   [3|4]       ← 양쪽으로 분할

Step 3 — 5 삽입:
        [2]
       /   \
    [1]   [3|4|5]     ← 5 삽입, 아직 공간 있음

Step 4 — 6 삽입 시 오른쪽 노드 분할:
오른쪽 노드 [3|4|5|6] 오버플로
중간값 4가 부모로 올라감:

        [2 | 4]        ← 4가 루트로 상승
       /   |   \
    [1]  [3]  [5|6]   ← 분할 완료
분할의 핵심 규칙 중간값(median)이 부모로 올라가므로 트리의 정렬 속성이 항상 유지된다. 루트가 분할되면 트리 높이가 1 증가하고, 이때만 높이가 변한다.
3

삭제 — 병합(Merge)과 재분배(Redistribute)

삭제 후 노드의 키가 최솟값(t-1개) 미만이 되면 두 가지 방법으로 복구한다.

방법 A — 재분배 (형제 노드에서 빌리기)
재분배 
삭제 전:
        [20]
       /    \
  [10|15]   [30]     ← 30 삭제

30 삭제 후 오른쪽이 빔:
        [20]
       /    \
  [10|15]   []       ← 최솟값 미만!

형제([10|15])에서 15를 빌림:
        [15]          ← 부모 20이 내려오고, 15가 부모 자리로 올라감
       /    \
    [10]   [20]      ← 재분배 완료
방법 B — 병합 (형제와 합치기)
병합 
삭제 전:
        [20]
       /    \
    [10]   [30]      ← 형제도 최솟값(키 1개)이라 빌려줄 수 없음

30 삭제 후:
        [20]
       /    \
    [10]    []       ← 최솟값 미만!

형제 병합 — 부모(20)가 내려와서 합침:

    [10 | 20]        ← 루트가 사라지고 높이 1 감소
    (단일 노드)
병합과 재분배 선택 기준 형제 노드가 키를 빌려줄 수 있으면 → 재분배 (트리 높이 유지)
형제 노드도 최솟값이면 → 병합 (트리 높이 감소 가능)
4

균형 유지 흐름 요약

삽입·삭제 시 균형 처리 
삽입 시:
  노드 공간 있음   → 그냥 삽입 후 정렬
  노드 꽉 참       → 분할(Split): 중간값을 부모로, 둘로 쪼갬
  루트까지 꽉 참   → 루트 분할, 트리 높이 +1

삭제 시:
  삭제 후 여유 있음    → 그냥 삭제
  최솟값 미만 발생     →  형제가 여유 있음  → 재분배(Redistribute)
                           형제도 최솟값    → 병합(Merge), 높이 -1 가능

모든 경우에 리프 노드 깊이는 동일 → 항상 균형 유지
CH 11

핵심 요약

전체 흐름 한눈에

  • DB는 디스크를 쓰므로 접근 횟수 최소화가 핵심이다
  • BST는 노드당 키 1개 → 깊이 크고 디스크 접근 많음
  • B 트리는 노드당 키 수백 개 → 트리 납작 → 접근 줄어듦
  • B+ 트리는 내부 노드에 키만 저장해 더 많은 키를 담는다
  • 리프 노드만 실제 데이터 주소를 가지며 연결 리스트로 연결된다
  • 세컨더리 인덱스 = 해당 컬럼 전용 B+ 트리를 별도로 생성
  • 세컨더리 인덱스는 PK를 얻은 뒤 클러스터드 인덱스를 다시 탐색한다
  • 인덱스는 조회 성능을 높이지만 쓰기 성능을 낮추므로 신중히 건다
항목B 트리B+ 트리
내부 노드 저장키 + 데이터 위치키만
리프 노드 저장키 + 데이터 위치키 + 데이터 위치
리프 연결없음연결 리스트
범위 검색느림빠름
실제 DB 사용거의 없음MySQL, PostgreSQL 등

내부 노드는 키와 자식 노드 주소(①)만 저장한다. 실제 row 데이터 위치(②)는 리프 노드에만 있다.
Q2. 세컨더리 인덱스(name 인덱스)의 리프 노드에 저장되는 것은?
A
name 값 + 실제 row 전체
B
name 값만
C
name 값 + PK
D
PK만
세컨더리 인덱스 리프에는 인덱스 컬럼 값(name)과 PK가 저장된다. 실제 row는 없고, PK로 클러스터드 인덱스를 다시 탐색해야 한다.
Q3. 다음 중 B+ 트리가 B 트리보다 유리한 이유로 옳은 것은?
A
내부 노드가 가벼워 같은 공간에 키를 더 많이 담을 수 있다
B
모든 노드에 데이터가 있어 탐색이 빠르다
C
트리 높이가 항상 1이다
D
리프 노드가 없다
B+ 트리 내부 노드는 키만 저장해 가볍다. 같은 노드 크기(= 디스크 블록)에 더 많은 키를 담을 수 있어 트리가 더 납작해지고 디스크 접근이 줄어든다.
