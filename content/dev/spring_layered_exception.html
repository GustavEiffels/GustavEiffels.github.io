Infrastructure vs Domain Service — 예외와 검증, 어디서 처리해야 하는가?

1

레이어드 아키텍처 구조

DDD 기반 레이어드 아키텍처에서 각 레이어의 역할과 의존 방향은 다음과 같다.

Layered Architecture — 의존 방향 
Application Layer   ← UseCase 오케스트레이션
        ↓
Domain Layer        ← DomainService, Repository Interface, Entity
        ↓
Infrastructure      ← RepositoryImpl, JPA, 외부 서비스

의존성은 항상 위 → 아래 방향이며, Infrastructure는 Domain의 Repository 인터페이스를 구현한다.

핵심 질문 JPA Repository를 Infrastructure에서 구현할 때, 예외 처리와 검증을 어느 레이어에서 담당해야 하는가?
2

Option A — Infrastructure에서 처리

Repository 구현체가 null 체크, 중복 검증, 예외 변환을 모두 처리한다.

Option A — Infrastructure가 예외·검증 담당 
// Infrastructure Layer
@Repository
public class UserRepositoryImpl implements UserRepository {

    @Override
    public User findById(Long id) {
        return jpa.findById(id)
            .orElseThrow(() -> new UserNotFoundException("User not found: " + id)); // ← 예외 여기서
    }

    @Override
    public void save(User user) {
        if (jpa.existsByEmail(user.getEmail())) {
            throw new DuplicateEmailException("이미 존재하는 이메일"); // ← 검증도 여기서
        }
        jpa.save(UserJpaEntity.from(user));
    }
}

// Domain Service — 단순 위임만
public class UserDomainService {

    public void registerUser(User user) {
        userRepository.save(user);          // 깔끔해 보이지만...
    }

    public User getUser(Long id) {
        return userRepository.findById(id);   // Optional 처리 없음
    }
}

장점

Domain Service 코드가 짧고 깔끔해 보임

Repository 호출 시 항상 동일한 예외 보장

Optional을 매번 처리하지 않아도 됨

단점

비즈니스 규칙이 Infrastructure에 스며듦

Infrastructure → Domain 예외 클래스 의존 (역방향)

같은 Repository를 다른 맥락에서 쓸 때 유연성 저하

3

Option B — Domain Service에서 처리

Repository 구현체는 데이터 접근만 담당하고, 비즈니스 의미 있는 판단은 Domain Service가 담당한다.

Option B — Infrastructure는 순수 데이터 접근 
// Infrastructure Layer — 순수 데이터 접근만
@Repository
public class UserRepositoryImpl implements UserRepository {

    @Override
    public Optional<User> findById(Long id) {      // ← Optional 반환
        return jpa.findById(id).map(UserJpaEntity::toDomain);
    }

    @Override
    public boolean existsByEmail(String email) {  // ← 단순 질의만
        return jpa.existsByEmail(email);
    }

    @Override
    public void save(User user) {
        jpa.save(UserJpaEntity.from(user));          // ← 저장만
    }
}

// Domain Service — 비즈니스 규칙 집중
public class UserDomainService {

    public void registerUser(User user) {
        if (userRepository.existsByEmail(user.getEmail())) {
            throw new DuplicateEmailException("이미 존재하는 이메일"); // ← 도메인 규칙
        }
        userRepository.save(user);
    }

    public User getUser(Long id) {
        return userRepository.findById(id)
            .orElseThrow(() -> new UserNotFoundException("User not found: " + id)); // ← 예외도 도메인
    }
}

장점

도메인 규칙이 Domain 레이어에 집중

의존성 방향 정상 유지 (Domain ← Infrastructure)

비즈니스 로직 재사용성 향상

단위 테스트 명확 (Domain Service만 테스트)

단점

Optional 처리로 코드가 약간 verbose

여러 Domain Service에서 비슷한 패턴 반복 가능

4

NULL 체크의 함정

"DB 단에서 NULL 체크는 Infrastructure에서" — 얼핏 합리적으로 보이는 이 분리가 실제로는 문제가 된다.

Infrastructure에서 NULL 체크? 
@Override
public void save(User user) {
    if (user.getEmail() == null) {                // ← 이게 왜 Infrastructure에?
        throw new InvalidUserException("email is required");
    }
    jpa.save(UserJpaEntity.from(user));
}
핵심 질문 email == null이 안 되는 이유가 무엇인가? 그 이유가 어느 레이어에 속하는가?
이유 성격 올바른 위치
DB 컬럼이 NOT NULL이라서 기술적 제약 Infrastructure에서 JPA 예외 wrapping
"이메일 없는 유저는 서비스 정책상 불가" 비즈니스 규칙 Domain Entity 또는 Domain Service
결론 대부분의 NULL 체크는 비즈니스 의미를 가지므로 Infrastructure에 두는 것이 관심사 분리 위반이다.
5

더 나은 위치 — Domain Entity 불변식

NULL 체크나 형식 검증은 Domain Entity 생성자에서 담당하는 것이 가장 자연스럽다. Entity가 자기 불변식(Invariant)을 스스로 지킨다.

Domain Entity — 불변식을 생성자에서 보장 
// Domain Entity — 불변식을 생성자에서 보장
public class User {

    private final String email;
    private final String name;

    public User(String email, String name) {
        if (email == null || email.isBlank()) {
            throw new InvalidUserException("email은 필수입니다");  // ← 가장 자연스러운 위치
        }
        if (name == null || name.isBlank()) {
            throw new InvalidUserException("name은 필수입니다");
        }
        this.email = email;
        this.name  = name;
    }
}

// Infrastructure — 이제 진짜 기술 예외 wrapping만
@Override
public void save(User user) {
    try {
        jpa.save(UserJpaEntity.from(user));
    } catch (DataIntegrityViolationException e) {
        throw new DuplicateEmailException("이미 존재하는 이메일", e); // ← wrapping만
    }
}

// Domain Service — 순수 비즈니스 규칙만
public void registerUser(User user) {
    if (userRepository.existsByEmail(user.getEmail())) {
        throw new DuplicateEmailException("이미 존재하는 이메일");  // ← 비즈니스 선제 검증
    }
    userRepository.save(user);
}
왜 Entity 생성자인가? User 객체가 존재하는 순간 반드시 만족해야 하는 조건 = 불변식. 어디서 생성하든 보장되어야 하므로 생성자가 가장 적절하다.
6

Trade-off 완전 비교

기준 Option A (Infrastructure 처리) Option B (Domain Service 처리)
관심사 분리 위반 인프라가 비즈니스 의미를 앎 준수 도메인 규칙이 Domain에 집중
코드 간결성 Domain Service 코드가 짧아 보임 Optional 처리로 약간 verbose
재사용성 항상 같은 예외 → 맥락별 대응 불가 상황마다 다른 처리 가능
테스트 명확성 Infra 모킹 시 예외까지 함께 설정 명확 Domain / Infra 단위 테스트 분리
의존성 방향 역방향 Infra → Domain 예외 클래스 정방향 정상 유지
7

최종 역할 분담 원칙

어디서 무엇을 처리하는가 
NULL · 형식 검증   →  Domain Entity 생성자   (불변식, 항상 보장)

비즈니스 규칙      →  Domain Service         (이메일 중복, 성인 여부 등)

DB 기술 예외       →  Infrastructure         (JPA 예외 → Domain 예외 wrapping)
핵심 판단 기준 "이 규칙이 비즈니스 의미를 가지는가?" → Yes = Domain / No (기술적 제약) = Infrastructure wrapping
완성된 전체 흐름
3단계 처리 흐름 
// 1. Entity 생성 시점 — NULL·형식 불변식
User user = new User("hong@test.com", "홍길동");  // null이면 여기서 예외

// 2. Domain Service — 비즈니스 규칙
if (userRepository.existsByEmail(user.getEmail())) {
    throw new DuplicateEmailException(...);           // 비즈니스 선제 검증
}
userRepository.save(user);

// 3. Infrastructure — JPA 예외 wrapping (안전망)
try {
    jpa.save(UserJpaEntity.from(user));
} catch (DataIntegrityViolationException e) {
    throw new DuplicateEmailException("DB 레벨 중복 감지", e);  // 안전망
}
Note Domain Service의 existsByEmail 검증 + Infrastructure의 DataIntegrityViolationException wrapping을 함께 사용하는 것이 실무에서 가장 견고한 방식이다. 선제 검증은 명확한 에러 메시지를, DB 제약은 동시성 상황의 안전망을 제공한다.

핵심 요약

  • Infrastructure는 기술적 예외(JPA)를 Domain 예외로 wrapping하는 역할만 담당
  • NULL·형식 검증은 Domain Entity 생성자에서 불변식으로 보장
  • 비즈니스 규칙(이메일 중복, 나이 조건 등)은 Domain Service에서 판단
  • Infrastructure에 비즈니스 조건을 두면 관심사 분리 위반 + 역방향 의존 발생
  • 선제 검증(Domain) + DB 제약(Infrastructure wrapping)을 함께 쓰면 가장 견고한 구조
8

퀴즈 — 직접 확인해보자

Q1. Option B에서 Infrastructure의 역할은?
A 비즈니스 규칙 검증
B 예외 발생 후 도메인 로직 호출
C 순수 데이터 접근 + JPA 예외 wrapping
D NULL 체크와 형식 검증
정답: C
Option B에서 Infrastructure는 순수 데이터 접근(Optional 반환, existsByEmail 질의, save)과 JPA 기술 예외를 Domain 예외로 wrapping하는 역할만 담당한다. 비즈니스 판단은 Domain Service가 한다.
Q2. Option A의 가장 큰 문제점은?
A 코드가 너무 복잡해진다
B 비즈니스 규칙이 Infrastructure에 스며들어 관심사 분리가 깨진다
C 트랜잭션 처리가 어려워진다
D Optional을 반환해야 해서 verbose해진다
정답: B
Option A의 핵심 문제는 비즈니스 의미를 가진 규칙(중복 이메일 불가 등)이 Infrastructure에 위치하여 관심사 분리를 위반하고, Infra → Domain 예외 클래스 방향의 역방향 의존이 생긴다는 점이다.
Q3. Domain Entity 생성자에 검증을 두는 이유로 가장 적절한 것은?
A 어디서 생성하든 불변식이 반드시 보장되어야 하기 때문
B Infrastructure 코드를 줄이기 위해
C @Validated 어노테이션을 사용하기 위해
D Spring이 생성자를 자동으로 검증하기 때문
정답: A
불변식(Invariant)이란 "이 객체가 존재하는 순간 반드시 만족해야 하는 조건"이다. 어디서 User를 생성하든 email이 null이 아님을 보장하려면 생성자에 넣는 것이 가장 자연스럽다.
Q4. DB NOT NULL 제약으로 인한 JPA 예외를 처리하기 가장 올바른 위치는?
A Application Layer (Controller)
B Domain Service
C Domain Entity 생성자
D Infrastructure (RepositoryImpl)
정답: D
DB NOT NULL 제약은 기술적 제약이다. DataIntegrityViolationException 같은 JPA 기술 예외를 Domain 예외로 wrapping하는 것은 Infrastructure의 역할이다. 비즈니스 의미가 없는 기술적 예외 변환만 여기서 담당한다.
Q5. 동시성 환경에서 이메일 중복 등록을 가장 견고하게 막는 방법은?
A Domain Service의 existsByEmail 검증만
B Domain Service 선제 검증 + Infrastructure의 DataIntegrityViolationException wrapping
C Infrastructure의 existsByEmail 검증만
D Entity 생성자에서만 검증
정답: B
선제 검증(Domain Service의 existsByEmail)은 명확한 에러 메시지를 제공하지만, 동시 요청 시 두 스레드가 모두 통과할 수 있다. DB 유니크 제약 + Infrastructure wrapping이 최후 안전망이 된다. 둘을 함께 쓰는 것이 가장 견고하다.
