2026-05-19 Spring Bean CGLIB Proxy

Spring Bean vs Proxy Bean

@Service · @Component · @Bean 으로 등록된 모든 빈이 CGLIB 프록시인 줄 알았다. 실제로는 특정 조건을 가진 빈만 프록시로 교체된다. Application 초기화 과정에서 무엇이 그 차이를 만드는지 정리한다.

핵심 정리

  • 일반 @Service · @Component 빈은 순수 객체(POJO) 그대로 컨테이너에 저장된다
  • @Transactional · @Aspect 등 AOP 적용 대상만 CGLIB 프록시로 교체된다
  • 교체 시점은 Bean 생성 직후 BeanPostProcessor 단계다
  • 프록시 여부는 런타임에 AopUtils.isAopProxy(bean) 또는 bean.getClass()로 확인할 수 있다
1

흔한 오해 — "모든 Bean은 프록시다"

오해 Spring Container에 등록된 Bean은 전부 CGLIB이 감싼 프록시 객체다.

이 오해가 생기는 이유는 @Configuration 클래스 동작 방식 때문이다. @Configuration이 붙은 클래스는 클래스 자체가 CGLIB 프록시로 교체된다. 그 안의 @Bean 메서드를 여러 번 호출해도 같은 인스턴스를 반환하도록 가로채기 위해서다. 하지만 @Bean 메서드가 반환하는 객체는 별개다. 해당 객체에 AOP 대상 어노테이션이 없으면 순수 객체 그대로 등록된다.

프록시가 되는 것

@Configuration 클래스 자체

@Transactional이 붙은 클래스 / 메서드를 가진 빈

@Aspect의 Pointcut에 매칭되는 빈

Spring Security — 메서드 시큐리티(@PreAuthorize) 대상 빈

@Async가 붙은 빈

@Cacheable / @CacheEvict 등 캐시 대상 빈

순수 객체(POJO)로 남는 것

@Service · @Component · @Repository 단독 선언

위 어노테이션이 없는 일반 @Bean 반환 객체

DTO · Entity · Value Object

AOP Pointcut에 매칭되지 않는 모든 빈

2

Application 초기화 — Bean이 만들어지는 순서

Spring Container가 Bean을 생성하고 등록하는 흐름은 아래와 같다. 프록시 교체는 4단계 BeanPostProcessor에서 발생한다.

STEP 1

BeanDefinition 등록

@ComponentScan이 클래스패스를 스캔하고, @Bean 메서드를 파싱해 Bean의 설계도(BeanDefinition) 를 메타데이터로 등록한다. 아직 객체는 생성되지 않는다.

STEP 1 — BeanDefinition 내부 동작 (의사 코드) 
// @Service, @Component가 붙은 클래스를 스캔
@Service
public class OrderService { ... }      // 대상 발견

@Service
public class UserQueryService { ... }  // 대상 발견

// 클래스패스 스캔 결과 → BeanDefinition 메타데이터로 변환 후 registry에 저장
// 이 시점에는 new OrderService() 호출이 일어나지 않는다
BeanDefinition bd = new RootBeanDefinition(OrderService.class);
bd.setScope("singleton");
registry.registerBeanDefinition("orderService", bd); // 설계도만 등록
STEP 2

BeanPostProcessor 자체 등록

AutowiredAnnotationBeanPostProcessor, AnnotationAwareAspectJAutoProxyCreator 등 특수 후처리기들이 일반 Bean보다 먼저 인스턴스화되어 컨테이너에 등록된다.

STEP 2 — BeanPostProcessor 우선 등록 
// Spring Boot AutoConfiguration 또는 @EnableAspectJAutoProxy가 자동 등록
// 일반 Bean 생성 전에 아래 후처리기들이 먼저 인스턴스화된다

AutowiredAnnotationBeanPostProcessor     // @Autowired 의존성 주입 담당
CommonAnnotationBeanPostProcessor        // @PostConstruct, @PreDestroy 담당
AnnotationAwareAspectJAutoProxyCreator   // ← 프록시 생성 담당 (핵심)

// AnnotationAwareAspectJAutoProxyCreator는 이 시점에
// @Aspect 클래스를 읽어 Advisor 목록을 미리 구성해둔다
STEP 3

일반 Bean 인스턴스 생성 + 의존성 주입

컨테이너가 BeanDefinition을 보고 생성자 또는 팩토리 메서드를 호출해 순수 객체(POJO) 를 만든다. 이후 @Autowired 등으로 의존성이 주입된다.

STEP 3 — AbstractAutowireCapableBeanFactory 내부 동작 (의사 코드) 
// 3-A. 생성자 호출 → 순수 POJO 생성
OrderService rawBean = new OrderService();
// rawBean.getClass() → class com.example.OrderService  (아직 프록시 아님)

// 3-B. 의존성 주입 (@Autowired, 생성자 주입 등)
OrderRepository repo = ctx.getBean(OrderRepository.class);
rawBean.setOrderRepository(repo);

// 3-C. 초기화 콜백
rawBean.init();  // @PostConstruct 또는 afterPropertiesSet()

// → 이 시점까지 rawBean은 여전히 순수 POJO
// → 다음 STEP 4에서 프록시 교체 여부가 결정된다
STEP 4 — 프록시 교체 발생 지점

BeanPostProcessor.postProcessAfterInitialization()

Bean 초기화(@PostConstruct, afterPropertiesSet()) 완료 후 등록된 모든 BeanPostProcessor가 순차 실행된다. AnnotationAwareAspectJAutoProxyCreator는 이 시점에 각 Bean이 AOP 대상인지 판단하고, 해당하면 CGLIB 서브클래스 프록시로 교체한다. 컨테이너는 원본 객체 대신 프록시 객체를 최종 등록한다.

STEP 4 — AnnotationAwareAspectJAutoProxyCreator 내부 동작 (의사 코드) 
public Object postProcessAfterInitialization(Object bean, String beanName) {

    // STEP 2에서 구성해둔 Advisor 목록을 순회하며 Pointcut 매칭 검사
    List<Advisor> eligibleAdvisors = findEligibleAdvisors(bean.getClass());

    if (eligibleAdvisors.isEmpty()) {
        return bean; // 매칭 없음 → POJO 그대로 반환 (UserQueryService 등)
    }

    // 매칭 있음 → CGLIB이 원본 클래스를 상속한 서브클래스 생성
    Object proxy = createCglibProxy(bean, eligibleAdvisors);
    // proxy.getClass() → class com.example.OrderService$$SpringCGLIB$$0
    // proxy 내부의 target 필드 → 원본 rawBean (OrderService)

    return proxy; // 컨테이너는 이 proxy를 최종 Bean으로 저장
}
STEP 5

ApplicationContext 준비 완료

컨테이너에는 일반 빈은 POJO로, AOP 대상 빈은 프록시로 저장된 상태가 된다. 이후 getBean() 또는 @Autowired로 조회하면 최종 등록된 객체가 반환된다.

STEP 5 — ApplicationContext 최종 상태 확인 
// @Transactional 있는 Bean → 프록시로 저장됨
ctx.getBean("orderService").getClass().getName();
// → com.example.OrderService$$SpringCGLIB$$0

// 어노테이션 없는 Bean → POJO 그대로 저장됨
ctx.getBean("userQueryService").getClass().getName();
// → com.example.UserQueryService

// 메서드 호출 흐름 비교
orderService.placeOrder(dto);
// → CGLIB 프록시가 가로챔 → TransactionInterceptor 실행 → 원본 메서드 위임

userQueryService.findById(id);
// → 직접 실행 (가로채는 레이어 없음)
3

프록시가 생성되는 조건 — Advisor Matching

AnnotationAwareAspectJAutoProxyCreator는 모든 Bean에 대해 등록된 Advisor 목록을 순회한다. Advisor의 Pointcut이 해당 Bean의 클래스 또는 메서드에 매칭되면 프록시를 생성한다.

대표 Advisor와 Pointcut 매칭 조건
어노테이션 Advisor Pointcut 매칭 조건 프록시 타입
@Transactional BeanFactoryTransactionAttributeSourceAdvisor 클래스/메서드에 @Transactional이 존재 CGLIB (기본), JDK Dynamic (인터페이스 있을 때 설정 가능)
@Aspect 사용자 정의 Advisor (AspectJ 표현식) @Pointcut 표현식에 매칭되는 클래스/메서드 CGLIB 또는 JDK Dynamic
@Async AsyncAnnotationAdvisor 클래스/메서드에 @Async가 존재 CGLIB
@PreAuthorize 등 MethodSecurityInterceptor Advisor Spring Security 메서드 시큐리티 어노테이션 존재 CGLIB
@Cacheable BeanFactoryCacheOperationSourceAdvisor 클래스/메서드에 캐시 어노테이션이 존재 CGLIB
(없음) 매칭 없음 어떤 Advisor의 Pointcut에도 매칭되지 않음 프록시 없음 — POJO 그대로
결론 매칭 여부 판단은 Advisor → Pointcut → 클래스/메서드 순으로 진행된다. 하나라도 매칭되면 프록시가 생성되고, 모두 미매칭이면 원본 POJO가 그대로 등록된다.
4

런타임에서 프록시 여부 확인하기

아래 코드를 작성하면 각 Bean이 실제로 프록시인지 직접 출력해볼 수 있다.

방법 1 — getClass() 출력
ProxyCheckRunner.java 
@Component
public class ProxyCheckRunner implements ApplicationRunner {

    @Autowired private OrderService      orderService;   // @Transactional 있음
    @Autowired private UserQueryService  userQueryService; // 어노테이션 없음

    @Override
    public void run(ApplicationArguments args) {
        // CGLIB 프록시면 클래스명에 "$$SpringCGLIB$$" 또는 "$$EnhancerBySpringCGLIB$$" 포함
        System.out.println(orderService.getClass().getName());
        // → com.example.OrderService$$SpringCGLIB$$0

        System.out.println(userQueryService.getClass().getName());
        // → com.example.UserQueryService  (POJO 그대로)
    }
}
방법 2 — AopUtils 사용 (권장)
AopUtils API 
import org.springframework.aop.support.AopUtils;

AopUtils.isAopProxy(bean);       // JDK Dynamic + CGLIB 모두 true
AopUtils.isCglibProxy(bean);     // CGLIB 프록시일 때만 true
AopUtils.isJdkDynamicProxy(bean); // JDK Dynamic Proxy일 때만 true
방법 3 — ApplicationContext 전체 Bean 목록 순회
ProxyInspector.java 
@Component
public class ProxyInspector implements ApplicationRunner {

    @Autowired
    private ApplicationContext ctx;

    @Override
    public void run(ApplicationArguments args) {
        for (String name : ctx.getBeanDefinitionNames()) {
            Object bean = ctx.getBean(name);
            if (AopUtils.isAopProxy(bean)) {
                System.out.printf("[PROXY] %s → %s%n", name, bean.getClass().getSimpleName());
            }
        }
    }
}
실행 결과 예시 [PROXY] orderService → OrderService$$SpringCGLIB$$0 [PROXY] paymentService → PaymentService$$SpringCGLIB$$0 (userQueryService, productService 등은 출력되지 않음 — POJO)
5

@Configuration 클래스 — 항상 프록시인 이유

@Configuration은 AOP Pointcut 매칭과 관계없이 항상 CGLIB 프록시가 된다. 이유는 @Bean 메서드 간 싱글톤 보장 때문이다.

@Configuration 없이 @Bean만 사용하면?

AppConfig 클래스가 POJO 그대로 등록된다. dataSource()를 여러 Bean이 호출하면 매번 새 객체가 생성된다. 싱글톤 보장이 깨진다.

@Configuration 있으면?

CGLIB이 AppConfig를 상속한 서브클래스를 만들어 @Bean 메서드를 오버라이드한다. 이미 컨테이너에 등록된 Bean이면 새로 생성하지 않고 컨테이너에서 꺼내 반환한다. 싱글톤이 보장된다.

AppConfig.java — @Configuration의 싱글톤 보장 
@Configuration
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        return new HikariDataSource();
    }

    @Bean
    public TransactionManager txManager() {
        // dataSource()를 직접 호출하지만, CGLIB이 가로채서 컨테이너의 싱글톤을 반환
        return new DataSourceTransactionManager(dataSource());
    }
}
주의 — proxyBeanMethods = false @Configuration(proxyBeanMethods = false) 로 설정하면 CGLIB 프록시가 생성되지 않는다. @Bean 메서드 간 싱글톤 보장이 사라지므로, 메서드 간 의존 관계가 없을 때만 사용한다.
6

POJO Bean vs Proxy Bean — 내부 구조

POJO Bean

클래스: UserQueryService

부모: Object

메서드 호출: 직접 실행

Interceptor 체인: 없음

원본 객체: 자기 자신

CGLIB Proxy Bean

클래스: OrderService$$SpringCGLIB$$0

부모: OrderService (상속)

메서드 호출: Interceptor 체인 → 원본 위임

Interceptor 체인: TransactionInterceptor 등

원본 객체: 내부 target 필드에 보관

JDK Dynamic Proxy Bean

클래스: $Proxy42

부모: Proxy (인터페이스 구현)

메서드 호출: InvocationHandler → 원본 위임

조건: 인터페이스 존재 + 설정 필요

원본 객체: InvocationHandler 내부에 보관

CGLIB vs JDK Dynamic — Spring Boot 기본값 Spring Boot 2.x 이후 기본은 CGLIB이다. 인터페이스가 있어도 CGLIB을 사용한다. JDK Dynamic Proxy로 바꾸려면 spring.aop.proxy-target-class=false를 설정해야 한다. CGLIB은 클래스 상속 방식이므로 final 클래스나 final 메서드에는 적용할 수 없다.
7

한 줄 요약 — 무엇이 차이를 만드는가

핵심 BeanPostProcessor가 각 Bean을 검사해 등록된 Advisor의 Pointcut에 매칭되는지 확인한다. 매칭되면 CGLIB 서브클래스 프록시로 교체해 컨테이너에 저장하고, 매칭되지 않으면 POJO 그대로 저장한다. 결국 @Transactional · @Aspect · @Async 등 AOP Advice가 필요한 빈만 프록시가 된다.
질문 답변
모든 Spring Bean이 프록시인가? No — AOP 대상이 아닌 Bean은 POJO 그대로 등록된다
프록시 교체는 언제 일어나는가? Bean 초기화 완료 직후 BeanPostProcessor.postProcessAfterInitialization()
무엇이 매칭 여부를 판단하는가? AnnotationAwareAspectJAutoProxyCreator가 Advisor 목록을 순회해 Pointcut 매칭 검사
@Configuration은 왜 항상 프록시인가? @Bean 메서드 간 싱글톤 보장을 위해 CGLIB이 메서드 호출을 가로채야 하기 때문
런타임에 확인하는 방법은? AopUtils.isAopProxy(bean) 또는 bean.getClass().getName()에서 $$SpringCGLIB$$ 확인

퀴즈 — 직접 확인해보자

Q1. 다음 중 Spring Container 초기화 시 CGLIB 프록시로 저장되는 Bean은?
A @Service만 붙은 UserQueryService
B @Transactional 메서드를 가진 OrderService
C @Repository만 붙은 UserRepository
D @Component만 붙은 EventPublisher
정답: B
@Transactional은 BeanFactoryTransactionAttributeSourceAdvisor의 Pointcut에 매칭되므로 AnnotationAwareAspectJAutoProxyCreator가 CGLIB 프록시로 교체한다. A · C · D는 AOP Advisor Pointcut에 매칭되는 어노테이션이 없으므로 POJO 그대로 등록된다.
Q2. Bean이 프록시로 교체되는 정확한 시점은?
A BeanDefinition이 registry에 등록된 직후
B @Autowired 의존성 주입이 완료된 직후
C @PostConstruct 실행 후 BeanPostProcessor.postProcessAfterInitialization()
D ApplicationContext.refresh()가 시작되기 직전
정답: C
프록시 교체는 Bean 초기화(@PostConstruct, afterPropertiesSet()) 완료 이후 BeanPostProcessor.postProcessAfterInitialization() 단계에서 일어난다. 이 시점까지 Bean은 순수 POJO이며, 이 메서드가 프록시를 반환하면 컨테이너가 원본 대신 프록시를 최종 등록한다.
Q3. AnnotationAwareAspectJAutoProxyCreator가 프록시 생성 여부를 결정하는 기준은?
A Bean 클래스 이름에 "Service" · "Repository" 키워드가 포함되는지
B 등록된 Advisor의 Pointcut이 해당 Bean의 클래스 또는 메서드에 매칭되는지
C Bean이 인터페이스를 구현하는지 여부
D @Autowired 필드의 개수가 일정 수 이상인지
정답: B
Advisor → Pointcut → 클래스/메서드 순으로 매칭을 검사한다. 하나라도 매칭되면 프록시가 생성되고, 모두 미매칭이면 POJO 그대로 반환된다. 인터페이스 구현 여부(C)는 JDK Dynamic Proxy vs CGLIB 선택에 관여하지만, 프록시 생성 자체를 결정하지는 않는다.
Q4. 아래 코드의 출력 결과는? (UserQueryService에는 @Transactional, @Async, @Cacheable 등 AOP 어노테이션이 전혀 없다)
Quiz Q4 
ctx.getBean("userQueryService").getClass().getName();
A com.example.UserQueryService$$SpringCGLIB$$0
B com.example.$Proxy42
C com.example.UserQueryService
D java.lang.Object
정답: C
AOP Advisor Pointcut에 매칭되는 어노테이션이 없으므로 postProcessAfterInitialization()가 원본 POJO를 그대로 반환한다. 결과적으로 컨테이너에 UserQueryService 인스턴스 자체가 저장되며 클래스명에 $$SpringCGLIB$$가 붙지 않는다. A는 CGLIB 프록시, B는 JDK Dynamic Proxy의 클래스명 패턴이다.
Q5. @Configuration(proxyBeanMethods = false)로 설정했을 때 발생하는 문제는?
A @Bean 메서드 자체가 실행되지 않아 Bean이 등록되지 않는다
B CGLIB 프록시가 생성되지 않아 @Bean 메서드 간 직접 호출 시 매번 새 객체가 생성될 수 있다
C JDK Dynamic Proxy로 자동 전환되어 인터페이스 없는 Bean이 등록 실패한다

proxyBeanMethods = false로 설정하면 @Configuration 클래스가 CGLIB 프록시가 되지 않는다. 따라서 dataSource() 같은 @Bean 메서드를 다른 @Bean 메서드 내에서 직접 호출하면 컨테이너의 싱글톤 Bean을 반환하는 것이 아니라 new DataSource()를 새로 실행해 버린다. @Bean 메서드 간 의존 관계가 없을 때만 안전하게 사용할 수 있다.
