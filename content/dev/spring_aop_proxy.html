횡단 관심사부터 CGLIB 내부 동작까지 — 읽고 나면 직접 설명할 수 있다

1

횡단 관심사란 무엇인가

코드를 작성하다 보면, 비즈니스 로직과는 직접적인 관련이 없지만 시스템 전반에 반복적으로 등장하는 코드들이 있다. 이를 횡단 관심사 (Cross-cutting Concern) 라고 한다.

이름 그대로다 — 코드를 수평으로 잘라서 들여다보면, 동일한 코드가 여러 계층을 가로질러 반복되고 있기 때문이다.

Cross-cutting Concern Diagram 
Controller  ─────────────────────────────────────────
  [로깅]  [트랜잭션]  [보안체크]  비즈니스로직  [로깅]
Service     ─────────────────────────────────────────
  [로깅]  [트랜잭션]  [보안체크]  비즈니스로직  [로깅]
Repository  ─────────────────────────────────────────
  [로깅]  [트랜잭션]  [보안체크]  비즈니스로직  [로깅]
         ↑ 이 부분들이 횡단으로 동일하게 반복된다
횡단 관심사 예시 설명
트랜잭션 DB 작업의 원자성 보장 — 모든 Service 메서드에 반복
로깅 메서드 호출 기록 — 계층 전체에 반복
보안 체크 권한 확인 — 모든 API 진입점에 반복
캐싱 결과 캐시 — 조회 메서드 전반에 반복
핵심 횡단 관심사는 비즈니스 로직이 아니다. 하지만 없애면 시스템이 망가진다. "필요하지만 비즈니스와 무관한 것" — 이게 횡단 관심사의 정의다.
2

AOP를 쓰는 이유

횡단 관심사를 매 메서드마다 직접 작성하면 어떻게 되는가.

AOP 없이 직접 작성하는 경우 
// AOP 없이 직접 작성하는 경우
public void updateWorkflow(WorkflowDto dto) {

    // ▼ 비즈니스와 무관한 인프라 코드들
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);
    log.info("updateWorkflow 시작");
    if (!hasPermission()) throw new UnauthorizedException();

    // ▼ 진짜 비즈니스 로직 (이것만 있어야 하는데)
    workflowMapper.update(dto);

    // ▼ 또 인프라 코드
    conn.commit();
    log.info("updateWorkflow 완료");
}
문제점 메서드가 100개면 이 코드를 100번 반복해야 한다. 비즈니스 로직을 보려면 인프라 코드를 뚫고 지나가야 한다. 하나를 바꾸면 100곳을 다 바꿔야 한다.

AOP (Aspect-Oriented Programming)는 이 문제를 해결한다. 공통 기능을 한 곳에 정의하고, 조건에 맞는 메서드에 자동으로 적용한다.

AOP 사용 후 
// AOP 사용 후 — 비즈니스 로직만 남는다
@Transactional
public void updateWorkflow(WorkflowDto dto) {
    workflowMapper.update(dto);  // 이것만
}
결과 비즈니스 로직과 공통 기능이 완전히 분리된다. 개발자는 비즈니스에만 집중할 수 있다. 공통 기능을 바꿀 때 한 곳만 수정하면 된다.

AOP의 핵심 용어 4가지:

용어 의미 비유
Aspect 공통 기능 묶음 트랜잭션 처리 전체
Advice 실제 실행 코드 Before / After / Around
Pointcut "어디에" 적용할지 조건 execution(* com.sbt..*Service.*(..))
JoinPoint 끼워 넣을 수 있는 지점 메서드 호출 순간

Spring Boot의 AOP — Proxy 객체

Spring Boot에서 AOP를 구현하는 수단이 바로 Proxy 패턴이다.

@Autowired 로 주입받은 Service 객체를 실제로 출력해보면 놀라운 것을 볼 수 있다.

Proxy 객체 확인 
@Autowired
WorkflowService workflowService;

System.out.println(workflowService.getClass().getName());
// 출력: com.example.workflow.WorkflowService$$EnhancerByCGLIB$$abc123
//                                          ↑ 진짜 Service가 아니다!

$$EnhancerByCGLIB — 이게 보이면 Spring이 만든 Proxy 객체다. 내가 @Autowired 로 받는 것은 처음부터 Proxy다.

Spring ApplicationContext (Bean Container) 
"workflowService"   →  [WorkflowService$$CGLIB@1a2b3c]  ← Proxy만 등록됨
                            └── target: [진짜 WorkflowService]  ← Bean 아님, 내부에 숨어있음

"taskService"        →  [TaskService$$CGLIB@4d5e6f]
"workflowController" →  [WorkflowController$$CGLIB@7g8h9i]
중요 — Container에는 Proxy 하나만 저장된다 진짜 Service 객체는 Bean으로 등록되지 않는다. Proxy 내부에 target 필드로 품고 있을 뿐이다.

또한 Proxy는 서버 시작 시 딱 한 번 만들어지고 이후 API 호출에서 재사용된다. Bean의 기본 Scope가 Singleton이기 때문이다.

Scope Proxy 생성 시점 생성 횟수
singleton (기본) 컨테이너 시작 시 1번
prototype 주입/요청 시마다 매번
request HTTP 요청마다 요청당 1번

AOP의 구조 — CGLIB & Reflection

CGLIB(Code Generation Library)은 진짜 클래스를 상속한 자식 클래스를 바이트코드로 런타임에 생성한다. 이 자식 클래스가 바로 Proxy 객체다.

CGLIB Proxy 생성 개념 
// 원본 클래스
@Service
public class WorkflowService {
    public void getWorkflow() {
        System.out.println("비즈니스 로직");
    }
}

// CGLIB이 런타임에 자동 생성하는 Proxy (개념적 표현)
public class WorkflowService$$CGLIB extends WorkflowService {

    private Object target;              // ① 진짜 WorkflowService 객체
    private List<Interceptor> chain;    // ② Aspect 들 (트랜잭션, 로깅 ...)

    @Override
    public void getWorkflow() {          // ③ 메서드를 Override로 가로챔

        ReflectiveMethodInvocation inv =
            new ReflectiveMethodInvocation(target, method, args, chain);

        inv.proceed();                     // ④ Chain 실행 시작
    }
}

Chain의 실행을 관리하는 ReflectiveMethodInvocation의 내부 동작은 다음과 같다.

ReflectiveMethodInvocation 내부 (단순화) 
class ReflectiveMethodInvocation {

    Object              target;   // 진짜 WorkflowService
    Method              method;   // getWorkflow
    Object[]            args;
    List<Interceptor>   chain;    // [TransactionInterceptor, LoggingInterceptor]
    int                 index = 0;

    public Object proceed() throws Throwable {

        if (index == chain.size()) {
            // Chain 끝 → Reflection으로 진짜 메서드 직접 호출
            return method.invoke(target, args);
        }

        // 다음 Interceptor에게 넘김 (자기 자신을 전달해 proceed() 재호출 가능하게)
        Interceptor next = chain.get(index++);
        return next.invoke(this);
    }
}
Reflection이란? Java에서 클래스·메서드 정보를 런타임에 다루는 기능이다. method.invoke(target, args) 한 줄로 어떤 객체의 어떤 메서드든 동적으로 호출할 수 있다. Proxy가 "진짜 객체를 호출"하는 실제 수단이다.

각 Advice 타입과 실행 위치:

Advice 실행 순서 
   메서드 호출
        ↓
① @Before       ← 메서드 실행 전
        ↓
② 실제 메서드 실행
    ↓ (정상)                  ↓ (예외)
③ @AfterReturning    ③ @AfterThrowing
        ↓                         ↓
④ @After        ← 무조건 실행 (finally와 동일)

────────────────────────────────────────
@Around = 위 전체를 하나로 감싸는 가장 강력한 Advice
           proceed() 호출 전 = Before 구간
           proceed() 호출 후 = After 구간

전체 실행 흐름

Controller에서 Service 메서드를 호출하는 순간부터 끝까지.

① Spring 시작 — Proxy 생성

BeanPostProcessor가 @Transactional 등 감지 → CGLIB이 Proxy 클래스 생성 → Proxy를 Bean으로 등록. 진짜 객체는 Proxy.target으로 숨어들어감.

② @Autowired — Proxy 주입

Controller에 주입되는 것은 이미 Proxy 객체다. 개발자는 모르는 채로 Proxy를 받는다.

③ Controller → workflowService.getWorkflow() 호출

실제로는 Proxy.getWorkflow() 가 호출된다. Proxy가 @Override로 가로챈다.

④ ReflectiveMethodInvocation 생성 → Chain 실행

Interceptor 목록을 순서대로 실행. 각 Interceptor는 proceed()를 호출해 다음으로 넘긴다. 재귀 구조.

⑤ Chain 소진 → method.invoke(target) — 진짜 메서드 실행

Reflection으로 진짜 WorkflowService.getWorkflow()를 직접 호출한다.

⑥ 역순으로 반환 — After 처리

진짜 메서드 완료 후 Interceptor들이 역순으로 After 처리(커밋/롤백 등). 양파 껍질 구조로 들어갔다 나온다.

⑦ Controller로 결과 반환

모든 처리 완료. Controller는 Proxy가 있었는지조차 모른다.

여러 Aspect — 재귀 콜스택 구조 
// 여러 Aspect가 있을 때 — 재귀 콜스택 구조

LoggingAspect.around() 진입
    → proceed()
        TransactionAspect.around() 진입    // 트랜잭션 시작
            → proceed()
                CacheAspect.around() 진입
                    → proceed()
                        진짜 getWorkflow() 실행  // ← 가장 안쪽
                    ← 반환
                CacheAspect After
            ← 반환
        TransactionAspect After               // 커밋 or 롤백
    ← 반환
LoggingAspect After

// 들어갈 때 순서대로, 나올 때 역순
자기 호출(Self-invocation) 주의 같은 클래스 내에서 this.method() 로 호출하면 Proxy를 거치지 않아 AOP가 적용되지 않는다. Controller → Service 처럼 다른 Bean을 거쳐야 Proxy가 끼어들 수 있다.

핵심 정리

  • 횡단 관심사 = 비즈니스와 무관하지만 시스템 전반에 반복되는 코드 (트랜잭션, 로깅, 보안)
  • AOP = 횡단 관심사를 한 곳에 정의하고 자동 적용 → 비즈니스 코드를 깨끗하게 유지
  • Spring Bean = 기본적으로 Proxy 객체로 등록됨 (CGLIB이 상속으로 생성)
  • Proxy = 원본 객체를 target으로 품고, 메서드 Override로 호출을 가로챔
  • Chain = proceed() 재귀 호출로 Interceptor를 순서대로 통과
  • 최종 호출 = method.invoke(target) — Reflection으로 진짜 메서드 실행
  • Proxy는 서버 시작 시 1번 생성, Singleton으로 재사용됨

퀴즈 — 직접 확인해보자

Q1. 횡단 관심사가 아닌 것은?
A 메서드 실행 시간 로깅
B 주문 금액 계산 로직
C DB 트랜잭션 관리
D 사용자 권한 체크
정답: B
주문 금액 계산은 명확한 비즈니스 로직이다. 나머지(로깅, 트랜잭션, 권한 체크)는 비즈니스와 무관하게 시스템 전반에 반복되는 횡단 관심사다.
Q2. Spring Container에 등록되는 것은?
A 진짜 Service 객체만
B 진짜 Service 객체 + Proxy 객체 둘 다
C Proxy 객체만 (진짜 객체는 Proxy 내부에)
D 클래스 설계도(Class 파일)
정답: C
Container에는 Proxy 객체 하나만 등록된다. 진짜 객체는 Proxy의 target 필드로 숨어있고, Bean으로는 등록되지 않는다.
Q3. CGLIB이 Proxy를 만드는 방식은?
A 원본 클래스의 소스코드를 직접 수정
B 원본 클래스와 동일한 인터페이스를 구현
C 원본 클래스 내부에 Advice 코드를 삽입
D 원본 클래스를 상속한 자식 클래스를 바이트코드로 생성
정답: D
CGLIB은 런타임에 원본 클래스를 상속한 자식 클래스를 바이트코드로 만든다. 그래서 final 클래스나 final 메서드에는 적용이 불가하다(상속/Override 불가이므로).
Q4. Chain의 마지막에서 진짜 메서드를 호출하는 수단은?
A 직접 new 로 객체를 생성해서 호출
B Java Reflection — method.invoke(target, args)
C Spring Context에서 Bean을 다시 꺼내서 호출
D target을 캐스팅해서 직접 메서드 호출
정답: B
ReflectiveMethodInvocation은 Chain이 소진되면 method.invoke(target, args)로 진짜 메서드를 실행한다. Reflection을 쓰기 때문에 메서드 이름을 문자열로 다룰 수 있고, 동적으로 어떤 메서드든 호출 가능하다.
Q5. 다음 코드에서 AOP가 적용되지 않는 것은?
OrderService.java 
@Service
public class OrderService {

    @Transactional
    public void placeOrder() {
        this.sendEmail();  // (A)
    }

    @Transactional
    public void sendEmail() { ... }
}

// Controller에서 호출:
orderService.placeOrder();   // (B)
orderService.sendEmail();    // (C)
A (A) — placeOrder() 내부에서 this.sendEmail() 호출
B (B) — Controller에서 placeOrder() 호출
C (C) — Controller에서 sendEmail() 호출
D 모두 적용됨
정답: A
this.sendEmail()은 자기 호출(Self-invocation)이다. this는 Proxy가 아닌 진짜 객체를 가리키기 때문에 Proxy를 우회한다. 결과적으로 sendEmail()의 @Transactional이 적용되지 않는다. (B), (C)는 Controller → Proxy → 진짜 객체 경로를 거치므로 정상 적용된다.
