Chapter 1

SSE 연결의 시작 — 일반 HTTP 요청과 100% 동일

SSE(EventSource)는 최초 연결 단계에서 일반 HTTP 요청과 다른 점이 전혀 없다. 클라이언트는 GET /api/sse를 딱 1번 보낼 뿐, 그 뒤로 이 URL을 다시 호출하지 않는다. 

클라이언트 GET /api/sse (딱 1번)
    |
TCP 3-way handshake -> Acceptor accept() -> Poller 등록 큐 -> Poller register()
    |
(idle) 실제 요청 바이트 도착 -> Poller가 readable 감지 -> Worker 작업 큐에 알림
    |
Worker가 take() -> socket.read() -> HTTP 파싱 -> 컨트롤러 진입

여기까지는 Tomcat 커넥터 스레드 모델(Acceptor/Poller/Worker)의 NIO Step 1~10과 완전히 같다.

차이는 딱 하나 응답 헤더가 Content-Type: text/event-stream이고, 이 응답의 몸통(body)이 논리적으로 "끝나지 않는다"는 것뿐이다. 그 의미는 Chapter 3에서 다룬다.
Chapter 2

나이브(Blocking) vs Async — 여기서 갈라진다

노드 Worker — Tomcat 소유, maxThreads로 제한 별도 스레드 — application이 직접 관리, 개수 자유 
@RestController
public class SseController {

    @GetMapping(value = "/api/sse", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public void stream(HttpServletResponse response) throws IOException {
        PrintWriter writer = response.getWriter();

        while (연결이_살아있는_동안) {
            String event = eventQueue.take();   // 여기서 블로킹
            writer.write("data: " + event + "\n\n");
            writer.flush();
        }
    }
}
1
Worker#1 컨트롤러 진입, while문 시작 메서드가 리턴 안 함

startAsync()를 호출한 적이 없으므로, 이 메서드가 실행되는 동안 Worker#1은 이 호출 스택 안에 그대로 갇혀 있다.

2
연결이 끊길 때까지 while 탈출 -> 메서드 리턴 그제서야 반납

클라이언트 200명이 붙으면(maxThreads=200 기준) 그 순간 Worker 풀 전체가 SSE 연결 유지에만 소진된다. 이후 들어오는 모든 일반 HTTP 요청도 대기열에서 굶는다.

C10K 문제의 재발 NIO가 해결했던 "idle 연결이 Worker 하나씩 영구 점유"하던 문제가, SSE 레이어에서 똑같이 재발한다. 
@GetMapping("/sse")
SseEmitter stream() {
    SseEmitter emitter = new SseEmitter(0L);
    emitters.put(userId, emitter);   // application이 직접 관리 (Chapter 7 참고)
    return emitter;                  // 메서드 즉시 리턴
}
1
Worker#1 startAsync() 호출 AsyncContext 생성

Spring이 SseEmitter를 리턴받으면 내부적으로 request.startAsync()를 자동으로 걸어준다. "이 응답 아직 진행 중"이라는 상태가 소켓에 매달려 저장된다.

2
Worker#1 메서드 즉시 리턴 Tomcat 풀로 즉시 반납

Worker#1이 이 연결에 매여 있던 시간은 딱 "요청 진입 ~ startAsync() 호출"까지 — 일반 요청과 다를 바 없이 짧다. 연결 자체는 안 끊긴 채 그대로 열려 있다.

( Worker#1은 이제 이 연결과 완전히 무관 — 다른 요청 처리하러 감. 이 소켓은 emitters 맵에 참조로만 남아있음 )
3
별도 스레드 (Worker 아님) emitters.get(userId).send(이벤트) 클라이언트

시간이 흘러 이벤트가 발생하면, Worker#1이 아니라 그 이벤트를 발생시킨 스레드(스케줄러, 또는 다른 요청을 처리하던 Worker)가 emitters 맵에서 참조를 꺼내 직접 write한다. Acceptor/Poller의 dispatch 경로를 타지 않는다 — 자세한 두 갈래는 Chapter 4 참고.

write 실행 주체: emitter.send()를 호출한 바로 그 스레드 — Worker#1과는 무관
핵심 push를 실행하는 건 Worker#1이 아니다. Worker#1은 이미 반납되어 전혀 다른 요청을 처리하러 갔을 수 있다. 누가 push하는지는 Chapter 4에서 더 자세히 다룬다.
Chapter 3

"응답 body가 안 끝난다" — SocketInfo 상태값과 백그라운드 순찰

TCP는 바이트 스트림일 뿐이라 "메시지가 여기서 끝났다"는 개념이 없다. 그건 HTTP가 Content-Length 또는 Transfer-Encoding: chunked로 정의한다. SSE는 길이를 미리 모르므로 chunked를 쓰는데, 그 종료 마커(0\r\n\r\n)를 서버가 일부러 안 보낸다. Tomcat은 소켓마다 "이 요청 완료됐나?"라는 상태값을 하나 들고 있고 (단순화하면 SocketInfo<Long, Boolean> 정도로 생각해도 된다), 이 값이 완료(true)로 바뀌어야만 그 소켓이 "idle 대기 그룹"에 들어가서 이후 keepAliveTimeout 검사 대상이 된다.

노드 SocketInfo — 소켓마다 Tomcat이 들고 있는 "완료 여부" 상태 백그라운드 순찰 — Worker와 무관하게 주기적으로 도는 타임아웃 체크
1
Poller register() 호출 시점 SocketInfo 생성

소켓이 감시 목록에 등록되는 그 순간, "완료 여부" 상태값도 함께 생성된다.

2
Worker 요청 처리, 응답 작성 클라이언트

Content-Length만큼 다 쓰거나, chunked라면 종료 마커(0\r\n\r\n)까지 전송하고 메서드가 리턴된다.

3
SocketInfo 상태값 -> 완료(true)로 전환 idle 대기 그룹 편입

응답이 완료됐다는 사실이 확정되는 순간, 이 소켓은 "idle 대기 그룹" 목록에 들어간다.

( idle 구간 — Worker의 write와는 완전히 무관하게, 별도로 도는 백그라운드 순찰이 계속 주기적으로 실행 중 )
4
백그라운드 순찰 idle 그룹 훑으며 확인 keepAliveTimeout 초과?

순찰이 이 소켓의 마지막 활동 시각과 현재 시각 차이를 계산한다. keepAliveTimeout을 넘었으면 순찰이 직접 socket.close()를 호출한다.

검사 주체: Worker가 아니라 별도의 백그라운드 순찰
1
Poller register() 호출 시점 SocketInfo 생성

일반 요청과 완전히 동일 — 소켓 등록 시 상태값도 똑같이 생성된다.

2
Worker startAsync() 호출 후 즉시 반납 응답은 아직 진행 중

Worker는 반납되지만, 응답 자체는 "아직 안 끝남" 상태로 남는다 (Chapter 2 참고).

3
종료 마커(0\r\n\r\n) emitter.complete() 전까지 미전송 SocketInfo 계속 미완료(false)

이벤트가 몇 개가 오가든 이 종료 마커만 안 나가면, Tomcat 입장에서 이 요청은 계속 "안 끝남" 상태다.

( SocketInfo가 계속 false -> 이 소켓은 "idle 대기 그룹" 명단에 이름을 올린 적이 없음 )
4
백그라운드 순찰 idle 그룹만 훑음 이 소켓은 목록에 없음

순찰 자체는 똑같이 계속 돌지만, 검사 대상 목록(idle 그룹)에 이 소켓이 없어서 keepAliveTimeout 초과 여부를 검사받을 기회 자체가 없다. Worker가 write를 했는지 안 했는지와는 무관한 결과다.

검사 대상 포함 여부: SocketInfo가 완료(true)로 안 바뀌는 한 영원히 제외
정리 "완료 여부"라는 상태값 하나가 idle 그룹 편입을 가른다. Worker가 write하는 시점과 백그라운드 순찰이 검사하는 시점은 서로 다른 주체가 하는 서로 무관한 사건이며, SSE는 그 상태값을 계속 false로 남겨두기 때문에 순찰 대상 자체에 포함되지 못할 뿐 — keep-alive가 없는 게 아니라 검사받을 자격 자체가 없는 것이다.
그래서 SSE에 heartbeat가 필요하다 keepAliveTimeout이 이 소켓을 검사 대상에서 원천 제외한다는 건, 뒤집어 보면 Tomcat이 이 연결의 생사를 자동으로 확인해주는 안전장치가 이 소켓에는 아예 없다는 뜻이다. 일반 요청은 idle 그룹에 들어가 있으니 백그라운드 순찰이 알아서 죽은 연결을 걸러주지만, SSE 소켓은 그 순찰 대상 목록에 이름을 올린 적이 없어서 아무도 대신 확인해주지 않는다. 클라이언트가 탭을 닫거나 네트워크가 끊겨도 이 소켓 쪽에서는 아무 자동 감지가 안 일어난다. 그래서 애플리케이션이 스스로 주기적으로 : ping\n\n 같은 heartbeat를 보내 write를 강제로 발생시켜야 한다 — Tomcat의 순찰이 안 해주는 "이 연결 아직 살아있나?" 확인을, 애플리케이션이 write 성공/실패로 직접 떠맡는 것이다. 이 write가 실패하는 순간 죽은 연결을 조기 발견해 정리로 이어지는 자세한 메커니즘은 Chapter 5 참고.
Chapter 4

Push를 실제로 실행하는 스레드 — Worker가 아니라 "그 순간 send()를 호출한 스레드"

emitter.send() 호출은 Poller의 OP_READ 감지도, Worker 큐 알림도 아니다. 새로운 요청이 아니므로 Acceptor/Poller의 dispatch 경로 자체를 타지 않는다. 이미 확보된 채널에 그냥 직접 쓸 뿐이다. 

emitter.send(이벤트) 호출
    |
이 호출을 실행한 스레드가 그 자체로 write 수행
    |
소켓 버퍼 여유 있음 -> 그 자리에서 write 완료
소켓 버퍼 꽉 참    -> Poller에 OP_WRITE 등록해두고 나중에 이어서 완료 (Worker 재할당 아님)

이 write를 실행하는 스레드는 트리거에 따라 둘 중 하나

별도 스레드풀

트리거가 시간/외부 이벤트인 경우(주기적 heartbeat, 주가 업데이트 등) — HTTP 요청과 자연스럽게 안 엮여 있으므로, 개발자가 별도로 관리하는 스레드풀(스케줄러, ExecutorService — maxThreads와 무관한 자원)이 담당

다른 요청의 Worker

트리거가 다른 사람의 HTTP 요청인 경우(예: 채팅에서 B가 메시지 보내면 A에게 push) — B의 요청을 처리하던 Worker가 자기 컨트롤러 로직 안에서 그대로 emitters.get(A).send(...) 호출. 이때는 Worker 자신이 push의 write까지 수행

공통점은 하나뿐 최초에 그 SSE 연결을 열었던 그 Worker가 다시 돌아와서 push하는 일은 없다 — 이미 반납되어 전혀 다른 요청을 처리하러 갔을 수 있다. "커스텀 풀을 안 만들면 자동으로 Worker가 대신 일해준다"는 폴백 메커니즘도 존재하지 않는다.
Chapter 5

SSE 종료 로직 — 4가지 트리거

SSE는 idle 타이머로 저절로 안 끝난다. 아래 사건 중 하나가 실제로 발생해야 끝난다.

① 명시적 완료

emitter.complete() 호출. 컨테이너가 chunked 종료 마커 전송 + socket.close()까지 수행.

② 클라이언트 이탈

클라이언트가 FIN을 보내도 서버 커널은 즉시 CLOSE_WAIT로만 전환할 뿐, 애플리케이션이 다음 send() 시도에서 IOException(Broken pipe)을 맞아야 비로소 알아챈다.

③ 타임아웃

SseEmitter(timeoutMillis) 또는 spring.mvc.async.request-timeout(Spring 기본 30초!) 경과 시 onTimeout() 콜백 실행.

④ 컨테이너 종료

Tomcat 셧다운 시 강제 종료.

②번이 위험한 이유 — CLOSE_WAIT 누적

클라이언트 FIN 전송
    |
서버 커널: CLOSE_WAIT로 전환 (여기서 자동으로 안 끝남, TCB는 그대로 살아있음)
    |
애플리케이션이 write를 시도한 적이 없으면 -> 이 사실을 영원히 모름
    |
CLOSE_WAIT 상태로 무한정 쌓일 수 있음 (fd 누수)
그래서 heartbeat가 필요하다 실무에서는 주기적으로 : ping\n\n 같은 heartbeat를 보내 write를 강제로 발생시킨다. 이 write가 실패하는 순간 죽은 연결을 조기 발견해 onError() -> 정리로 이어진다. (일부 컨테이너 구현은 OP_READ로 EOF를 감지해 write 실패보다 먼저 알아채는 경로도 제공하지만, 타이밍 신뢰도가 낮아 heartbeat가 표준 관행이다.)
Chapter 6

OS 소켓은 HTTP든 SSE든 WebSocket이든 구분하지 않는다

3-way handshake(SYN/SYN-ACK/ACK)는 연결을 "여는" 절차, 4-way handshake(FIN/ACK/FIN/ACK)는 "닫는" 절차다. 프로토콜 종류와 무관하게 모든 TCP 연결이 동일하게 밟는다.

3-way — 연결 열기

HTTP든 SSE든 WebSocket이든 전부 동일한 절차

4-way — 연결 닫기

마찬가지로 전부 동일한 절차

WebSocket이 "특별해 보이는" 지점 — TCP가 아니라 HTTP 레이어

1. TCP 3-way handshake (여기까진 그냥 TCP)
2. HTTP 요청 1개: GET /chat, Upgrade: websocket, Connection: Upgrade
3. 서버 응답: 101 Switching Protocols
    |
   이 순간부터 "같은 소켓, 같은 바이트 스트림"을 애플리케이션이
   "이제부터 WebSocket 프레임으로 해석하겠다"고 자기들끼리 약속한 것뿐
커널에는 구분 플래그가 없다 커널은 fd, 소켓 상태(ESTABLISHED/CLOSE_WAIT/...), 수신·송신 버퍼만 안다. 그 바이트를 HTTP 요청으로 볼지, SSE 텍스트로 볼지, WebSocket 프레임으로 볼지는 전적으로 유저스페이스(Tomcat + 애플리케이션 코드)의 해석이다. Tomcat이 101 응답 이후 그 소켓을 처리하는 Processor 객체를 WebSocket 전용으로 갈아끼우는 건 JVM 메모리 안의 일일 뿐, 커널이 소켓에 뭔가를 표시하는 게 아니다.
Chapter 7

소켓 정보 저장 위치 — Tomcat(JVM) 관리 vs Application 관리

"JVM이냐 application이냐"는 사실 두 레이어로 나뉜다.

레이어저장하는 것관리 주체
저수준 배관 실제 소켓(fd, SocketChannel), Poller의 Selector 등록(SelectionKey), AsyncContext 객체 Tomcat(컨테이너)
커널 TCB(순서 번호, 윈도우 크기, 버퍼) OS 커널
비즈니스 매핑 "이 emitter가 어느 유저 것이었는지"를 기억하는 저장소 (예: Map<userId, SseEmitter>) Application(개발자 코드)
Tomcat은 비즈니스 개념을 모른다 Tomcat은 "이 소켓이 비동기 응답 진행 중"이라는 사실은 알지만, "userId=42한테 push해줘" 같은 비즈니스 개념은 전혀 모른다. 그래서 나중에 특정 유저에게 이벤트를 보내려면, 개발자가 직접 Map<userId, SseEmitter> 같은 저장소에 그 참조를 넣어뒀다가 이벤트 발생 시 꺼내 써야 한다. 이 저장소를 안 만들어두면 Tomcat 쪽엔 아무 문제가 없어도 애플리케이션 입장에서는 그 연결을 다시 찾을 방법이 없다.

한 줄 정리

  • SSE 최초 연결은 일반 HTTP 요청과 완전히 동일 — 다른 건 Content-Type과 body가 안 끝난다는 것뿐
  • body가 "안 끝난다"는 건 chunked encoding의 종료 마커(0\r\n\r\n)를 서버가 일부러 안 보낸다는 뜻
  • 나이브 구현(startAsync() 미사용)은 Worker를 연결 수명 내내 붙잡음 -> C10K 문제 재발
  • Async 구현은 최초 요청 처리 후 Worker를 즉시 반납 -> 이후 push는 Acceptor/Poller의 dispatch 경로를 안 탐
  • push를 실행하는 스레드는 트리거에 따라 다름 — 별도 스레드풀(시간/외부 이벤트 기반)이거나, 다른 요청을 처리하던 Worker(요청 기반 트리거) 그 자신
  • SSE 종료는 idle 타이머가 아니라 complete()/write 실패 발견/타임아웃/컨테이너 종료 중 하나의 사건으로 트리거됨 — 클라이언트 FIN만으로는 CLOSE_WAIT에 머물 뿐 완전히 안 지워짐
  • 3-way/4-way handshake는 프로토콜별 차이가 아니라 모든 TCP 연결의 open/close 절차 — WebSocket 구분은 HTTP 레이어의 Upgrade 협상일 뿐, 커널에 프로토콜 구분 플래그는 없음
  • 저수준 배관(소켓, Selector 등록, AsyncContext)은 Tomcat이, "이 연결이 누구 것인지"는 application이 각자 저장
