Frontend 알고리즘 useMemo 그래프 순회 2026-07-15

인접 리스트 재사용 · 방문 Set 공유 · shift→pop · useMemo — 느려지는 상황을 재현하고 하나씩 고쳐본다

대상 예시: 대댓글이 있는 댓글 스레드 뷰어(실제 코드가 아닌 개념 설명용 analogy)

범위: 계산(자료구조) 단계만 다룬다. 계산 결과를 화면에 반영하는 그리기(렌더링) 단계는 카드 리스트 렌더링 메모이제이션 최적화 문서 참고. 이 문서는 그 이전, "어떤 댓글을 숨길지"를 구하는 단계에서 벌어지는 문제를 다룬다.

0

배경

대댓글이 많은 게시판, 이슈 트래커의 스레드형 댓글, 협업 툴의 답글 체인처럼 부모-자식 관계를 가진 항목을 재귀적으로 접고 펼치는 UI를 만들다 보면 실무에서 자주 마주치는 성능 함정이 하나 있는데, 그걸 재현한 예제로 이 글을 시작한다.

게시글 상세 화면에서 대댓글이 많은 스레드는 기본적으로 접힌 상태로 시작한다고 하자. "답글 보기"를 누르기 전까지는 자식 댓글이 화면에 안 보이는, 흔히 보는 UI다.

post (게시글) / \ c1 c2 / \ \ c3 c4 c5 \ c6 comments 배열 ({id, parentId} 형태): [ c1{post}, c2{post}, c3{c1}, c4{c1}, c5{c2}, c6{c5} ] // N = 6개

핵심 변수 두 가지: collapsedThreadIds: Set<string> — "지금 접혀 있는 댓글 id 목록". 댓글 자신은 화면에 보이고, 그 댓글의 답글만 숨겨진다는 뜻. replyIndex: Map<commentId, replyId[]> — "댓글 id → 바로 아래 답글 id 배열" 관계표. (아래 이름 replyIndex, collapsedThreadIds 등은 전부 예시용이며 실제 코드가 아니다.)

1

상황 재현 — 무엇이 느렸나

화면을 그리는 컴포넌트에는 접힌 스레드들의 모든 답글 id 집합(hiddenIds)을 계산해 필터로 숨기는 computeVisibleComments 같은 함수가 있다. 아래는 이 역할을 하는 코드를 실무에서 흔히 보이는 형태로 재현한 것이다.

computeVisibleComments.js (Before) 
// 댓글 하나의 모든 답글 id를 모아서 반환하는 "자기 완결형" 함수
function getHiddenReplyIds(commentId, comments) {
  // 호출될 때마다 매번 새로 만드는 "부모 → 답글 목록" 색인
  const replyIndex = new Map();
  for (const c of comments) {
    if (!c.parentId) continue;
    if (!replyIndex.has(c.parentId)) replyIndex.set(c.parentId, []);
    replyIndex.get(c.parentId).push(c.id);
  }

  // 호출될 때마다 매번 새로 만드는 "이미 방문한 댓글" 집합
  const visited = new Set();
  const toVisit = [commentId];
  while (toVisit.length > 0) {
    const cur = toVisit.shift();          // 맨 앞에서 뺀다
    for (const replyId of replyIndex.get(cur) ?? []) {
      visited.add(replyId);
      toVisit.push(replyId);
    }
  }
  return visited;
}

// 접힌 스레드들의 답글을 전부 모아 화면에서 숨기는 함수
function computeVisibleComments(allComments, collapsedThreadIds) {
  const hiddenIds = new Set();
  for (const id of collapsedThreadIds) {          // 접힌 스레드가 800개면
    getHiddenReplyIds(id, allComments).forEach((d) => hiddenIds.add(d));  // ← 800번 호출
  }

  // "답글 있는 댓글 집합"을 위해 comments 배열을 또 한 번 순회
  const hasRepliesSet = new Set(allComments.filter((c) => c.parentId).map((c) => c.parentId));

  return {
    visibleComments: allComments.filter((c) => !hiddenIds.has(c.id)),
    hasReplies: (id) => hasRepliesSet.has(id),
  };
}

컴포넌트 쪽에서 이 함수들을 호출하는 코드:

CommentThread.jsx (Before) 
// 답글 미리보기를 열 때마다 호출
const hiddenIds = getHiddenReplyIds(commentId, allComments);

// 댓글을 클릭할 때마다 호출
const hasReplies = allComments.some((c) => c.parentId === commentId);
이 코드가 왜 문제인가 댓글 2,000개짜리 스레드(접힌 스레드 800개)라고 하면 — 접기/펴기를 한 번 클릭할 때마다 getHiddenReplyIds가 800번 호출되고, 그때마다 replyIndex를 처음부터 다시 만드느라 comments 배열을 800번 훑는다. 단순 계산으로도 배열 스캔만 160만 회. 여기에 미리보기 호버·클릭마다 반복되는 추가 스캔까지 더하면 클릭 한 번에 수백만 번 단위의 불필요한 연산이 쌓인다.

이런 일이 벌어지는 이유는 하나로 요약된다: "항목 1개를 처리하는 함수" 안에 "전체를 준비하는 계산"이 함께 들어 있어서다. getHiddenReplyIds(commentId, comments)는 댓글 하나만 다루는 것처럼 보이지만, 그 안에서 매번 스레드 전체의 관계표(replyIndex)를 새로 만든다. 이 함수를 collapsedThreadIds 개수만큼 루프에서 호출하는 순간, "전체 준비"가 호출 횟수만큼 그대로 반복된다 — 함수 하나만 보거나 호출부 하나만 봐서는 눈에 띄지 않는 함정이다.

  1. replyIndex를 호출마다 다시 그린다 — 접힌 스레드 수만큼 똑같은 색인을 반복 생성 (→ Chapter 2)
  2. Set을 공유하지 않는다 — 조상이 이미 방문한 답글을 자식이 또 방문 (→ Chapter 3)
  3. toVisit.shift()로 맨 앞에서 뺀다 — 목록이 길수록 매번 전체가 한 칸씩 밀림 (→ Chapter 4)
  4. 컴포넌트에서 매번 다시 호출한다 — useMemo 없이 렌더/클릭마다 재계산 (→ Chapter 5)
  5. 같은 정보를 두 번 만든다 — hasRepliesSet을 위해 comments를 또 순회 (→ Chapter 6)
2

개선 1 — replyIndex는 한 번만 만든다

comments 배열은 (자식, 부모) 쌍의 나열이라 "c1의 답글이 누구지?"에 바로 답할 수 없다. 그래서 순회 전에 부모 → 답글 목록 색인(replyIndex)을 만드는 것 자체는 맞는 접근이다. 문제는 이 색인을 getHiddenReplyIds 함수 안에, 즉 호출될 때마다 만들었다는 것.

replyIndex = { post: [c1, c2], c1: [c3, c4], c2: [c5], c5: [c6] }
문제 Chapter 1의 코드는 "이 댓글 밑에 누가 있어?"를 물을 때마다 comments 배열을 처음부터 끝까지 읽어 replyIndex를 새로 만들었다. 접힌 스레드가 800개면 같은 색인을 800번 만든 셈.
AFTER
buildReplyIndex.js 
function buildReplyIndex(comments) {
  const replyIndex = new Map();
  for (const c of comments) {
    if (!c.parentId) continue;
    if (!replyIndex.has(c.parentId)) replyIndex.set(c.parentId, []);
    replyIndex.get(c.parentId).push(c.id);
  }
  return replyIndex;
}

function computeVisibleComments(allComments, collapsedThreadIds) {
  const replyIndex = buildReplyIndex(allComments);  // ← 딱 1번만 생성
  const hiddenIds = new Set();
  for (const id of collapsedThreadIds) collectHiddenReplyIds(id, replyIndex, hiddenIds);
}
원칙 입력(comments)이 같으면 결과가 항상 같은 계산은 반복문 밖으로 꺼낸다(호이스팅).

개선 2 — hiddenIds(방문 Set)를 공유해서 중복 순회 제거

접힌 스레드끼리 포함 관계(접힌 댓글의 답글 중에 또 접힌 댓글이 있는 경우)가 있을 수 있다:

c1 (접힘) ├─ r1 └─ c2 (접힘) ├─ r2 └─ r3

collectHiddenReplyIds(c1, replyIndex, hiddenIds) → hiddenIds = {r1, c2, r2, r3} (c1의 답글 전부). 이어서 collectHiddenReplyIds(c2, replyIndex, hiddenIds) → r2, r3이 이미 hiddenIds에 있어서 즉시 스킵.

collectHiddenReplyIds.js 
function collectHiddenReplyIds(commentId, replyIndex, hiddenIds) {
  const toVisit = [commentId];
  while (toVisit.length > 0) {
    const cur = toVisit.pop();
    for (const replyId of replyIndex.get(cur) ?? []) {
      if (!hiddenIds.has(replyId)) {   // 이미 방문했나?
        hiddenIds.add(replyId);
        toVisit.push(replyId);
      }
    }
  }
}
흔한 오해 바로잡기 — "hiddenIds를 공유하면 남의 댓글까지 숨기는 거 아닌가?" 아니다. 탐색 범위 자체는 언제나 replyIndex.get(cur)(실제 답글 구조)로만 결정된다. hiddenIds.has(replyId) 체크는 "이미 아는 답글이니 더 안 내려가도 됨"을 판단할 뿐, 탐색을 남의 스레드로 확장시키지 않는다. c2가 c1의 답글인 경우 c2의 답글 r2, r3은 c2 입장에서도 진짜 자기 답글이라 겹치는 게 당연한 것 — 무관한 댓글이 섞이는 게 아니다.

개선 3 — queue(shift) → stack(pop)

BEFORE (Chapter 1)
Before 
const toVisit = [commentId];
const cur = toVisit.shift();   // 배열 맨 앞 제거 = 나머지 전부 한 칸씩 당김 → O(n)
AFTER
After 
const toVisit = [commentId];
const cur = toVisit.pop();     // 배열 맨 뒤 제거 = 아무도 안 움직임 → O(1)

최종적으로 구하는 건 순서 없는 Set이라, 답글을 위쪽부터 훑든 아래쪽부터 훑든 결국 방문하는 댓글 집합은 완전히 동일하다. 결과는 그대로 두고 연산만 싸게 바꾼 변경이다.

개선 4 — 컴포넌트 쪽, useMemo로 결과 재사용

BEFORE (Chapter 1)
Before 
const handleReplyPreviewHover = useCallback((commentId) => {
  const hiddenIds = getHiddenReplyIds(commentId, allComments);
  // ← 미리보기 표시할 때마다 allComments를 처음부터 순회
}, [allComments]);

const handleCommentClick = useCallback((commentId) => {
  const hasReplies = allComments.some((c) => c.parentId === commentId);
  // ← 클릭할 때마다 배열을 처음부터 한 줄씩 확인
}, [allComments]);
AFTER
After 
const replyIndex = useMemo(() => buildReplyIndex(allComments), [allComments]);

const handleReplyPreviewHover = useCallback((commentId) => {
  const hiddenIds = new Set();
  collectHiddenReplyIds(commentId, replyIndex, hiddenIds);  // 이미 있는 색인 조회만
}, [replyIndex]);

const handleCommentClick = useCallback((commentId) => {
  if (!replyIndex.has(commentId)) return;   // O(1) 해시 조회
}, [replyIndex]);

useMemo가 정확히 어떻게 이걸 막았나 — React는 렌더링마다 이전 의존성(allComments)과 이번 allComments를 참조 비교한다. 호버·클릭은 다른 state(setSelectedCommentId 등)를 바꿔 리렌더시키지만, 이때 comments/collapsedThreadIds는 그대로이므로 allComments 참조도 그대로 유지된다 → buildReplyIndex를 재실행하지 않고 캐시된 Map을 그대로 반환한다.

전제조건 allComments가 상위 useMemo의 결과라 참조가 안정적이어야 한다. useMemo 체인은 위에서부터 참조 안정성이 유지돼야 효과가 있다.

개선 5 — 덤, 같은 정보를 두 번 만들지 않기

hasReplies.js 
// Before (Chapter 1): "답글 있는 댓글 집합"을 위해 comments 전체를 또 한 번 순회
const hasRepliesSet = new Set(allComments.filter((c) => c.parentId).map((c) => c.parentId));

// After: replyIndex 의 key 가 곧 "답글 있는 댓글" — 이미 있는 정보 재사용

replyIndex에 key로 있다 = 답글이 있다는 뜻이다. 같은 정보를 두 개의 자료구조로 표현하지 않는다.

성능 요약

댓글 2,000개짜리 스레드(접힌 스레드 800개 가정)에서 접기/펴기 클릭 1회당:

구분BeforeAfter
replyIndex 생성800번(전체 순회 160만 회)1번(2,000회)
답글 순회중복 방문 다수(최악 O(N²))댓글당 최대 1회
큐/스택 연산shift O(n)pop O(1)
클릭 시 답글 존재 판단Array.some O(N)Map.has O(1)

왜 안전한가(회귀 위험 없음) — hiddenIds = "접힌 스레드들의 답글 합집합" — Set을 각자 만들어 합치든 하나에 누적하든, 순회 순서를 바꾸든 집합으로서 결과는 동일하다. hasReplies = replyIndex의 key 집합 = 답글이 있는 parentId 집합, 정의상 같다. 즉 계산 방법만 바꾸고 결과는 그대로 유지한 리팩터링이다.

8

일반화 — 다른 코드에도 적용 가능한 패턴

  • 불변 계산 호이스팅 — 입력이 안 변하는 계산은 함수/반복문 밖으로.
  • 방문 상태 공유 — 반복 호출들이 "방문 여부" Set을 공유하면 중복 순회 자동 차단.
  • 순서가 필요 없으면 싼 쪽 끝에서 — 집합만 필요하면 shift 대신 pop.
  • 렌더 간 재사용은 useMemo — 단, deps의 참조 안정성이 전제.
  • 원본 데이터 vs 파생값 구분 — 재계산 불가능은 useState, 재계산 가능은 useMemo, 외부 동기화는 useEffect.

핵심 정리

  • "항목 1개 처리 함수" 안에 준비 작업을 넣지 않는다 — 루프에서 호출되는 순간 준비가 N번 중복된다
  • 불변 계산(replyIndex)은 반복문 밖으로 호이스팅, 방문 상태(Set)는 호출 간에 공유
  • 집합만 필요하면 shift 대신 pop — 순서가 필요 없는 곳에 굳이 비싼 연산을 쓰지 않는다
  • useMemo 체인은 deps 참조 안정성이 전제 — 위쪽이 매 렌더 새 배열이면 무용지물
  • 같은 정보를 두 자료구조로 중복 계산하지 않는다 — 이미 만든 색인의 key를 재사용한다

계산 결과를 화면에 반영하는 그리기(렌더링) 단계의 최적화는 카드 리스트 렌더링 메모이제이션 최적화 문서 참고.
