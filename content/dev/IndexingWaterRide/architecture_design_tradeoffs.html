Chapter 1

데이터 저장소 선택

Member / Reminder 를 Notion DB 로 선택한 이유

  • 트레이드오프: Postgres 테이블/마이그레이션을 직접 관리하는 비용 vs Notion API 호출 지연 및 비공식 사용량 제한
  • 선택 이유 1: 개인 규모 운영에서는 스키마 마이그레이션 부담을 줄이는 게 더 중요했음
  • 선택 이유 2: 내 Notion을 통해서 사용자를 직접 선별하고 싶었음

물타기 포지션은 Postgres 사용

  • Member/Reminder와 달리 AveragingPosition은 JPA로 PostgreSQL에 직접 CRUD
  • 선택 이유: 매수 단가·수량처럼 정밀도가 중요하고 조회 빈도가 높은 금융 데이터를 외부 API(Notion) 지연·레이트리밋에 노출시키고 싶지 않았음
기준 "스키마 안정성이 더 중요한가, 정밀도·조회속도가 더 중요한가"로 저장소를 나눠서 선택했다.
Chapter 2

외부 API 연동

비공식 외부 API(KRX, Naver, Yahoo, FRED) 사용

  • 트레이드오프: 무료·즉시 사용 가능 vs 공식 스펙이 없어 응답 포맷이 예고 없이 바뀔 수 있음
  • 실제로 겪은 문제: KRX가 JSON을 내려주면서 Content-Type을 text/html로 받아서 WebClient deserialize가 실패했고, 응답 크기도 기본 버퍼 한도(256KB)를 넘어서 따로 안 늘리면 버퍼가 터져버림
  • 해결 방식: 추측으로 고치지 않고 실제 curl 호출과 로그로 원인을 재현한 뒤 수정
비공식 API의 본질적 위험 스펙 문서가 없다는 건 "오늘 동작했다"가 "내일도 동작한다"를 보장하지 않는다는 뜻이다. Content-Type 불일치, 버퍼 한도 같은 문제는 코드 리뷰로는 안 보이고 실제 호출로만 드러난다.
Chapter 3

캐싱 전략

Eager preload vs Lazy cache-aside

  • 국내 종목(KRX 전체 목록)은 "전체 목록"을 한 번에 받을 수 있는 API가 있어서 기동 시 전부 캐시에 적재(eager)
  • 해외 종목은 그런 전체 목록 API가 없어서, 검색에 성공한 키워드만 캐시에 적재하고 실패 결과는 캐시하지 않는 lazy cache-aside로 설계
  • 트레이드오프: lazy 전략은 첫 조회가 항상 외부 API를 거치지만, 안 쓰는 데이터를 무한정 메모리에 들고 있지 않음
구분국내 종목해외 종목
전체 목록 API있음없음
적재 전략Eager preload (기동 시 전부)Lazy cache-aside (성공한 키워드만)
첫 조회 비용없음 (이미 캐시됨)외부 API 호출 1회
메모리 사용전체 목록만큼 고정실제 쓰는 만큼만 증가
Chapter 4

JPA / 트랜잭션

JPA 트랜잭션 함정

  • deleteByIdAndTelegramId처럼 커스텀 derived delete 메서드는 상속받은 CRUD 메서드(deleteById)와 달리 자동으로 트랜잭션이 걸리지 않아서, 포지션 삭제가 조용히 실패하는 버그로 나타남
  • 실제 TransactionRequiredException을 재현하는 테스트를 먼저 작성해 원인을 확정한 뒤 @Transactional을 추가하고, 같은 테스트로 수정을 검증
함정 Spring Data JPA의 derived delete 메서드는 기본 CRUD 메서드와 같은 인터페이스에 있어도 트랜잭션이 자동으로 안 걸린다. "조용히 실패"하는 버그라 알아채기 어렵고, 재현 테스트를 먼저 작성하는 게 원인 확정에 제일 빨랐다.
Chapter 5

텔레그램 봇 UX

자동 진행(auto-skip) 대신 항상 버튼 확인

  • 검색 결과가 1개거나 정확히 일치해도 자동으로 다음 단계로 넘기지 않고, 항상 버튼으로 확인받도록 설계
  • 트레이드오프: 사용자가 눌러야 하는 횟수는 늘지만, 의도하지 않은 종목이 실수로 선택되는 사고를 막음 — 포지션(돈)을 다루는 도구라 안전을 편의보다 우선

"계산기"와 "실제 매수"의 분리

  • 계산기(물타기 what-if, % 계산기)는 절대 DB에 반영하지 않고, 순수 계산 로직만 호출하도록 실제 매수 플로우와 코드 경로를 분리
  • 트레이드오프: 코드 경로가 두 개로 나뉘어 약간의 중복이 생기지만, "미리보기였는데 실수로 실제 포지션이 바뀌는" 사고를 원천 차단

포지션 수정 UX: 한 번에 입력 vs 단계별 입력

  • 처음엔 "평단가,수량" 쉼표 구분 한 줄 입력으로 설계했다가, 평단가 → 수량 → (해외는 환율까지) 단계별 입력으로 다시 변경
  • 트레이드오프: 대화 턴 수는 늘지만, 포맷 실수(쉼표 누락, 순서 혼동) 가능성이 줄고 기존 포지션 생성 플로우와 UX가 일관됨

종목 검색 결과 정렬: 완전일치 > 접두일치 > 부분일치 > 길이순

종목명 검색(국내: StockMasterService.search)은 입력값과 완전히 같은 이름을 최우선, 그다음 입력값으로 시작하는 이름, 그다음 단순 포함만 하는 이름 순으로 정렬하고, 동일 등급 내에서는 이름이 짧은(=입력값에 더 가까운) 종목을 먼저 보여준다.

순위등급종목명
1완전일치SK하이닉스
2접두일치SK하이닉스레버리지
3부분일치Kodex SK하이닉스레버리지
트레이드오프 정렬 로직이 한 단계 더 늘지만, 사용자가 의도한 종목이 후보 목록 상단에 오도록 보장해 잘못된 종목을 실수로 선택할 위험을 줄인다.
Chapter 6

인프라 / CI·CD

GitHub 클라우드 러너(inbound SSH) vs self-hosted runner(outbound polling)

  • 홈서버는 공유기 포트포워딩을 열지 않아 외부에서 inbound 접속이 원천적으로 불가능한 환경
  • 처음엔 GitHub 클라우드 러너 + scp-action/ssh-action으로 설계했으나, 이 전제 자체가 깨져서 self-hosted runner(홈서버가 GitHub로 outbound polling)로 전환
  • 트레이드오프: SSH 키 발급/등록, 포트포워딩, DDNS 같은 인바운드 노출 설정이 전부 사라지고 빌드 산출물도 cp로 바로 옮길 수 있어 더 단순하고 안전해지지만, 홈서버에 runner 프로세스를 항상 띄워두고 직접 관리해야 하는 책임이 생김
TODO로 남긴 것 같은 홈서버에 다른 프로젝트가 추가될 가능성을 고려해, runner를 프로젝트당 1개씩 별도 디렉토리/서비스/레이블(iwr-home-server)로 분리했다. 레포 수가 늘어나면 매번 runner를 새로 까는 비용이 커지므로, 그 시점엔 Organization 이전 + org-level runner 공유로 전환할 것을 TODO로 남겨둠.
Chapter 7

아키텍처 구조의 한계

단일 프로세스 구조의 한계

  • Telegram bot polling은 토큰 하나당 프로세스 하나만 가능해, Spring Boot 한 프로세스가 REST API + Bot + 스케줄러를 모두 담당
  • 비용·운영은 단순해지지만, 그 프로세스가 죽으면 전체 기능이 동시에 멈추는 단일 장애점(SPOF)이 됨
인지하고 있는 것 개인 규모에서는 이 SPOF를 감수하는 게 합리적인 선택이었지만, 운영 부하나 사용자 수가 늘어나면 봇/스케줄러/API를 프로세스 단위로 분리해야 할 지점이다.

한 줄 정리

  • 스키마 안정성 vs 정밀도/속도 — 데이터 성격에 따라 저장소를 분리했다
  • 비공식 API는 추측이 아니라 실제 호출 재현으로 디버깅했다
  • 전체 목록이 있으면 eager, 없으면 lazy cache-aside
  • derived delete 메서드는 트랜잭션이 자동으로 안 걸린다는 함정을 테스트로 확정 후 수정
  • 돈을 다루는 봇이라 편의보다 안전(버튼 확인, 계산기/실매수 분리)을 우선했다
  • 인프라 제약(포트포워딩 불가)이 CI/CD 설계 자체를 바꿨다
  • 단일 프로세스 SPOF는 알고 있는 채무로 남겨두고 있다
