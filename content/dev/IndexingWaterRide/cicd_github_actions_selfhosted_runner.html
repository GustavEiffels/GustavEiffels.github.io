IndexingWaterRide 배포 자동화 — 포트포워딩이 막힌 홈서버에 outbound polling 방식으로 CI/CD를 구축한 기록

Chapter 1

배경 및 환경

프로젝트 환경

IndexingWaterRide는 텔레그램 polling 방식으로 사용자 메시지를 감지하고 응답한다. 즉 외부에서 서버로 들어오는(inbound) 연결이 필요 없는 구조다.

서버는 집에 있는 개인 서버이며, 보안 취약성 우려로 포트포워딩을 열지 않았다. 그 결과 외부에서 인바운드로 서버에 접근할 수 없는 상태다.

제약 조건 GitHub가 제공하는 클라우드 러너는 해당 서버에 직접 접속해 배포할 방법이 없다. 서버가 먼저 GitHub 쪽으로 연결을 거는 방식이 필요하다.

기존 배포 방식의 문제

배포할 때마다 집 서버에 SSH로 직접 접속해서 빌드 파일을 내렸다 올렸다 하는 수동 작업을 반복했다. 사람이 매번 개입해야 하고, 절차가 사람마다/순간마다 달라질 수 있다는 점이 문제였다.

Chapter 2

GitHub Actions 기본 개념

GitHub Actions란

레포지토리에 .github/workflows/*.yml 형태로 워크플로우를 정의해두면, push·PR 같은 이벤트가 발생할 때 GitHub가 그 워크플로우를 자동으로 실행해주는 CI/CD 도구다.

워크플로우는 하나 이상의 job으로 구성되고, 각 job은 다시 순차적으로 실행되는 step들로 구성된다. 각 job은 runs-on에 지정한 실행 환경에서 돈다.

클라우드 러너 vs Self-hosted 러너

구분클라우드 러너Self-hosted 러너
실행 위치GitHub가 제공하는 임시 VM직접 등록한 머신(여기서는 홈서버)
네트워크 방향GitHub → 클라우드 VM 생성러너 → GitHub로 outbound polling
인바운드 서버 적합성부적합 (직접 접속 불가)적합 (서버가 먼저 연결을 검)

인바운드가 막힌 홈서버에 배포하려면 서버 쪽에서 먼저 GitHub로 연결을 거는 self-hosted runner가 필요한 이유가 여기에 있다.

Chapter 3

적용한 방식

Self-hosted Runner 등록

홈서버에 GitHub Actions Runner를 설치하고 레포지토리에 등록했다. 레이블은 self-hosted, Linux, X64, iwr-home-server로 지정.

동작 방식 Runner는 등록 후 GitHub 쪽으로 outbound polling만 하면서 "실행할 job 있어?"를 계속 물어본다. 포트포워딩 없이도 GitHub과 통신이 가능한 이유다.

레이블을 프로젝트 전용(iwr-home-server)으로 둔 이유는, 같은 서버에 다른 프로젝트 runner가 떠 있어도 job이 섞이지 않게 하기 위함이다.

Repository Variable 설정 화면

deploy.yml 워크플로우

트리거는 main 브랜치 push. concurrency 그룹으로 묶어서 배포가 동시에 겹치지 않게 막는다.

deploy.yml — 트리거 / 동시성 제어 / 체크아웃 / JDK 세팅 
name: Deploy

on:
  push:
    branches: [main]

concurrency:
  group: deploy-main
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: [self-hosted, iwr-home-server]
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
deploy.yml — 테스트 / 빌드 / 배포 파일 교체 / 컨테이너 재기동 
      - name: Grant execute permission for gradlew
        working-directory: server
        run: chmod +x gradlew

      - name: Run tests
        working-directory: server
        run: ./gradlew test

      - name: Build jar
        working-directory: server
        run: ./gradlew bootJar

      - name: Copy jar into deploy directory
        working-directory: server
        run: |
          JAR=$(ls build/libs/*.jar | grep -v plain | head -n1)
          cp "$JAR" "${{ vars.DEPLOY_PATH }}/server.jar"

      - name: Restart server container
        working-directory: ${{ vars.DEPLOY_PATH }}
        run: docker compose up -d --force-recreate server

전체 동작 흐름

main push → 배포 완료까지 
main 브랜치에 push
  → GitHub Actions가 deploy.yml 트리거 감지
  → runs-on: [self-hosted, iwr-home-server] 와 일치하는 runner 탐색
  → 홈서버에서 polling 중이던 runner가 job 수신
  → 홈서버 위에서 직접 실행:
       checkout → JDK 17 세팅 → gradlew test
       → bootJar 빌드 → jar를 DEPLOY_PATH로 복사
       → docker compose up -d --force-recreate server

Chapter 5

조금 더 파본 것 — polling이 정확히 뭘 하는가

"몇 초마다 물어보나요?"에 답하지 못했다

처음 이 글을 쓸 땐 "runner가 GitHub 쪽으로 outbound polling을 한다"까지만 알고 있었다. 근데 다시 파고들다 보니 이 표현이 애매하다는 걸 깨달았다 — polling이라고 하면 보통 "1초마다 짧게 물어보고 끊기를 반복"하는 방식(short polling)을 떠올리게 되는데, 실제로는 그렇게 동작하지 않았다.

실제로는 long-polling이다 Runner가 요청을 하나 걸어두면, GitHub 서버는 즉시 응답하지 않고 job이 생길 때까지 그 요청을 붙잡고 있는다 (보통 최대 약 50초). 그 사이 job이 큐에 들어오면 그 순간 응답을 내려주고, 아무 일도 없이 타임아웃되면 연결이 끊기고 runner가 즉시 재연결해서 다시 대기를 건다.

이 차이를 알고 나니 인바운드가 왜 필요 없는지가 더 명확해졌다. 연결은 항상 서버 -> GitHub 방향으로만 새로 생기고, 그 연결 하나를 오래 붙잡아두는 방식이라 짧은 폴링처럼 매초 요청을 스팸하지도 않는다. "서버가 먼저 GitHub에 물어보는 구조"라고 뭉뚱그려 알고 있던 걸, "아웃바운드 HTTPS 연결을 오래 열어두고 응답을 기다리는 구조"로 한 단계 더 구체화한 셈이다.

Chapter 6

Runner를 여러 개 등록할 수 있는가

같은 서버에 여러 대도 가능하다

러너 하나는 자기 작업 디렉토리(_work/)에 체크아웃한 소스, 빌드 캐시, PID 파일을 쌓아둔다. 두 러너가 같은 폴더를 쓰면 동시에 도는 job끼리 파일을 덮어쓰며 충돌하기 때문에, 러너를 늘리려면 디렉토리를 러너 개수만큼 분리해야 한다.

두 번째 runner 등록 — 이름만 다르게, 레이블은 같게 
./config.sh --url https://github.com/<owner>/IndexingWaterRide \
  --token <REG_TOKEN> \
  --name iwr-runner-2 \
  --labels self-hosted,Linux,X64,iwr-home-server

--name만 다르게 주고 --labels는 기존 러너와 동일하게 두면, 워크플로우 파일(deploy.yml)을 전혀 건드리지 않아도 GitHub이 같은 레이블을 가진 러너 중 놀고 있는 쪽으로 job을 자동 배정해준다.

지금 당장은 의미가 없다 이 프로젝트의 deploy.yml은 concurrency: group: deploy-main으로 배포를 일부러 직렬화해뒀다. 그래서 러너를 2개로 늘려도 배포 자체는 여전히 하나씩 순서대로 돈다. 병렬이 실제로 의미 있어지는 건 PR 테스트 워크플로우처럼 배포와 별개의 job이 동시에 도는 상황이 생겼을 때다.
Chapter 7

이 구조, 보안상 괜찮은가

"파일을 받으면 배포도 받을 수 있나?" — 아니다

config.sh로 받는 tar.gz는 GitHub 공식 오픈소스 배포판이라 누구나 받을 수 있는 완전히 공개된 파일이다. 이 파일 자체엔 비밀이 없다. 진짜 관문은 --token으로 넘기는 등록 토큰이었다.

  • 이 토큰은 repo의 Settings > Actions > Runners에서 repo admin 권한으로만 생성된다
  • repo 스코프가 고정돼 있어 다른 repo에는 이 토큰으로 등록할 수 없다
  • 약 1시간이면 만료되고, 등록이 끝나면 이후 통신엔 별도 세션 자격증명을 쓴다

즉 "이 tar.gz를 손에 넣은 사람"이 아니라 "이 repo의 admin 권한을 가진 사람"만 새 러너를 등록할 수 있는 구조였다.

그럼 진짜 위험은 어디에 있나

핵심 공식 main에 push할 수 있는 사람 = 홈서버에서 임의 명령을 실행할 수 있는 사람이다. 워크플로우의 모든 run: 명령은 러너를 실행한 리눅스 유저 권한을 그대로 상속하기 때문이다.

특히 이 프로젝트는 docker compose로 컨테이너를 재기동하는데, 이게 되려면 러너 유저가 docker 그룹에 속해 있어야 한다. 근데 docker 그룹 소속 유저는 root 권한 컨테이너를 자유롭게 띄울 수 있어서 사실상 root와 동급이다. 워크플로우가 뚫리면 홈서버 전체가 뚫리는 것과 다르지 않다는 뜻이다.

GitHub이 공식적으로 경고하는 시나리오는 public repo + 외부 PR 트리거 조합이다 — 외부인이 올린 PR의 워크플로우가 pull_request 트리거로 실행되면서 임의 코드가 서버에서 돌 수 있기 때문이다. 이 프로젝트는 private repo + push 트리거만 쓰고 있어서 그 경로 자체가 막혀 있다. 완전 무위험은 아니지만, 가장 흔한 공격 경로는 처음부터 차단된 구조였던 셈이다.

실질적인 방어선 결국 공격 표면은 "GitHub 계정/repo admin 권한이 털리느냐"로 좁혀진다. branch protection으로 main 직접 push를 막고 PR 리뷰를 강제하는 것, 그리고 계정 2FA를 켜두는 것이 여기서 가장 효율이 높은 방어책이다.
Chapter 8

아직 남은 것들

같은 워크플로우 안에서도 권한의 근거는 다르다

chmod +x gradlew가 아무 문제 없이 되는 이유는, 방금 체크아웃한 자기 소유 파일이라 특별한 권한이 필요 없기 때문이다. 반면 docker compose up이 되는 이유는 러너 유저가 docker 그룹에 속해 있기 때문이다 — 같은 워크플로우 안의 명령이라도 "왜 가능한가"의 근거는 서로 다르다.

고쳐야 할 지점

문제현재 상태
롤백cp로 jar를 그냥 덮어씀 — 배포 실패 시 이전 버전으로 되돌릴 수단 없음
헬스체크docker compose up -d 성공 = 컨테이너가 떴다는 뜻이지, 앱이 실제로 정상 기동했다는 뜻은 아님
다운타임--force-recreate로 컨테이너를 통째로 내렸다 올리는 구간에 무중단이 아닌 공백이 생김

개인 홈서버 규모에 blue-green 배포 같은 걸 끌어오는 건 과하다고 보고, jar 백업 + 배포 후 /health 확인 정도를 다음에 추가해볼 계획이다.

핵심 정리

  • 인바운드가 막힌 홈서버에는 self-hosted runner의 outbound polling 방식이 적합하다
  • runner 레이블을 프로젝트 전용으로 두면 같은 서버의 다른 프로젝트와 job이 섞이지 않는다
  • 배포 경로 같은 가변 값은 repository variable로 분리해 워크플로우 파일을 환경에 종속되지 않게 만든다
  • main push 한 번으로 테스트 → 빌드 → jar 교체 → 컨테이너 재기동까지 전 과정이 자동화됐다
  • polling은 짧은 간격 재요청이 아니라 long-polling — 연결 하나를 오래 붙잡아두고 job이 생기면 바로 응답받는 방식이다
  • 등록 파일 자체는 공개 소프트웨어이고, 진짜 보안 경계는 repo admin만 발급 가능한 단기 등록 토큰이다
  • 워크플로우의 모든 명령은 러너를 실행한 리눅스 유저 권한을 그대로 물려받는다 — docker 그룹 소속이면 사실상 root급 권한이라는 뜻
  • private repo + push 트리거만 쓰는 구조라 GitHub이 경고하는 "외부 PR로 인한 임의 코드 실행" 위험은 막혀 있다
