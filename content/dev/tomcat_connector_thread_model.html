Concurrency Tomcat BIO NIO C10K 2026-07-21

"기다리기"와 "일하기"를 분리해 C10K 문제를 해결한 구조 — Acceptor / Poller / Worker

Chapter 1

배경 — 왜 스레드를 3종류로 나눴나 (C10K 문제)

옛날 방식(BIO, thread-per-connection)은 연결 하나당 스레드 하나를 그대로 배정했다. 그 스레드는 연결이 끊기기 전까지, 데이터가 올 때까지 read()에서 블로킹된 채로 붙잡혀 있었다.

문제는 HTTP keep-alive 연결의 대부분은 "열려만 있고 아무것도 안 하는 시간"이 훨씬 길다는 것이다. 그런데도 스레드(기본 스택 512KB~1MB, 컨텍스트 스위칭 비용)를 연결 하나를 위해 계속 낭비하게 된다. ( 연결 1만 개 = 스레드 1만 개라는, 이른바 C10K 문제 )

해결 방향 연결 유지와 요청 처리를 분리한 게 지금의 NIO 모델이다.
Chapter 2

이전 방식(BIO) vs 현재 방식(NIO) ( 탭으로 비교 )

두 모델 모두 Step 1~3까지는 완전히 동일하고, Step 4에서 갈라진다.

노드 클라이언트 OS 커널 Acceptor — 연결 받는 스레드 (1개) Poller — 감시 스레드 (1~2개, NIO에만 존재) Worker — 일하는 스레드 (풀)

Acceptor와 Worker 사이는 BlockingQueue 기반 Producer-Consumer 패턴이다.

1
클라이언트 SYN / SYN-ACK / ACK OS 커널

TCP 3-way handshake. 전부 커널이 처리 ( Tomcat 은 관여하지 않음 )

2
OS 커널 완성된 연결을 쌓아둠 accept queue

커널이 완성된 연결을 자기 큐(backlog, 크기 = acceptCount)에 쌓아둔다.
( 다른 스레드를 호출하는 것이 아닌 Queue 에 Connection 을 삽입 )

Connection 위치: 커널의 accept queue
3
Acceptor accept()로 꺼냄 (pull) accept queue

tomcat 의 Acceptor thread 를 이용 accept() 를 호출한 채 Queue 에 연결이 삽입되길 기다림
( Polling )

Connection 위치: Acceptor
4
Acceptor 연결되자마자 즉시 던짐 Worker 작업 큐

여기가 NIO와 갈라지는 지점. 클라이언트로부터의 요청이 왔는지 확인하지 않고, 연결만 되면 즉시 Worker 작업 큐에 던진다. 특정 Worker를 지목하지는 않는다 ( Worker Queue 에 삽입만 )

Connection 위치: Worker 작업 큐
5
Worker take()로 가져가서 연결 유지 연결이 끊길 때까지

대기하던 Worker가 스스로 가져간 뒤, 이 Connection이 끊길 때까지 블로킹 상태로 붙잡혀 있는다.
사용자가 아무 요청도 안 보내는 idle 시간에도 해당 Worker Thread 는 대기.

연결 위치: Worker가 점유 ( Connection 종료 전까지 )
이 구조의 한계 Worker가 Connection 유지 역할까지 관리한다. idle 연결도 스레드 하나씩 영구 점유한다.
( 연결 1만 개 = 스레드 1만 개 , C10K 문제 그대로 노출 )

Acceptor가 하는 일은 BIO와 똑같다. (Step 1~3 동일)
Step 4에서 넘기는 대상이 Worker 큐가 아닌 Poller에게 넘김 ( 1부(연결 저장)는 연결당 한 번, 2부(요청 처리)는 요청마다 반복 )

1부. 연결이 맺어지고 "저장"되기까지 — 연결당 딱 1번

1
클라이언트 SYN / SYN-ACK / ACK OS 커널

TCP 3-way handshake. 전부 커널이 처리 — BIO와 동일.

Connection 위치: Kernel 이 생성
2
OS 커널 완성된 연결을 쌓아둠 accept queue

커널이 accept queue(backlog, 크기 = acceptCount)에 쌓아둠 — BIO와 동일.

Connection 위치: 커널의 accept queue
3
Acceptor accept()로 꺼냄 (pull) accept queue

큐 앞에서 대기하던 Acceptor가 꺼내 감 — BIO와 동일.

Connection 위치: Acceptor가 꺼내 전달 중
4
Acceptor "이 소켓 감시해줘" Poller 등록 큐

여기가 BIO와 갈라지는 지점. Worker 큐가 아니라 Poller의 등록 큐에 넣고, Acceptor는 즉시 다음 accept() 대기로 복귀한다.

Connection 위치: Poller 등록 큐
5
Poller register() = 저장 감시 목록

Poller가 큐에서 꺼내 register()를 호출하면 감시 목록(Selector)에 추가된다. "연결이 유지되고 있다"의 실체가 바로 이 목록(+ 커널의 TCP 상태)이다.

Connection 위치: Poller 감시 목록
( idle 구간 ) 클라이언트가 아무것도 안 보내는 동안 Poller 혼자 이 소켓 포함 수천 개를 감시만 한다.
Worker는 이 Connection의 존재도 모른다. 이때 Worker 스레드 비용은 0이다.

2부. 실제 요청이 왔을 때 — 요청마다 반복

6
클라이언트 HTTP 요청 바이트 커널 수신 버퍼

사용자가 실제 요청을 보낸다. 바이트는 커널의 소켓 수신 버퍼에 쌓이기만 한다.

요청 데이터 위치: 커널 수신 버퍼
7
Poller epoll_wait(): "읽을 거 생겼어?" OS 커널

이때 Poller가 Kernel에게 요청이 들어왔는지 확인, 요청이 들어왔다면 Socket에 대한 readable 알림 전송.
( 준비됐다는 신호일 뿐 데이터가 아님 )

요청 데이터 위치: 커널 수신 버퍼 (그대로)
8
Poller "처리 가능" 알림만 넣음 Worker 작업 큐

Poller가 Worker 작업 큐에 알림 객체를 삽입 ( Readable한 Socket이 존재한다 ).
특정 Worker를 지목하거나 요청 데이터를 건드리지 않는다.

알림 위치: Worker 작업 큐 / 데이터: 여전히 커널 버퍼
9
Worker take()로 꺼냄 (pull) 작업 큐

큐 앞에서 take()로 대기하던 Worker 중 하나가 스스로 깨어나 알림을 가져간다. Step 3의 Acceptor와 완전히 같은 패턴.

알림: Worker가 수령
10
Worker socket.read() 커널 수신 버퍼

실제 요청 데이터가 처음으로 읽히는 순간. 읽은 바이트를 HTTP로 파싱하고("아, GET 요청이구나"는 여기서 처음 판명) Application(컨트롤러) 코드를 실행한다.

요청 데이터 위치: Worker 메모리 — 파싱, 비즈니스 로직 실행
11
Worker socket.write() — 직접! 클라이언트

응답을 Worker가 직접 소켓에 쓴다. Poller를 거치지 않는다. Poller는 처음부터 끝까지 데이터를 조작하지 않는다.

응답: 클라이언트 도착
12
Worker 소켓 재등록 후 pool 복귀 Poller 감시 목록

keep-alive 연결이면 소켓을 다시 감시 목록에 등록해 두고, Worker 자신은 즉시 pool로 복귀한다. Worker가 이 연결에 매여 있던 시간은 딱 Step 9~12, 요청 처리 시간뿐.

Connection 위치: 다시 Poller 감시 목록 — 다음 요청이 오면 Step 6부터 반복
BIO와의 핵심 차이 BIO의 Worker는 Step 4부터 연결이 끊길 때까지 붙잡혀 있었다. NIO의 Worker는 Step 9~12만 — idle 비용은 전부 Poller(소수 스레드)가 흡수한다.

Chapter 4

"생성만 되어 있고 노는 Worker"의 정체

?
Worker (min-spare) take() 호출한 채 블로킹 대기 작업 큐

스레드 객체와 OS 스레드 자체는 이미 만들어져 있지만, 큐에서 take()를 호출한 채 잠들어 있다. 이 상태에서는:

  • 소켓에서 데이터를 읽지 않음
  • CPU 연산을 하지 않음
  • 그냥 "일이 들어오면 즉시 깨어날 수 있는" 상태로만 존재
깨어나는 유일한 순간: Poller가 알림을 큐에 넣을 때 — 그때 비로소 소켓 읽기, Application 호출, 응답 쓰기를 시작
Chapter 5

"던진다"의 정확한 의미 — 데이터가 아니라 알림

Poller가 Worker 큐에 "던지는" 건 클라이언트가 보낸 실제 데이터가 아니라, "이 소켓 처리 가능"이라는 알림 객체 하나다. 아래 세 흐름은 완전히 다른 층의 얘기라서 섞어서 보면 헷갈린다.

실제 데이터

클라이언트가 보낸 바이트는 네트워크를 지나 OS 커널의 소켓 수신 버퍼에 쌓인다. Poller/Worker 코드가 관여하기 전, OS가 알아서 처리.

알림

Poller가 던지는 것 — 데이터 내용은 안 건드리고, "이 소켓에 읽을 게 쌓였다"는 신호만 JVM 내부 큐에 넣는다.

진짜 읽기

Worker가 큐에서 알림을 꺼낸 뒤 socket.read()를 호출하는 바로 그 순간에만 실제 데이터가 커널에서 JVM으로 넘어온다.

전체 순서가 궁금하면 Chapter 2의 NIO 탭(Step 6~12), 그리고 fd 개념까지 합친 최종판은 Chapter 10을 보면 된다.
Chapter 6

TCP는 stateful, stateless인 건 HTTP

TCP — stateful

SYN/ACK로 연결을 맺는 순간부터 순서 번호(sequence number), 수신 윈도우 크기 같은 상태를 계속 추적해야 패킷 순서 보장과 재전송이 가능하다. 연결(소켓) 자체는 상태 덩어리다.

HTTP — stateless

그 위에 얹힌 애플리케이션 레벨 얘기다. "서버가 이전 요청을 기억하지 않는다"는 뜻일 뿐, 연결 자체의 상태 관리와는 다른 층이다.

keep-alive의 진짜 목적 연결을 일부러 길게 유지하는 최적화다. 요청마다 TCP(+HTTPS면 TLS) handshake를 반복하면 비용이 크기 때문에, 한 번 연결하면 여러 요청을 재사용하도록 설계된 것. 그래서 연결이 "찰나"가 아니라 수 초~수십 분까지 열려있을 수 있고, 그 유휴 구간의 비용을 누가 떠안느냐가 BIO/NIO 모델 차이의 핵심이었다 (Worker가 떠안던 걸 Poller로 옮김).

Chapter 9

Connection 은 실제로 어디에 저장이 되는가?

Acceptor의 등록 시 사용하는 Queue는 연결을 전달하기만 한다 ( 연결 정보를 보관하진 않음 ). Poller가 큐에서 꺼내는 순간 큐 항목은 사라진다. 실제로 "연결이 유지되고 있다"는 상태는 두 군데에 저장된다.

OS 커널 — TCP 스택(TCB)

연결을 맺는 순간부터 커널이 순서 번호·윈도우 크기·소켓 버퍼 같은 프로토콜 상태를 계속 들고 있다. Acceptor/Poller/Worker와 무관하게 커널이 관리.

Poller — Selector 등록 목록

channel.register(selector, OP_READ, attachment)를 호출하는 순간 SelectionKey 집합에 이 소켓이 추가된다. Tomcat이 버퍼·HTTP 파싱 상태 같은 부가 정보도 attachment()로 같이 매단다.

1
Acceptor accept() 후 큐에 잠깐 넣음 등록 큐

전달 대기일 뿐, 아직 저장이 아니다.

2
Poller register() 호출 SelectionKey 집합

이 순간이 "저장". 이후 epoll_wait() 호출마다 이 소켓도 같이 감시된다.

Connection 위치: 커널 TCB + Selector 등록 목록
연결 유지 = 정보 저장 뭔가 계속 능동적으로 작업하는 게 아니라, 그 소켓을 다시 쓸 수 있게 해주는 메타데이터가 메모리(커널 TCB + Selector 등록 목록)에 계속 남아있다는 뜻이다.

소켓의 실체는 어디에 — fd와 SocketChannel

"커널에도 저장하고 Tomcat에도 저장한다"는 이중 저장이 아니라 역할 분담이다. 소켓의 본체는 항상 커널에 있고, Tomcat(JVM)이 들고 있는 건 그 본체를 가리키는 참조다.

커널 — 소켓의 본체

TCB(순서 번호·윈도우 크기)와 수신/송신 버퍼. 커널 밖으로 절대 나오지 않는다.

Tomcat(JVM) — 리모컨

accept()가 리턴될 때 커널이 발급한 fd(파일 디스크립터, 그냥 정수 번호)를 감싼 SocketChannel 객체. 내용물은 fd 번호 + Tomcat 용도의 부가 상태(버퍼, HTTP 파싱 진행 상황)뿐.

요청이 도착했을 때 실제로 일어나는 일

1
클라이언트 요청 바이트 커널 수신 버퍼

커널이 그 소켓의 수신 버퍼에 쌓고, 해당 fd를 "readable"로 표시한다.

2
Poller epoll_wait(감시 중인 fd 목록) OS 커널

커널이 "3번 fd가 readable"이라고 번호로만 응답한다.

3
Poller fd 3번으로 기존 참조 조회 감시 목록

fd 3번에 매달아뒀던 기존 SocketChannel을 찾는다 — 새로 만들지 않는다. Socket 객체가 만들어지는 순간은 accept() 때 딱 한 번이고, 이후로는 계속 그 참조를 재사용.

4
Worker socket.read() = 시스템 콜 커널 수신 버퍼

"3번 fd 버퍼 내용 달라"는 요청 -> 커널이 버퍼 내용을 JVM 메모리로 복사해 준다.

데이터: 커널에서 JVM으로 복사됨 — 소켓 본체는 여전히 커널에
두 가지 오해 정리 1. "polling 후 Connection 정보를 읽어서 Socket을 만드나?" — 아니다. accept 때 만든 참조를 fd 번호로 다시 찾아 쓴다.
2. "OS에서 Socket을 들고 가나?" — 아니다. 소켓 본체는 커널을 떠나지 않고, 데이터만 read() 시스템 콜로 복사되어 나온다. 비유하면 금고(커널의 소켓 본체)는 은행에 있고, Tomcat은 금고 열쇠 번호(fd)만 들고 있는 것이다.

등록은 한 번이 아니라 요청 사이클마다 반복

이 등록은 연결 전체 수명 동안 딱 한 번이 아니라, 요청 하나가 끝날 때마다 해제와 재등록을 반복한다.

1
초기 등록 register() 최초 1회 감시 목록
2
요청 처리 시작 감시 목록에서 잠깐 제외 처리 중엔 감시 불필요
3
처리 완료, Worker 반납 다시 register() 감시 목록에 재등록
(idle 구간, Poller가 계속 감시) -> 다음 요청 도착 -> 다시 제외 -> 처리 -> 재등록 ... 연결이 끊길 때까지 반복.
Chapter 2 NIO 탭의 마지막 단계("다시 Poller의 감시 대상으로 복귀")가 바로 이 재등록이다.
Chapter 10

최종 통합 순서 — 전체 대화 정리

"요청"과 "데이터"는 다른 게 아니다 요청 자체가 곧 데이터(바이트)다. GET /index.html HTTP/1.1... 같은 바이트를 커널/Poller 입장에서는 그냥 "읽을 게 생겼다"로만 인식하고, 그걸 "이건 GET 요청이다"로 해석하는 건 나중에 Worker가 read() 후 HTTP 파싱할 때 일어난다. 이 연결 위로 클라이언트가 보내는 건 항상 HTTP 요청뿐이므로, "요청이 온다"와 "데이터가 온다"는 같은 사건을 가리키는 두 표현이다.

fd 개념까지 합친 최종 스토리보드

1
클라이언트 TCP 3-way handshake OS 커널

커널이 전담, Tomcat은 모른다. 완성된 연결은 accept queue(backlog = acceptCount)에 쌓인다.

연결 위치: 커널 accept queue
2
Acceptor accept()로 꺼냄 (pull) — fd 발급 accept queue

호출당하는 게 아니라 큐 앞에서 대기하다 꺼내간다. 이때 커널이 fd를 발급하고, JVM은 그걸 감싼 SocketChannel을 딱 한 번 만든다. 곧바로 Poller에게 넘김 — 아직 저장 아님, 전달만.

연결 위치: Poller 등록 큐
3
Poller register() = 저장 감시 목록

이 순간 저장(메타정보 등록) — Selector의 감시 목록에 이 연결이 추가된다.

연결 위치: 커널 TCB + Poller 감시 목록
( idle 구간 ) Poller는 이 연결을 포함해 다른 수천 개도 같이 계속 감시만 한다 — 아직 아무 일도 일어나지 않음
4
클라이언트 실제 요청 (HTTP 바이트) 커널 수신 버퍼

바이트가 커널 버퍼에 쌓이고, 이 소켓(fd)이 "readable" 상태가 된다.

데이터 위치: 커널 수신 버퍼
5
Poller epoll_wait()가 감지, 알림 투입 Worker 작업 큐

커널이 "이 fd readable"이라고 번호로 알려주면, Poller는 기존 SocketChannel을 찾아 "처리 가능" 알림을 작업 큐에 넣는다. 데이터는 안 건드린다.

알림: Worker 작업 큐 / 데이터: 여전히 커널 버퍼
6
Worker take() -> read() -> 파싱 -> 실행 커널 수신 버퍼

대기하던 Worker가 알림을 스스로 가져가고, socket.read() 시스템 콜로 커널 버퍼의 바이트를 JVM으로 복사해 온다. HTTP 파싱("이건 GET이다"가 여기서 판명) 후 Application(컨트롤러) 실행.

데이터 위치: Worker 메모리
7
Worker socket.write() — 직접 전송 클라이언트

응답을 Worker가 직접 쓴다. Poller를 거치지 않는다.

응답: 클라이언트 도착
8
Worker 재등록 후 pool 복귀 Poller 감시 목록

keep-alive면 소켓을 감시 목록에 재등록하고 Worker는 즉시 반납된다. 새 요청이 오면 Step 4부터 반복.

연결 위치: 다시 Poller 감시 목록
TCP 연결이 끊기면 — Poller의 감시 목록에서 이 소켓 제거 + OS 커널의 TCB도 함께 폐기 (둘 다 정리됨)

한 줄 정리

  • C10K 문제 -> "기다리기"와 "일하기"를 분리해서 해결
  • Acceptor가 하는 일 자체는 옛날(BIO)과 동일 — 바뀐 건 넘기는 대상(Worker 큐 -> Poller 등록 큐)
  • handshake는 커널이 전담 — Acceptor는 호출당하는 게 아니라 accept queue 앞에서 대기하다 꺼내간다(pull)
  • 큐는 3개, 대기자도 3명: (커널 accept queue -> Acceptor), (등록 큐 -> Poller), (작업 큐 -> Worker) — 전부 같은 Producer-Consumer 패턴
  • Poller는 특정 Worker를 지목/할당하지 않는다 — 대기 중인 Worker가 스스로 가져감(pull 방식)
  • Worker는 항상 "일이 확정된 순간에만" 소환되고, idle 비용은 전부 Poller(저렴)가 흡수
  • "던진다"는 건 데이터가 아니라 알림 — 실제 데이터는 Worker의 read()/write() 두 순간에만 움직인다
  • 응답은 Worker가 socket.write()로 직접 쓴다 — Poller는 데이터를 한 바이트도 만지지 않는다
  • TCP는 stateful, stateless는 HTTP의 특성 — keep-alive는 연결을 일부러 길게 유지하는 최적화
  • 정적 페이지는 다운로드 후 유휴 타임아웃으로 조용히 끊겼다가 필요할 때 새로 맺어진다
  • 연결 유지는 Acceptor 큐가 아니라 커널 TCB + Poller(Selector)의 등록 목록에 저장되며, 요청 사이클마다 해제/재등록을 반복한다
  • 소켓 본체는 커널에 있고 Tomcat이 가진 건 fd를 감싼 참조(SocketChannel)뿐 — Socket 생성은 accept() 때 1회, read()는 커널 버퍼를 JVM 메모리로 복사하는 시스템 콜이다
  • "요청이 온다"와 "데이터가 온다"는 같은 사건이다 — 요청 자체가 곧 바이트이고, "이건 GET 요청이다"라는 해석은 Worker가 파싱할 때 비로소 일어난다
