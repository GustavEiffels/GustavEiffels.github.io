동시성 정리 — 낙관적 락 / 비관적 락 / 분산락

프로젝트 하다 겪은 동시성 문제를 정리한 개인 노트. 뒤에 계속 이어서 작성 예정.

문제

왜 동시성 문제가 생기는가

프로젝트를 하다보면 동시성에 대해서 생각해야한다. 여러 인스턴스나 스레드에서 동일한 자원을 동시에 수정하려고 할 때 많은 문제점이 발생하기 때문이다.

문제가 발생하는 이유

문제가 되는 건 당연하다. 하나의 자원을 동시에 수행하려다 보니 몇 개의 시도가 누락되는 경우가 많이 발생하기 때문이다.

특정 자원(초기값 5)에 1을 빼는 작업을 5번 요청했다고 가정했을 때, 동시에 요청하다 보니 어느 요청들에서는 자원의 값이 4인 경우가 생기는 것이다.

Lost Update 결과 
작업 1 : A = 5  -> 5 - 1 = 4
작업 2 : A = 4  -> 4 - 1 = 3
작업 3 : A = 4  -> 4 - 1 = 3
...
작업 끝 : A = 1

작업 2와 작업 3이 서로 다른 시점에 실행됐지만, 둘 다 작업 1이 써놓은 A=4를 읽은 뒤 각자 4-1=3을 계산해서 그대로 덮어쓴다. 결과적으로 두 번의 -1 요청이 있었는데 자원 값은 한 번만 줄어든 것처럼 보이게 된다. 이런 일이 발생하면 우리는 이 데이터에 대해서 믿을 수 없게 된다.

나는 개발자이므로 보통 이런 경우를 막아야 하는 자원의 경우 DB 데이터가 주가 된다. 그래서 동시성을 위해서 사용하는 방법에 대해서 정리해보자.

1

스레드 간 동시성 — synchronized / ReentrantLock

DB나 여러 서버로 넘어가기 전에, 같은 프로세스 안에서 여러 스레드가 부딪히는 경우부터 봐야 한다. 자바에서는 이 문제를 synchronized 또는 ReentrantLock으로 막는다.

synchronized vs ReentrantLock

둘 다 임계 구역(critical section)에 한 번에 하나의 스레드만 들어가게 막는 도구다. synchronized는 블록을 벗어나면 JVM이 알아서 락을 풀어주고, ReentrantLock은 lock()/unlock()을 직접 호출해야 하는 대신 tryLock(), 공정성(fair) 옵션, 여러 개의 Condition 같은 걸 더 쓸 수 있다.

tryLock() — 실제 프로젝트에서 이렇게 썼다

프로젝트에서 주기적으로 도는 스케줄러가 있는데, 주기가 짧다 보니 이전 작업이 아직 안 끝났는데 다음 주기가 시작되는 경우가 생겼다. 이때 lock()으로 그냥 기다리게 만들면, 못 끝낸 작업이 계속 쌓여서 나중엔 스케줄이 통째로 밀리는 문제가 된다. 그래서 tryLock()을 써서, 이미 누가 락을 선점하고 있으면 이번 주기는 대기하지 않고 그냥 실행을 취소(skip)하도록 만들었다. 다음 주기에 다시 시도하면 되니까 굳이 기다릴 이유가 없다는 판단이었다.

tick 2가 왔을 때 작업 1이 아직 락을 들고 있어서 tryLock()이 즉시 false를 리턴하고, 이번 주기는 대기 없이 취소된다. tick 3에는 작업 1이 이미 끝났으니 tryLock()이 바로 성공한다. lock()이었다면 tick 2도 결국 실행은 됐겠지만, 대기하는 동안 스레드가 계속 묶여있었을 것이다.

private final ReentrantLock lock = new ReentrantLock();

@Scheduled(fixedDelay = 5000) // 5초마다 도는 스케줄
public void runPeriodicJob() {
    if (!lock.tryLock()) {
        // 이미 이전 주기가 실행 중 -> 대기하지 않고 이번 주기는 취소
        log.info("이전 작업이 아직 실행 중, 이번 주기는 skip");
        return;
    }
    try {
        doHeavyWork();
    } finally {
        lock.unlock();
    }
}
lock = threading.Lock()

def run_periodic_job():
    if not lock.acquire(blocking=False):
        # 이미 이전 주기가 실행 중 -> 대기하지 않고 이번 주기는 취소
        logger.info("이전 작업이 아직 실행 중, 이번 주기는 skip")
        return
    try:
        do_heavy_work()
    finally:
        lock.release()

ConcurrentHashMap도 결국 이 얘기다

동시성 컬렉션인 ConcurrentHashMap도 내부적으로는 락(그리고 락이 아닌 것들)을 조합해서 쓴다. 어떻게 조합했는지 보면 왜 지금 상황에 맞는 락을 골라 써야 하는지 감이 온다.

Java 7 — 세그먼트(Segment) 단위 락

배열 전체를 기본 16개의 Segment로 나누고, Segment 클래스 자체가 ReentrantLock을 상속받는다. put/remove 할 때 해당 key가 속한 세그먼트 하나만 잠그면 되고, 나머지 15개는 동시에 다른 스레드가 건드릴 수 있었다. 문제는 세그먼트 개수가 생성 시점에 고정된다는 것 — 세그먼트 수보다 많은 스레드가 몰리면 결국 같은 세그먼트를 두고 다시 경합이 생긴다.

바로 아래 Java 8 버킷 다이어그램과 비교해보면, "묶어서 하나로 잠그는 것"과 "버킷 하나하나를 따로 잠그는 것"의 차이가 그림으로 바로 보인다.

Java 8 — 버킷(bin) 단위 락

Segment를 아예 없애고, 해시 버킷(테이블의 각 슬롯) 단위로 훨씬 잘게 쪼갰다. 버킷이 비어있으면 락 없이 바로 값을 넣고, 이미 값이 있는 버킷이라면 그 버킷 하나만 synchronized로 잠근다. 그래서 같은 순간에도 서로 다른 버킷끼리는 아무 영향 없이 동시에 읽고 쓸 수 있다.

참고로 한 버킷의 체인 길이가 8개를 넘고 테이블 전체 크기가 64 이상이면, 연결리스트를 레드-블랙 트리로 바꿔서(treeify) 최악의 경우에도 조회가 O(log n)에 그치게 만든다.

Java 8에서 ReentrantLock을 뺀 이유 세그먼트(16개 고정)보다 버킷 단위가 훨씬 잘게 쪼개져서 경합이 줄고, synchronized의 JIT 최적화(biased/lightweight locking)가 좋아져서 굳이 ReentrantLock의 오버헤드를 감수할 필요가 없어졌다.

get()은 아예 락을 안 잡는다

읽기(get)는 Java 7이든 8이든 원래 락을 잡지 않는다. 대신 노드의 val, next 필드를 volatile로 선언해서, 다른 스레드가 쓴 값이 happens-before 규칙에 따라 바로 보이도록 보장한다. 그래서 쓰기가 진행 중인 버킷을 읽더라도 대기하지 않고, 그 시점에 반영된 가장 최근 값을 그대로 읽어간다.

size()는 카운터 하나로 안 센다

전체 크기를 AtomicLong 하나로 세면, 모든 스레드의 put/remove가 결국 그 카운터 하나를 두고 경합하게 된다. 그래서 ConcurrentHashMap은 baseCount와 CounterCell[](요즘의 LongAdder와 같은 아이디어)로 카운트를 여러 칸에 분산시켜두고, size()를 호출할 때만 이 칸들을 다 더해서 리턴한다. 쓰기는 스레드마다 자기 칸에 CAS로 더하기만 하면 되니 경합이 훨씬 줄어든다.

실제 프로젝트에서 이렇게 썼다

WebSocket으로 실시간 데이터를 받는 콜백 스레드와, HTTP 요청을 처리하는 스레드가 동시에 같은 구독 목록을 건드리는 경우가 있었다. 구독 추가/조회가 서로 다른 스레드에서 동시에 일어나도 별도로 synchronized를 걸 필요 없이 ConcurrentHashMap(그리고 newKeySet()으로 만든 concurrent set)에 맡겨서 안전하게 공유했다.

SubscriptionRegistry.java 
private final Set<String> subscribedTickers = ConcurrentHashMap.newKeySet();
private final Map<String, String> tickerExchangeMap = new ConcurrentHashMap<>();

// HTTP 요청 스레드에서 호출
public void subscribe(String ticker, String exchangeCode) {
    if (subscribedTickers.contains(ticker)) return;
    subscribedTickers.add(ticker);
    tickerExchangeMap.put(ticker, exchangeCode);
}

// WebSocket 콜백 스레드에서 동시에 호출됨
public Set<String> getSubscribedTickers() {
    return Set.copyOf(subscribedTickers);
}
DB 락과 같은 층위의 도구 — DB 자체는 아니다 ConcurrentHashMap은 DB의 낙관적/비관적 락과 같은 층위, 즉 "동시성을 어떻게 보장하냐"의 방법 중 하나일 뿐이다. DB가 락 말고 추가로 해주는 것들 — 영속성(재시작해도 안 사라짐), 인스턴스 간 공유, 여러 key를 묶은 트랜잭션 — 은 여기 없다. 메모리에만 있어서 재시작하면 사라지고, 서버 인스턴스마다 따로 논다.
2

낙관적 락 (Optimistic Lock)

DB 락의 종류 중 하나이다. 동시성을 제어할 대상 테이블에 version이라는 컬럼을 두어 언제 수정이 됐는지 확인하여 재시도 등을 할 수 있도록 한 방식이다.

예를 들면:

version 충돌 감지 
A : version 1  -> 작업하려고 보니까 version 이 1이였음
A : version 2  -> 작업을 수행하고 업데이트를 하려고 보니 version 이 2가 됨
즉, 누군가 내가 업데이트 완료하기 전에 값을 변경함

이렇게 구별하는 것이다. 보통 이런 경우 어떻게 할 것인지 개발자에게 위임하는 게 가능하다. 다시 version 2의 값을 가지고 작업을 다시 수행할 것인지 아니면 적용하지 않을 것인지 말이다.

충돌 = 데이터 오염이 아니다 낙관적 락은 충돌이 나면 항상 감지해서 예외를 던지기 때문에, 잘못된 값이 조용히 저장되는 일은 없다. 다만 충돌난 요청을 재시도할지 말지는 개발자의 몫이다.

낙관적 락은 보통 사용자 경합이 많이 없는 경우에 많이 쓰이는 편이다.

@Entity
public class Account {
    @Id
    private Long id;
    private Long balance;

    @Version
    private Long version; // 낙관적 락 컬럼
}

@Transactional
public void withdraw(Long id, Long amount) {
    Account account = accountRepository.findById(id).orElseThrow();
    account.setBalance(account.getBalance() - amount);
    accountRepository.save(account);
    // UPDATE ... WHERE id=? AND version=?
    // 영향받은 row 가 0개면 OptimisticLockException 발생
}
class Account(Base):
    __tablename__ = "account"
    id = Column(Integer, primary_key=True)
    balance = Column(BigInteger)
    version_id = Column(Integer, nullable=False)

    __mapper_args__ = {
        "version_id_col": version_id  # 낙관적 락 컬럼
    }

def withdraw(session: Session, account_id: int, amount: int):
    account = session.get(Account, account_id)
    account.balance -= amount
    try:
        session.commit()
    except StaleDataError:
        # 다른 트랜잭션이 먼저 값을 바꿈 -> 재시도 여부는 개발자 몫
        session.rollback()
        raise

비관적 락 (Pessimistic Lock)

DB 락의 종류 중 하나이다. 앞의 낙관적 락과 다르게 모든 요청이 특정 행에 대해 적용이 된다. 특정 값에 대해서 여러 사람들이 요청하면 우리가 흔히 아는 lock을 걸어 해당 작업에 대해 오직 하나의 요청만 수행하게 되며 나머지 요청들은 기다리게 된다. 이때 다른 요청들은 LOCK을 획득할 때까지 기다려야 한다.

여러 요청이 와도 정상적으로 처리가 되지만, Lock 획득 시까지 기다려야 하며 DB 락이기 때문에 그 기다리는 시간만큼 DB Connection이 잡혀있게 된다. 그리고 하나의 트랜잭션에 다수의 비관적 락을 사용하는 경우 자칫 잘못하면 Dead Lock에 빠질 수 있다.

요청 2, 3은 요청 1이 트랜잭션을 끝내고 Lock을 반납할 때까지 DB Connection을 잡은 채로 순서를 기다린다. 요청이 몰릴수록 대기 줄이 길어지고, 그만큼 커넥션 풀이 소모된다.

비용 락 대기 = DB Connection 점유 시간. 대기가 길어질수록 커넥션 풀 전체가 영향을 받는다. 
public interface AccountRepository extends JpaRepository<Account, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") Long id);
    // SELECT ... FOR UPDATE 로 행 잠금, 다른 트랜잭션은 대기
}

@Transactional
public void withdraw(Long id, Long amount) {
    Account account = accountRepository.findByIdForUpdate(id).orElseThrow();
    account.setBalance(account.getBalance() - amount);
} // 트랜잭션 종료 시 락 해제
def withdraw(session, account_id: int, amount: int):
    row = session.execute(
        text("SELECT balance FROM account WHERE id = :id FOR UPDATE"),
        {"id": account_id}
    ).one()
    # 여기서 다른 트랜잭션은 이 행에 대해 대기함

    new_balance = row.balance - amount
    session.execute(
        text("UPDATE account SET balance = :b WHERE id = :id"),
        {"b": new_balance, "id": account_id}
    )
    session.commit()  # 커밋 시점에 락 해제

분산락 (Distributed Lock)

분산환경에서 사용 가능해서 분산락이다. 보통 개발자들이 Lock을 걸면 위와 같은 DB 락을 많이 사용하며, DB 락만 걸어도 충분할 것 같다.

하지만 Transaction 범위가 길거나, 배치 등으로 다수의 row를 수정하거나, 하나의 Transaction에 외부 API 호출 부분이 포함되어 있는 경우 DB 락으로는 비효율적인 부분이 많다.

위의 경우 DB 락을 사용한다면 그만큼 DB Connection을 오래 점유하게 되어 커넥션 풀이 고갈될 수 있다. 반면 분산 락의 경우 각각의 인스턴스가 접근 가능한 저장소에 key를 가지는 형식으로 lock을 획득하여 운영되기 때문에 DB Connection 유지로 인한 커넥션 고갈을 막을 수 있다.

Instance A만 SETNX(없을 때만 설정)로 key 선점에 성공해서 락을 갖고, B/C는 같은 key에 대한 시도가 실패해서 재시도하거나 포기한다. A가 작업을 끝내고 key를 지우거나(TTL 만료) 하면 그때 다른 인스턴스가 다시 시도해서 획득할 수 있다.

RLock lock = redissonClient.getLock("lock:account:" + accountId);
boolean acquired = false;
try {
    acquired = lock.tryLock(3, 10, TimeUnit.SECONDS); // 대기 3초, 점유 TTL 10초
    if (!acquired) {
        throw new IllegalStateException("락 획득 실패");
    }
    // critical section: 외부 API 호출 + DB 갱신 등
    accountService.applyWithdraw(accountId, amount);
} finally {
    if (acquired) {
        lock.unlock();
    }
}
def acquire_lock(key: str, ttl_ms: int = 10000) -> str | None:
    token = str(uuid.uuid4())
    ok = r.set(f"lock:{key}", token, nx=True, px=ttl_ms)  # 없을 때만 설정 + TTL
    return token if ok else None

def release_lock(key: str, token: str):
    script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end"
    r.eval(script, 1, f"lock:{key}", token)  # 내가 잡은 락만 지움 (fencing)

def withdraw(account_id: int, amount: int):
    token = acquire_lock(f"account:{account_id}")
    if not token:
        raise RuntimeError("락 획득 실패")
    try:
        apply_withdraw(account_id, amount)
    finally:
        release_lock(f"account:{account_id}", token)

락은 메서드가 아니라 row(자원) 단위로 건다

위 코드에서 getLock("lock:account:" + accountId)를 보면, key 안에 accountId가 들어가 있다. 이게 핵심이다 — 메서드 이름으로 잠그는 게 아니라, 그 메서드가 실제로 건드리는 자원의 식별자로 잠근다. 만약 getLock("lock:withdraw")처럼 메서드 단위로 잠갔다면, 계좌 1번 출금과 계좌 2번 출금이 서로 아무 관계가 없는데도 같은 락을 두고 경합하게 된다.

DB 비관적 락과 같은 원리 SELECT ... FOR UPDATE WHERE id = ?도 테이블 전체가 아니라 특정 row만 잠근다. 분산락도 마찬가지다 — 락의 범위는 "실제로 충돌할 수 있는 단위"에 맞춰야 한다. 그보다 넓게 잡으면 서로 무관한 요청들이 이유 없이 줄을 서게 되고, 처리량만 떨어진다.

그럼 언제 일부러 넓게(메서드/테이블 단위로) 잠그는가 — 보호하려는 불변조건이 row 하나가 아니라 여러 row에 걸쳐 있을 때다. 예를 들어 예약된 작업들을 주기적으로 정리하는 배치 스케줄러가 있고, 동시에 다른 스케줄러가 같은 테이블에 새 예약을 대량으로 써넣는 상황이라면, 이 둘이 지키려는 건 특정 row 하나가 아니라 테이블 전체의 일관된 상태다. 이런 경우엔 row 단위로 쪼개는 게 오히려 의미가 없고, 의도적으로 넓은 범위(예: lock:scheduler)로 잠가야 한다.

정리하면: 기본값은 row/엔티티 단위(key에 식별자 포함)로 좁게 잡고, 여러 row를 한꺼번에 건드리는 배치성 작업일 때만 의도적으로 넓힌다.

분산락이 이중 실행되는 이유 — TTL 때문

락을 잡은 인스턴스가 TTL이 끝나기 전에 작업을 못 끝내는 경우가 진짜 위험한 시나리오다. 꼭 죽지 않아도, GC pause나 네트워크 지연으로 "잠깐 멈췄다 깨어나는 것"만으로도 똑같이 터진다.

A는 T=0에 정상적으로 락을 획득했지만 GC pause로 멈춰있는 동안 T=10에 TTL이 자동으로 만료된다. T=11에 B가 같은 락을 정상적으로 획득해서 작업을 시작하고, T=15에 A가 깨어나 "나는 아직 락을 갖고 있다"고 착각한 채로 마저 작업을 수행한다. 결과적으로 A와 B가 동시에 같은 자원을 건드리게 된다 — 분산락을 쓴 이유 자체가 무너지는 상황이다.

TTL을 없앨 수도 없다 TTL이 없으면 A가 진짜로 죽었을 때 락이 영원히 안 풀린다(누구도 다음 작업을 못 함). TTL이 있으면 방금 본 것처럼 "너무 일찍 풀려서 이중 실행"이 생길 수 있다. 둘 다 위험하다는 게 분산락의 근본적인 딜레마다.

TTL로 인한 이중 실행 방지 — Fencing Token

락 자체가 이 문제를 막아주는 게 아니라, 자원 쪽에서 이중 실행을 걸러내는 방식이다. 락을 줄 때마다 계속 증가하는 번호(token)를 같이 주고, 실제 자원(DB 등)에 쓸 때 이 번호도 같이 보내서 "마지막으로 처리한 번호보다 낮은 건 거부"하도록 만든다. A가 33번, (A가 멈춘 사이) B가 34번을 받았다면, T=15에 깨어난 A가 33번 토큰으로 쓰려고 해도 자원 쪽은 이미 B의 34번을 처리한 뒤라 A의 쓰기를 거부한다.

중요한 건, 이중으로 락을 잡는 것 자체는 못 막아도 이중으로 실제 쓰기가 반영되는 것은 막는다는 점이다. 다만 이건 자원 쪽이 토큰 비교 로직을 직접 구현해줘야 동작하는 거라, 락 라이브러리만 바꾼다고 공짜로 되는 게 아니다.

public class AccountRepository {
    private final Map<Long, Long> lastFencingToken = new ConcurrentHashMap<>();

    public void applyWithdraw(Long accountId, long fencingToken, long amount) {
        Long lastToken = lastFencingToken.get(accountId);
        if (lastToken != null && fencingToken <= lastToken) {
            // 이미 더 최신 토큰이 처리됨 -> 오래된 락에서 온 요청, 거부
            throw new StaleLockException("fencing token too old: " + fencingToken);
        }
        lastFencingToken.put(accountId, fencingToken);
        doWithdraw(accountId, amount);
    }
}

// 락 획득 시 fencing token 도 같이 발급 (Redis INCR로 단조 증가)
long fencingToken = redisson.getAtomicLong("fencing:account:" + accountId).incrementAndGet();
accountRepository.applyWithdraw(accountId, fencingToken, amount);
last_fencing_token: dict[int, int] = {}

def apply_withdraw(account_id: int, fencing_token: int, amount: int):
    last_token = last_fencing_token.get(account_id)
    if last_token is not None and fencing_token <= last_token:
        # 이미 더 최신 토큰이 처리됨 -> 오래된 락에서 온 요청, 거부
        raise StaleLockError(f"fencing token too old: {fencing_token}")
    last_fencing_token[account_id] = fencing_token
    do_withdraw(account_id, amount)

# 락 획득 시 fencing token도 같이 발급 (Redis INCR로 단조 증가)
fencing_token = r.incr(f"fencing:account:{account_id}")
apply_withdraw(account_id, fencing_token, amount)
그 외 완화 방법 하트비트/lease 갱신 — 작업이 오래 걸리면 살아있는 동안 주기적으로 TTL을 연장(Redisson의 watchdog이 자동으로 해줌). 작업 자체를 멱등하게 설계하면 이중 실행이 나도 결과가 같아서 훨씬 덜 위험해진다.

위 예시의 허점 — 비교 상태도 공유돼야 한다

위 AccountRepository 예시의 lastFencingToken은 ConcurrentHashMap, 즉 JVM 프로세스 메모리 안에 있다. 그런데 막으려는 경합은 서로 다른 인스턴스 A와 B 사이의 경합이다 — A와 B는 각자 다른 JVM이라 자기만의 lastFencingToken Map을 따로 갖는다. A가 뒤늦게 33번 토큰으로 applyWithdraw를 호출해도 A의 로컬 Map엔 B가 처리한 34번 기록이 아예 없으니 거부되지 않는다. "마지막 토큰"이라는 비교 기준 자체도 모든 인스턴스가 함께 보는 공유 저장소에 있어야 fencing이 실제로 동작한다.

그래서 실전에서는 DB 컬럼으로 구현한다 메모리 Map은 개념 설명용 예시로만 유효하다. 여러 인스턴스를 실제로 방어하려면 "마지막 토큰"을 DB row에 저장하고, 그 비교와 갱신을 하나의 원자적 UPDATE 문으로 처리해야 한다.

실전 구현 — DB 컬럼 기반 CAS

토큰 비교는 애플리케이션 코드의 if문이 아니라 DB의 WHERE 절로 원자적으로 처리한다. 비교(체크)와 갱신(쓰기)이 한 문장이라 그 사이에 다른 트랜잭션이 끼어들 틈이 없다.

fencing token CAS 
UPDATE account
SET balance = :newBalance, last_fencing_token = :myToken
WHERE id = :accountId
  AND last_fencing_token < :myToken;

-- affected rows == 1 -> 내가 최신, 반영 성공
-- affected rows == 0 -> 이미 더 큰 토큰이 다녀감, 나는 stale -> 무시

이 체크와 실제 잔액 반영이 같은 UPDATE 문(=같은 트랜잭션)이라는 게 핵심이다. "먼저 토큰만 확인하고 커밋 → 나중에 잔액을 반영"처럼 두 단계로 쪼개면, 체크를 통과한 직후부터 잔액 반영이 끝날 때까지가 다시 무방비 구간이 된다 — fencing token으로 막으려던 것과 똑같은 종류의 틈이 재발한다.

토큰 발급용 key에는 TTL을 걸면 안 된다

락 key(lock:account:1)는 TTL이 있어야 하지만, 토큰 카운터 key(fencing:account:1)는 TTL 없이 영구히 유지돼야 한다. 카운터가 중간에 만료돼 리셋되면 그 뒤 발급되는 토큰이 DB에 이미 저장된 값보다 작아지고, 이후 정상 요청까지 전부 "나보다 큰 토큰이 이미 있다"며 영원히 거부당하는 가용성 장애로 이어진다.

핵심 통찰 — "원래 락을 잡았던 쪽(A)이 이겨야 하는가?" 아니다. TTL이 끝나는 순간 A는 시스템 규칙상 이미 자격을 잃은 것이고, 그 이후엔 B가 정당한 새 소유자다. A가 진짜 살아있는지 죽었는지는 시스템도 B도 판단할 수 없기 때문에, "기다렸다가 만료되면 다음 사람에게 넘긴다"는 규칙 자체가 최선이다. Fencing token은 A를 이기게 해주는 장치가 아니라, 이미 자격을 잃은 A가 뒤늦게 깨어나 B의 정당한 작업 결과를 덮어쓰지 못하게 막아주는 장치일 뿐이다.
