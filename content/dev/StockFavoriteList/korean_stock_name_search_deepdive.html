Section 0

🎯 배경 및 목적 — 왜 이 기능을 만들었나

문제 상황

기존 종목 검색은 티커(예: AAPL) 또는 ^접두사 지수만 인식했다. 사용자가 "애플", "테슬라" 같은 한글 종목명을 입력하면 백엔드에 도달하지도 못하고 프론트엔드 정규식 검증 단계에서 즉시 차단되었다.

💡 왜 바꿔야 했는가 종목 즐겨찾기 서비스인데 정작 회사 이름으로 검색이 안 되고 정확한 영문 티커를 외워서 입력해야 했다. 미국주식(ETF 제외)에 대해 한글 종목명 검색을 지원하도록 백엔드에 네이버 금융 자동완성(ac.stock.naver.com) 연동을 추가하고, 프론트엔드 입력 검증을 완화했다.
⚙️ ETF는 왜 대상에서 뺐는가 ETF(SOXL 등)는 사용자가 원래부터 영문 티커로 직접 입력하므로 별도 한글 매핑 대상에서 제외했다. 네이버 자동완성 응답을 category=stock으로 필터링하면 ETF는 자연히 제외되어 별도 예외 처리가 필요 없었다.

설계 결정과 이유 (Design Decisions)

결정이유
자체 한글-ticker 매핑 테이블 대신 네이버 자동완성 API 사용미국 상장 종목 전체에 대한 한글명 매핑을 직접 구축/유지보수하는 비용을 피하고, 네이버가 이미 관리하는 데이터를 재사용
category=stock && nationCode=USA 필터링만으로 ETF 제외사용자가 ETF는 영문 티커로 입력한다고 명시했고, 네이버 응답에서 ETF는 별도 category로 분류되어 추가 로직 없이 자연 제외됨
검색 실패(0건)는 캐싱하지 않음오타 등으로 인한 실패가 캐시에 영구 고정되면 오타를 고쳐도 계속 실패로 보일 위험 방지
alias 캐시 키를 원본 한글 입력값으로 유지동일 한글 재검색 시 네이버 API를 다시 타지 않고 기존 ticker 캐시로 즉시 응답
기존 findStockByTicker 파이프라인(캐시→DB→Yahoo) 재사용한글 검색은 "입력값을 ticker로 정규화"하는 전처리 단계로만 취급, 검색/저장 로직 중복 없이 기존 안정 경로에 합류

📄 infrastructure/stock/external/NaverStockSearchClient.java — /ac 호출부 (신규) 
public NaverExternalDto.AutoCompleteResponse search(String keyword) {
    try {
        return webClient.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/ac")
                        .queryParam("q", keyword)
                        .queryParam("target", "stock")
                        .build())
                .retrieve()
                .bodyToMono(NaverExternalDto.AutoCompleteResponse.class)
                .block();
    } catch (Exception e) {
        log.warn("Naver 종목 검색 실패 (keyword={}): {}", keyword, e.getMessage());
        return null;
    }
}

⚠️ .block()으로 동기 호출하고, 실패 시 예외를 던지지 않고 null을 반환한다 — IndexAndWaterRide와 완전히 동일한 폴백 방식이라 원본과 대조했을 때 사실상 동일 파일이다.

1-2. 이식하며 바뀐 부분 (구조적 차이)

  • IndexAndWaterRide: UsStockSearchRepositoryImpl(필터링) → UsStockSearchService(캐싱)로 책임이 Repository/Service 두 레이어로 분리.
  • stock_favorite_list: StockNameSearchClientImpl 한 클래스가 필터링 + 캐싱을 모두 담당하고, 기존 DDD 레이어링(포트/구현)에 맞춰 재배치.
  • IndexAndWaterRide는 결과가 UsStockCandidateDto(code, name) — 이름까지 보유. stock_favorite_list는 List<String>(ticker만) — 기존 findStockByTicker 파이프라인이 ticker 기준으로 동작하기 때문에 이름은 버린다.

Section 2

🔗 기존 Ticker 검색 로직과의 통합

2-1. 한글 분기 도입 이전의 원래 흐름

StockService.findStockByTicker의 뼈대는 한글 검색을 넣기 전에도 이미 캐시 → DB → 외부 API 3단 파이프라인이었다. 한글 검색은 이 파이프라인 앞에 "입력값을 candidate ticker 목록으로 정규화"하는 단계 하나만 끼워 넣은 것이다.

  • 캐시: StockCacheRepositoryImpl (Caffeine, stockInfoByTicker / stockInfoByName, 10,000건/24일 TTL)
  • DB: StockRepository.findStock(...) (PostgreSQL, StockEntity)
  • 외부 API: StockExternalApiClient.findSymbol(...) → Yahoo Finance → (실패 시) Finnhub fallback

기존 로직(한글 아닌 입력)은 originalInput + ^originalInput(지수 접두사) 두 개를 candidate로 만들고, 외부 API 조회는 원본 1회 호출로 끝났다.

2-2. 실제 소스: 한글 분기와 candidate 결정

📄 domain/stock/StockService.java — findStockByTicker (수정) 
String originalInput = searchDto.ticker();
boolean isKoreanKeyword = containsKorean(originalInput);

// 검색 대상 후보 결정
// - 한글 입력: Naver 자동완성으로 실제 미국주식 ticker 목록으로 변환
// - 그 외: 원본 ticker + ^접두사(지수)
List<String> candidates;
if (isKoreanKeyword) {
    candidates = nameSearchClient.searchUsTickers(originalInput);
    if (candidates.isEmpty()) {
        throw new RuntimeException("존재하지 않은 종목명입니다.");
    }
} else {
    candidates = new ArrayList<>();
    candidates.add(originalInput);
    if (!originalInput.startsWith("^")) {
        candidates.add("^" + originalInput);
    }
}
📄 domain/stock/StockService.java — 외부 API 조회 분기 
// - 한글 검색: 후보(candidate)마다 개별 조회 (Naver가 여러 ticker를 반환할 수 있음)
// - 그 외: 원본 ticker로 1회 조회 (findSymbol이 ^접두사 지수도 함께 병합해 반환)
if (isKoreanKeyword) {
    for (String t : needApiLookup) {
        fromExternal.addAll(externalRepository.findSymbol(t));
    }
} else {
    fromExternal = externalRepository.findSymbol(originalInput);
}

private boolean containsKorean(String input) {
    return input.codePoints().anyMatch(cp -> cp >= 0xAC00 && cp <= 0xD7A3);
}

2-3. 파이프라인 시각화 — 기존 로직 vs 한글 적용 후

회색 라인 = 한글 도입 이전부터 있던 기존 경로 · 파란 라인 = 한글 지원을 위해 새로 갈라진 경로. 두 경로는 candidate 생성과 API 호출 방식만 다르고, 캐시 → DB → 저장 파이프라인은 그대로 공유한다.

2-4. 다중 매치 시나리오와 정렬 로직 부재

IndexAndWaterRide의 TRADEOFFS.md에는 국내 종목명 검색(StockMasterService.search)에 대해 "완전일치 > 접두일치 > 부분일치 > 길이순" 정렬 로직이 문서화되어 있다(예: "SK하이닉스" 입력 시 SK하이닉스 → SK하이닉스레버리지 → Kodex SK하이닉스레버리지 순).

다만 이 정렬 로직은 국내(KRX) 종목명 검색 전용이며, 이번에 이식된 미국주식 Naver /ac 포트에는 애초에 존재하지 않았다. 즉 "정렬 로직이 이식되지 않은" 것이 아니라, 원본부터 미국주식 경로에는 정렬 로직이 없다 — 한 키워드가 여러 ticker에 매칭될 경우 Naver가 반환한 순서를 그대로 candidate 순서로 사용한다.

Section 3

⚡ 성능 개선 여부 확인

결론: 이 기능 자체는 성능 개선이 목적이 아니다. (같은 날 커밋된 "북마크 전환 속도 개선"과는 별개 작업이며 혼동하지 않도록 구분해야 한다.)

다만 아래 두 캐싱 계층 덕분에 반복 검색 비용은 줄어든다:

캐시캐싱 대상효과
koreanStockNameSearch (신규)한글 keyword → ticker 목록동일 한글 검색 재입력 시 Naver API 재호출 없이 즉시 반환
stockInfoByTicker alias (기존 재사용)originalInput(한글 원문) → 결과 ticker의 StockInfoCache한글 검색 성공 이후엔 Naver 호출 자체를 건너뛰고 기존 ticker 캐시로 바로 응답

즉 최초 1회는 Naver API 호출 + 기존 캐시/DB/Yahoo 파이프라인 그대로 타지만, 이후 동일 키워드는 두 계층 중 하나에서 바로 캐시 적중한다. 새로운 병목(순차 호출, N+1 등)은 도입되지 않았다 — candidate가 여러 개인 경우에도 개수가 작고(보통 1~3개), Naver 응답 자체가 배치이므로 문제되지 않는다.

🧑‍💻 엔지니어 코멘트: 실제 응답시간 실측(최초 요청 vs 캐시 적중, Naver /ac 자체 평균 응답시간)은 아직 수행되지 않았다. 구조상 병목이 없다는 것은 코드 경로 분석으로 확인된 것이며, 수치 검증은 운영 로그가 쌓인 뒤 후속 작업으로 남겨둔다.

📄 infrastructure/stock/external/StockNameSearchClientImpl.java 
private static final String CACHE_NAME = "koreanStockNameSearch";

public List<String> searchUsTickers(String keyword) {
    String key = keyword.trim();
    Cache cache = cacheManager.getCache(CACHE_NAME);

    if (cache != null) {
        List<String> cached = cache.get(key, List.class);
        if (cached != null) return cached;
    }

    List<String> result = resolve(key);
    // 0건이면 cache.put() 자체를 건너뛴다 → 오타 실패가 영구 캐싱되지 않음
    if (!result.isEmpty() && cache != null) {
        cache.put(key, result);
    }
    return result;
}
📄 StockNameSearchClientImpl.java — resolve() 
private List<String> resolve(String keyword) {
    var response = naverStockSearchClient.search(keyword);
    if (response == null || response.items() == null) return List.of();

    return response.items().stream()
            .filter(item -> "stock".equals(item.category())
                    && "USA".equals(item.nationCode()))
            .map(Item::code)
            .distinct()
            .toList();
}

⚖️ 도입 장단점

✅ 장점

  • 자체 한글-ticker 매핑 테이블을 만들고 유지보수할 필요 없음 (Naver가 이미 관리하는 데이터 재사용)
  • 기존 검색 파이프라인(캐시→DB→Yahoo)을 전혀 변경하지 않아 회귀 위험이 낮음 — 순수 추가(additive) 구조
  • IndexAndWaterRide에서 2026-06-19부터 실사용 검증된 코드라 신뢰도가 높음
  • 캐싱(신규 캐시 + alias) 덕분에 반복 검색 비용이 낮음
  • ETF 제외 요구사항이 별도 로직 없이 category 필터링만으로 자연스럽게 해결됨

⚠️ 단점 / 리스크

  • 외부 의존성 추가: Naver /ac는 비공식 API — 스펙 변경/차단 가능성이 있고, 공식 SLA가 없음
  • 폴백 없음: Yahoo는 Finnhub라는 폴백이 있지만, Naver 실패 시엔 바로 "존재하지 않는 종목명" 예외 — 한글 검색 자체가 막힘
  • 다중 매치 UX 미정리: 한 키워드가 여러 ticker에 매칭될 경우 필터링/우선순위 로직이 없어 노이즈 가능성. 국내 종목의 "완전일치>접두일치>부분일치>길이순" 정렬은 이번 미국주식 포트에는 애초에 대상이 아니었다 — 도입한다면 신규 설계 필요.
  • 캐시 무효화 정책 부재: 24일 TTL 동안 Naver 쪽 종목명이 바뀌어도 반영 안 됨 (다만 발생 빈도 낮음)
