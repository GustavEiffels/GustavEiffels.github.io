Section 3

🔬 문제 진단 — 왜 느렸는가 (원인 5가지, 영향도 순)

Explore 서브에이전트에게 "북마크 전환 흐름 전체를 추적해 지연 원인을 랭킹으로 보고하라"고 위임해 찾아낸 5가지 원인.

1
🐌 가격조회가 ticker당 순차 블로킹 호출 (가장 큰 원인)
KIS와 Yahoo를 모두 호출하고, 거래소 코드 미확정 ticker는 최대 3회까지 순차 시도. 20~30개 ticker 기준 최악 90~120회 순차 네트워크 라운드트립.
2
🚦 KIS WS 500ms 페이싱이 가격조회와 같은 커먼풀 점유
Thread.sleep(500)으로 점유된 ForkJoinPool.commonPool() 스레드가 늘어날수록, 같은 풀을 쓰는 즉시 가격조회 작업까지 실행이 밀림.
3
🔁 전체 unsubscribe 후 전체 재구독
겹치는 종목이 있어도 매번 전부 해제 후 전부 재구독 → 겹치는 종목까지 원인 2의 500ms 페이싱을 다시 탐.
→ 원인 2를 불필요하게 더 많이 유발
4
🧭 거래소 코드 미확정 ticker의 반복 탐색
캐시에 없는 ticker는 NAS/NYS/AMS를 순서대로 최대 3번 시도. 캐시 무효화 직후·최초 로딩 시점에 원인 1을 악화시킴.
→ 원인 1을 악화
🥵 체감 지연: 종목 목록 로딩이 느림 (원인 1 + 원인 2가 합쳐진 결과)
5
🔄 실시간 틱마다 리스트 전체 리렌더 (상시 비용, 전환 지연 아님)
React.memo 부재로 가격이 올 때마다 리스트 전체가 리렌더. "전환" 자체의 지연 요인은 아니라 이번 범위에서 제외.

원인 1 상세 — KIS와 Yahoo를 왜 같이 부르는가

단순히 "KIS 실패 시 Yahoo로 대체"하는 게 아니다. 실제로는 필드 단위로 병합한다 — KIS의 실시간 현재가를 우선 쓰되, KIS가 주지 않는 애프터마켓 가격·일중 고가/저가는 Yahoo 결과에서 보충한다. 이 이중 조회 자체가 원인 1을 키우는 구조다.

private StockPriceInfo fetchKisPrice(String ticker) {
    String cached = exchangeCodeCache.get(ticker);
    if (cached != null) {
        StockPriceInfo info = tryFetch(cached, ticker);
        if (info != null) return info;
        exchangeCodeCache.remove(ticker); // 캐시된 코드가 더 이상 안 맞으면 제거 후 재탐색
    }
    for (String code : EXCHANGE_CODES) { // {"NAS","NYS","AMS"}
        StockPriceInfo info = tryFetch(code, ticker);
        if (info != null) { exchangeCodeCache.put(ticker, code); return info; }
    }
    return null; // 3개 거래소 모두 실패
}

private Map<String, StockPriceInfo> fetchFromKis(List<String> tickers) {
    Map<String, StockPriceInfo> result = new HashMap<>();
    for (String ticker : tickers) {                       // 순차 for-loop
        StockPriceInfo priceInfo = fetchKisPrice(ticker); // 블로킹 HTTP 호출
        if (priceInfo != null) result.put(ticker, priceInfo);
    }
    return result;
}
📄 StockPriceClientImpl.java — fetchFromKis (After) 
// After — priceFetchExecutor(고정 24스레드)로 병렬화
private Map<String, StockPriceInfo> fetchFromKis(List<String> tickers) {
    List<CompletableFuture<Map.Entry<String, StockPriceInfo>>> futures = tickers.stream()
            .map(ticker -> CompletableFuture.supplyAsync(
                    () -> new AbstractMap.SimpleEntry<>(ticker, fetchKisPrice(ticker)),
                    priceFetchExecutor))
            .toList();

    Map<String, StockPriceInfo> result = new HashMap<>();
    for (var future : futures) {
        var entry = future.join();
        if (entry.getValue() != null) result.put(entry.getKey(), entry.getValue());
    }
    return result;
}

@Configuration
public class AsyncConfig {
    @Bean
    public ExecutorService priceFetchExecutor() {
        return Executors.newFixedThreadPool(24);
    }

    @Bean
    public ExecutorService kisSubscribeExecutor() {
        return Executors.newSingleThreadExecutor();
    }

🧩 왜 KIS/Yahoo 그룹 간 병렬화는 하지 않았는가 (중첩 스레드풀 데드락 회피) 둘 다 같은 priceFetchExecutor에 던지고 그 안에서 다시 ticker별로 같은 풀에 서브밋해 .join()으로 기다리면, 같은 고정 크기 풀에 작업이 중첩 제출되는 구조가 된다. 다중 세션이 겹치면 외곽 작업이 풀 스레드를 모두 점유한 채 내부 작업을 기다려 데드락 위험이 생긴다. 그래서 그룹(KIS→Yahoo) 자체는 순차 유지, 그룹 내부에서만 병렬화했다.

부수 결정 — 왜 @RequiredArgsConstructor를 명시적 생성자로 바꿨는가

ExecutorService 빈이 priceFetchExecutor/kisSubscribeExecutor 2개 존재하므로, 타입만으로는 Spring이 어느 빈을 주입할지 판단할 수 없다(둘 다 ExecutorService 타입). 그래서 캐시 이전에 WebClient 빈이 여러 개일 때 이미 쓰고 있던 @Qualifier("kisWebClient") 컨벤션을 그대로 재사용해, Lombok의 @RequiredArgsConstructor 대신 명시적 생성자 + @Qualifier로 바꿨다.

📄 StockPriceWebSocketController.java — 생성자 
public StockPriceWebSocketController(StockPriceRelayService relayService,
                                      StockPriceClient stockPriceClient,
                                      StockPriceClientImpl stockPriceClientImpl,
                                      KisRealtimeManager kisRealtimeManager,
                                      @Qualifier("priceFetchExecutor") ExecutorService priceFetchExecutor,
                                      @Qualifier("kisSubscribeExecutor") ExecutorService kisSubscribeExecutor) { ... }

같은 처리를 YahooPriceClient, StockPriceClientImpl에도 동일하게 적용했다 — 필드명-빈이름 매칭에 의존하지 않고 명시적으로 어떤 풀을 쓰는지 코드에서 바로 보이게 하기 위함.
