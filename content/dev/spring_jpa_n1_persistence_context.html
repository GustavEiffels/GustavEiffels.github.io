JPA — N+1 문제와 영속성 컨텍스트

JPA N+1 영속성 컨텍스트 2026-05-20

핵심 정리

  • N+1은 버그가 아닌 LAZY 로딩이 만들어내는 성능 안티패턴이다
  • 자바 코드처럼 보이는 연관 객체 호출이 실제로는 DB 쿼리다
  • 영속성 컨텍스트는 트랜잭션 단위로 생성되고 소멸한다
  • 1차 캐시는 같은 트랜잭션 안에서만 유효하다 — 요청 간 공유되지 않는다
  • Dirty Checking은 커밋 시점에 스냅샷과 비교해 변경분을 자동 UPDATE한다
CH 01

N+1 — 정의

한 줄 정의 N+1은 JPA의 LAZY 로딩으로 인해 N번 추가 쿼리가 발생하는 성능 문제다. 기능은 정상 동작하지만 쿼리 횟수가 폭발적으로 늘어나 운영 환경에서 장애로 이어질 수 있다.

N+1은 버그가 아니다. JPA가 LAZY 로딩 규칙대로 동작하다 보니 자연스럽게 발생하는 구조적 함정이다. 사용자 입장에서는 전혀 모른다. 순수하게 성능 문제다.

본질 자바 코드처럼 보이는 연관 객체 호출이 실제로는 DB 쿼리다. 이걸 N번 하면 N+1이다.
CH 02

왜 발생하나 — ORM의 구조적 함정

JPA는 ORM이다. 객체 호출이 곧 DB 쿼리다. 개발자가 쿼리가 나가는 걸 눈으로 못 보기 때문에 무심결에 N번 호출하게 된다.

N+1 발생 예시 
@OneToMany(mappedBy = "user", fetch = FetchType.LAZY)  // 기본값
List<Order> orders;

// N+1 발생
List<User> users = userRepository.findAll();  // 쿼리 1번

users.stream()
    .map(user -> user.getOrders())  // 호출할 때마다 쿼리 1번씩 추가
    .toList();
실제 나가는 SQL
SQL — 총 N+1번 
-- 1번: 유저 전체 조회
SELECT * FROM user;

-- N번: 각 유저의 주문 조회
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
-- ... N번
반복문만의 문제가 아니다 반복문이든 스트림이든 연관 객체를 N번 호출하는 상황이면 모두 발생한다. 단 1건 조회 후 연관 객체 1번 호출해도 1+1 = 2번의 쿼리가 나간다.
CH 03

EAGER로 바꾸면 해결되나?

LAZY (기본값)

연관 객체를 실제로 사용할 때 쿼리를 날린다

N개 엔티티에서 N번 호출 → N+1 발생

쓰지 않으면 쿼리 안 나감

EAGER

findAll() 시점에 무조건 JOIN해서 가져온다

안 쓰는 데이터도 항상 조회 → 메모리 낭비

N+1 발생 시점이 앞당겨질 뿐, 쿼리 수는 동일

결론 EAGER는 해결책이 아니다. N+1이 findAll() 시점으로 앞당겨질 뿐이다. 유저 10,000명 조회 시 EAGER면 쓰지도 않을 주문 10,000건을 무조건 JOIN해서 가져온다.
CH 04

N+1 해결책

방법 1 — JPQL Fetch Join
JPQL Fetch Join 
@Query("SELECT DISTINCT u FROM User u JOIN FETCH u.orders")
List<User> findAllWithOrders();
SQL — 1번으로 끝 
SELECT DISTINCT u.*, o.*
FROM user u
LEFT JOIN orders o ON o.user_id = u.id;
방법 2 — @EntityGraph
@EntityGraph 
@EntityGraph(attributePaths = {"orders"})
List<User> findAll();
방법 3 — QueryDSL Fetch Join
QueryDSL — 동적 조건 포함 
@RequiredArgsConstructor
@Repository
public class UserQueryRepository {

    private final JPAQueryFactory queryFactory;

    public List<User> findAllWithOrders() {
        return queryFactory
            .selectFrom(user)
            .leftJoin(user.orders, order).fetchJoin()  // fetchJoin() 핵심
            .distinct()
            .fetch();
    }

    // 동적 조건 추가
    public List<User> findWithOrders(String name, LocalDate from) {
        BooleanBuilder builder = new BooleanBuilder();

        if (name != null) builder.and(user.name.eq(name));
        if (from != null) builder.and(order.createdAt.goe(from));

        return queryFactory
            .selectFrom(user)
            .leftJoin(user.orders, order).fetchJoin()
            .where(builder)
            .distinct()
            .fetch();
    }
}
방법 4 — @BatchSize + QueryDSL (페이징 포함 시)

Fetch Join은 페이징과 함께 쓰면 메모리 문제가 발생한다. 페이징이 필요하면 @BatchSize를 쓴다.

@BatchSize + 페이징 
// Entity에 선언
@OneToMany(mappedBy = "user")
@BatchSize(size = 100)
List<Order> orders;

// QueryDSL — Fetch Join 없이 페이징
public Page<User> findUsers(Pageable pageable) {
    List<User> content = queryFactory
        .selectFrom(user)
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize())
        .fetch();

    long total = queryFactory
        .select(user.count())
        .from(user)
        .fetchOne();

    return new PageImpl<>(content, pageable, total);
}
SQL — 총 3번으로 끝 
SELECT * FROM user LIMIT 20 OFFSET 0;
SELECT * FROM orders WHERE user_id IN (1, 2, 3, ..., 20);
SELECT COUNT(*) FROM user;
방법 비교
방법페이징 가능동적 조건추천 상황
JPQL Fetch Join위험불편단순 고정 조회
@EntityGraph위험불가리포지토리 메서드 단순할 때
QueryDSL Fetch Join위험가능복잡한 조건, 페이징 없을 때
@BatchSize + QueryDSL안전가능페이징 + 연관 데이터 같이 필요할 때
CH 05

영속성 컨텍스트 — 정의

영속성 컨텍스트는 애플리케이션과 DB 사이의 버퍼다. 내부에 1차 캐시를 가지고 있으며 트랜잭션 단위로 생성되고 소멸한다.

영속성 컨텍스트 내부 구조 
+----------------------------------------------+
|  1차 캐시 (Map)                               |
|  key      엔티티          스냅샷              |
|  user:1 -> User(name=철수) | User(name=철수) |
|  user:2 -> User(name=영희) | User(name=영희) |
+----------------------------------------------+
엔티티 상태 4가지

비영속 (Transient)

new로 생성만 함

영속성 컨텍스트와 무관

영속 (Managed)

영속성 컨텍스트에 저장됨

Dirty Checking 대상

준영속 (Detached)

컨텍스트에서 분리됨

Dirty Checking 안 함

삭제 (Removed)

삭제 예약됨

커밋 시 DELETE 실행

CH 06

1차 캐시 — 동작 방식

같은 트랜잭션 안에서 같은 엔티티를 두 번 조회하면 DB를 안 간다.

1차 캐시 동작 
@Transactional
public void example() {
    User user1 = userRepository.findById(1L);  // DB 조회 -> 캐시 저장
    User user2 = userRepository.findById(1L);  // 캐시에서 반환 (DB 안 감)

    System.out.println(user1 == user2);  // true (같은 객체)
}

-- 쿼리 1번만 나감
SELECT * FROM user WHERE id = 1;
1차 캐시의 진짜 역할 DB 부하를 줄여주는 캐시라기보다 같은 트랜잭션 안에서 동일성을 보장해주는 장치에 가깝다. 트랜잭션이 다르면 각자 별도의 영속성 컨텍스트에서 따로 조회한다.
CH 07

Dirty Checking — 변경 감지

1차 캐시에 저장할 때 스냅샷을 같이 찍어둔다. 트랜잭션 커밋 시점에 엔티티와 스냅샷을 비교해서 변경된 게 있으면 UPDATE를 자동 실행한다.

Dirty Checking — save() 없이 UPDATE 
@Transactional
public void update() {
    User user = userRepository.findById(1L);
    // 캐시: User(name=철수) | 스냅샷: User(name=철수)

    user.setName("영희");
    // 캐시: User(name=영희) | 스냅샷: User(name=철수)

    // 트랜잭션 커밋 시점
    // 엔티티(영희) vs 스냅샷(철수) -> 다름 -> UPDATE 자동 실행
}
// save() 호출 안 했는데 UPDATE 나감

-- 자동으로 실행됨
UPDATE user SET name = '영희' WHERE id = 1;
비교 시점 메서드가 종료될 때가 아니라 트랜잭션이 커밋될 때 비교한다. 메서드가 끝나도 트랜잭션이 살아있으면 Dirty Checking 안 한다.
CH 08

생명주기와 범위 — 트랜잭션 단위

요청별 별도 영속성 컨텍스트 
// 요청 A
@Transactional
public void requestA() {
    Member tom = memberRepository.findById(1L);
    // 영속성 컨텍스트 A에 Tom 저장
}
// 트랜잭션 끝 -> 영속성 컨텍스트 A 소멸 -> 캐시 사라짐

// 요청 B (동시에 들어온 다른 요청)
@Transactional
public void requestB() {
    Member tom = memberRepository.findById(1L);
    // 영속성 컨텍스트 B에 Tom 따로 저장
    // A의 캐시와 전혀 관계없음 -> DB에서 다시 조회
}
영속성 컨텍스트 생명주기 
트랜잭션 시작    -> 영속성 컨텍스트 생성
엔티티 조회      -> 1차 캐시에 저장 (스냅샷 포함)
재조회           -> 캐시에서 반환 (DB 안 감)
트랜잭션 커밋    -> Dirty Checking -> 변경분 UPDATE
영속성 컨텍스트  -> 소멸 -> 1차 캐시 사라짐
1차 캐시 공유 범위 하나의 트랜잭션 안에서만 유효하다. 트랜잭션이 다르면 영속성 컨텍스트도 다르고 캐시도 다르다. 여러 요청이 동시에 와도 각자 자기 영속성 컨텍스트에서 따로 조회한다.
CH 09

트랜잭션 격리 수준

영속성 컨텍스트가 커밋된 내용을 읽느냐는 트랜잭션 격리 수준(Isolation Level) 설정에 따라 다르다.

격리 수준커밋 안 된 것커밋된 것실무 사용
READ UNCOMMITTED읽음읽음거의 안 씀
READ COMMITTED안 읽음읽음Oracle, PostgreSQL 기본값
REPEATABLE READ안 읽음시작 시점 기준MySQL 기본값
SERIALIZABLE안 읽음완전 순차 처리거의 안 씀
READ COMMITTED vs REPEATABLE READ
격리 수준 비교 시나리오 
// 시나리오
트랜잭션 A 시작
    -> 트랜잭션 B: Tom -> "Tommy" 변경 후 커밋
    -> 트랜잭션 A에서 Tom 재조회

READ COMMITTED  -> Tommy (커밋된 거 읽음)
REPEATABLE READ -> Tom   (트랜잭션 시작 시점 기준)

// JPA에서 설정
@Transactional(isolation = Isolation.READ_COMMITTED)
public void example() { ... }
CH 10

OSIV — Open Session In View

1 문제 상황 — 트랜잭션 밖에서 LAZY 로딩

영속성 컨텍스트는 트랜잭션이 끝나면 소멸한다. 트랜잭션 밖에서 LAZY 로딩을 시도하면 예외가 터진다.

LazyInitializationException 발생 
// Controller에서 LAZY 로딩 시도
public UserResponse getUser(Long id) {
    User user = userService.findUser(id);  // 트랜잭션 종료
    user.getOrders();  // LazyInitializationException 터짐
}

// 왜 터지냐
트랜잭션 종료 -> 영속성 컨텍스트 소멸
-> LAZY 로딩 불가 -> 예외 발생
2 OSIV가 하는 일

영속성 컨텍스트를 HTTP 요청이 끝날 때까지 열어둔다. Spring Boot 기본값은 ON이다.

OSIV ON / OFF 흐름 비교 
// OSIV OFF
HTTP 요청 -> [트랜잭션 + 영속성 컨텍스트] -> 종료 -> Controller -> 응답

// OSIV ON
HTTP 요청 -> [영속성 컨텍스트 시작] -> 트랜잭션 -> 종료
         -> Controller까지 컨텍스트 유지 -> 응답 -> 컨텍스트 소멸
application.properties 
spring.jpa.open-in-view=true  # Spring Boot 기본값
3 OSIV ON vs OFF 트레이드오프
구분OSIV ONOSIV OFF
LAZY 로딩Controller까지 가능트랜잭션 안에서만 가능
DB 커넥션요청 내내 점유트랜잭션 끝나면 반납
트래픽 많을 때커넥션 부족 위험안전
코드 복잡도단순서비스 계층에서 다 해결해야 함
OSIV ON의 위험 트래픽이 많은 서비스에서 OSIV ON이면 커넥션 풀이 고갈된다. 요청 하나가 DB 커넥션을 응답 시점까지 계속 점유하기 때문이다.
4 OSIV OFF 시 해결 패턴

@Transactional 안에서 LAZY 로딩을 전부 처리하고, Controller에는 완성된 DTO만 넘긴다.

잘못된 방식 — 엔티티를 Controller까지 넘김
Bad — LazyInitializationException 발생 
@Service
public class UserService {
    @Transactional
    public User findUser(Long id) {
        return userRepository.findById(id);  // 엔티티 그대로 반환
    }
}

@Controller
public class UserController {
    public UserResponse getUser(Long id) {
        User user = userService.findUser(id);
        user.getOrders();  // 트랜잭션 끝났으니 LazyInitializationException
    }
}
올바른 방식 — 서비스 계층에서 다 해결
Good — 서비스에서 DTO 변환 후 반환 
@Service
public class UserService {
    @Transactional
    public UserResponse findUser(Long id) {
        User user = userRepository.findById(id);
        List<Order> orders = user.getOrders();  // 트랜잭션 안이니까 가능
        return new UserResponse(user, orders);   // DTO로 변환해서 반환
    }
}

@Controller
public class UserController {
    public UserResponse getUser(Long id) {
        return userService.findUser(id);  // 이미 완성된 DTO만 받음
    }
}
OSIV OFF 핵심 원칙 LAZY 로딩이 필요한 건 전부 @Transactional 안에서 처리한다. Controller에는 이미 완성된 DTO만 넘긴다. 엔티티를 Controller까지 넘기지 않는다.
상황선택
소규모 / 트래픽 적음OSIV ON 그냥 써도 됨
대규모 / 트래픽 많음OSIV OFF + 서비스 계층에서 LAZY 로딩 해결
5 OSIV 테스트 방법

HTTP 요청 생명주기가 없는 테스트 환경에서는 OSIV가 동작하지 않는다. OpenEntityManagerInViewInterceptor가 HTTP 요청을 가로채야 하는데 테스트에는 그 과정이 없다.

방법 1 — @Transactional (가장 많이 씀)
@Transactional 테스트 
@SpringBootTest
class UserServiceTest {

    @Autowired UserRepository userRepository;

    @Test
    @Transactional  // 테스트 끝날 때까지 영속성 컨텍스트 유지
    void lazyLoadingTest() {
        User user = userRepository.findById(1L).orElseThrow();
        List<Order> orders = user.getOrders();  // 트랜잭션 안이니까 가능
        assertThat(orders).isNotEmpty();
    }

    @Test
    @Transactional
    @Commit  // 롤백 안 하고 실제 커밋하고 싶을 때
    void saveTest() { ... }
}
@Transactional 테스트의 자동 롤백 @Transactional이 붙은 테스트는 끝나면 자동으로 롤백된다. 다음 테스트에 영향을 주지 않아 테스트 격리가 보장된다.
방법 2 — @DataJpaTest (JPA만 테스트할 때)
@DataJpaTest 
@DataJpaTest  // JPA 관련만 로드, 자동으로 @Transactional 적용
class UserRepositoryTest {

    @Autowired UserRepository userRepository;

}

DB실제 DB 또는 설정 따름기본 H2 인메모리
트랜잭션직접 붙여야 함자동 적용
방법 3 — LazyInitializationException 직접 재현
EntityManager.detach()로 예외 재현 
@SpringBootTest
class LazyLoadingTest {

    @Autowired UserRepository userRepository;
    @Autowired EntityManager em;

    @Test
    void lazy_로딩_예외_재현() {
        User user = findUserInTransaction();

        // 트랜잭션 밖에서 LAZY 로딩 시도 -> 예외 발생 확인
        assertThatThrownBy(() -> user.getOrders().size())
            .isInstanceOf(LazyInitializationException.class);
    }

    @Transactional
    User findUserInTransaction() {
        User user = userRepository.findById(1L).orElseThrow();
        em.detach(user);  // 명시적으로 detach -> 영속성 컨텍스트에서 분리
        return user;
    }
}
방법 4 — MockMvc로 실제 HTTP 요청 시뮬레이션
MockMvc + @TestPropertySource 
// OSIV ON 상태 검증
@SpringBootTest
@AutoConfigureMockMvc
class OsivIntegrationTest {

    @Autowired MockMvc mockMvc;

    @Test
    void osivOn_lazy로딩_성공() throws Exception {
        mockMvc.perform(get("/users/1"))
            .andExpect(status().isOk());
    }
}

// OSIV OFF 동작 검증
@SpringBootTest
@AutoConfigureMockMvc
@TestPropertySource(properties = "spring.jpa.open-in-view=false")
class OsivOffTest {

    @Autowired MockMvc mockMvc;

    @Test
    void osivOff_컨트롤러에서_lazy로딩_예외() throws Exception {
        mockMvc.perform(get("/users/1/with-lazy"))
            .andExpect(status().is5xxServerError());  // LazyInitializationException
        mockMvc.perform(get("/users/1"))
            .andExpect(status().isOk());  // DTO 변환하면 정상
    }
}

Quiz

퀴즈 — 직접 확인해보자

Q1. FetchType.EAGER로 바꾸면 N+1 문제가 해결되는가?
A 해결된다. JOIN을 미리 해서 가져오므로 추가 쿼리가 없다
B LAZY보다 낫다. 반복문에서는 N+1이 발생하지 않는다
C 해결되지 않는다. 발생 시점이 findAll() 호출 시점으로 앞당겨질 뿐이다
D 단건 조회일 때만 해결된다
정답: C
EAGER는 findAll() 시점에 연관 엔티티를 즉시 가져오지만, 내부적으로는 여전히 N번 추가 쿼리가 발생한다. 유저 10,000명이면 쓰지도 않을 주문 10,000건을 무조건 JOIN해서 가져온다. 근본 해결책은 Fetch Join 또는 @BatchSize다.
Q2. Fetch Join을 페이징과 함께 사용하면 어떤 문제가 발생하는가?
A SQL 문법 오류가 발생한다
B 전체 데이터를 메모리에 올린 뒤 애플리케이션에서 페이징 처리해 OOM 위험이 있다
C DISTINCT가 동작하지 않아 중복 결과가 나온다
D 문제없이 정상 동작한다
정답: B
Fetch Join + 페이징 조합은 JPA가 DB에 LIMIT/OFFSET을 적용하지 못하고 전체 결과를 메모리로 가져온 뒤 페이징을 처리한다. 데이터가 많으면 OOM이 발생한다. 페이징이 필요할 땐 @BatchSize + QueryDSL 조합을 써야 한다.
Q3. 다음 코드에서 UPDATE 쿼리가 실행되는가?
UserService.java 
@Transactional
public void update() {
    User user = userRepository.findById(1L);
    user.setName("영희");
    // save() 호출 없음
}
A 실행된다. 트랜잭션 커밋 시 Dirty Checking이 스냅샷과 비교해 자동 UPDATE한다
B 실행되지 않는다. save()를 호출해야만 UPDATE가 나간다
C 실행되지 않는다. flush()를 명시적으로 호출해야 한다
D 실행되지 않는다. detach() 후 merge()를 해야 한다
정답: A
영속 상태(Managed)의 엔티티는 조회 시 스냅샷이 찍힌다. 트랜잭션 커밋 직전에 현재 상태와 스냅샷을 비교(Dirty Checking)해 변경이 감지되면 UPDATE를 자동 실행한다. save() 없이도 DB에 반영된다.
Q4. 동시에 들어온 두 HTTP 요청 A, B가 같은 userId=1을 조회한다. 1차 캐시는 공유되는가?
A 공유된다. 1차 캐시는 JVM 전체에서 동일하게 유지된다
B 공유된다. 같은 userId를 조회하면 같은 캐시 항목을 반환한다
C @Cacheable을 붙였을 때만 공유된다
D 공유되지 않는다. 트랜잭션마다 별도의 영속성 컨텍스트가 생성된다
정답: D
1차 캐시는 트랜잭션 단위로 생성·소멸한다. 요청 A와 B는 각자 별도의 영속성 컨텍스트를 가지므로 캐시도 분리된다. 요청 간 공유되는 것은 2차 캐시(ehcache 등 별도 설정 필요)다.
Q5. OSIV를 OFF로 설정했을 때 Controller에서 user.getOrders()를 호출하면?
A OSIV OFF여도 Controller에서 LAZY 로딩은 허용된다
B 경고 로그만 출력되고 빈 리스트를 반환한다
C LazyInitializationException이 발생한다. 트랜잭션 종료와 함께 영속성 컨텍스트가 소멸했기 때문이다
D DB 커넥션을 새로 열어서 조회한다
정답: C
OSIV OFF 상태에서는 트랜잭션이 끝나면 영속성 컨텍스트도 함께 소멸한다. 컨텍스트가 없는 상태에서 LAZY 로딩을 시도하면 LazyInitializationException이 발생한다. 해결책은 @Transactional 안에서 LAZY 로딩을 마치고 DTO로 변환해 Controller에 넘기는 것이다.
