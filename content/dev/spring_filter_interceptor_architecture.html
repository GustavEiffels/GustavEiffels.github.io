CH 02

Filter — Servlet 레이어의 문지기

1

Filter란 무엇인가

Filter는 Java EE (Jakarta EE) 표준 Servlet API에 정의된 인터페이스입니다. Spring과는 독립적으로, Tomcat 같은 서블릿 컨테이너가 관리합니다. DispatcherServlet이 요청을 받기 이전과 응답을 보내기 이후에 동작합니다.

위치 Tomcat (WAS) 내부 — DispatcherServlet 앞

인터페이스 jakarta.servlet.Filter

등록 방법 @Component 또는 FilterRegistrationBean

접근 범위 모든 요청 (정적 리소스 포함)

Filter의 3가지 메서드
jakarta.servlet.Filter 
public interface Filter {

    // 필터 초기화 (애플리케이션 시작 시 1회 실행)
    default void init(FilterConfig filterConfig) {}

    // 요청마다 실행 — 핵심 메서드
    void doFilter(ServletRequest request,
                  ServletResponse response,
                  FilterChain chain) throws IOException, ServletException;

    // 필터 소멸 (애플리케이션 종료 시 1회 실행)
    default void destroy() {}
}
doFilter의 실행 구조
doFilter 패턴 
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {

    // [A] 요청 처리 전 코드 (DispatcherServlet 도달 이전)
    log.info("요청 전처리");

    chain.doFilter(req, res);  // 다음 Filter 또는 DispatcherServlet으로 전달

    // [B] 응답 처리 후 코드 (DispatcherServlet 처리 완료 후 복귀)
    log.info("응답 후처리");
}
주의

chain.doFilter()를 호출하지 않으면 요청이 그 자리에서 차단됩니다. JWT 검증 실패 시 여기서 401 응답을 바로 내려보내는 패턴이 이것입니다.

2

Filter가 잘 맞는 상황

사용 사례 이유
인코딩 처리 CharacterEncodingFilter모든 요청에 적용, Spring 컨텍스트 불필요
CORS 처리 CorsFilterDispatcherServlet 이전에 CORS 헤더를 붙여야 OPTIONS 사전 요청도 처리 가능
JWT 파싱 / 토큰 검증Spring Security와 연계, Security Filter Chain에서 처리
요청/응답 로깅 (raw body)HttpServletRequest body를 읽으려면 Filter 레벨이 적합
Rate Limiting / IP 차단Spring 관계없이 가장 빠르게 차단 가능
정적 리소스 처리Filter는 /static/** 같은 경로에도 개입 가능
CH 03

Interceptor — Spring MVC 레이어의 관문

1

Interceptor란 무엇인가

Interceptor는 Spring MVC가 제공하는 인터페이스입니다. DispatcherServlet이 요청을 받은 이후, Controller(Handler)에 전달하기 이전에 동작합니다. Spring의 ApplicationContext를 완전히 활용할 수 있어 Bean 주입, AOP, 트랜잭션 컨텍스트 모두 접근 가능합니다.

위치 DispatcherServlet 내부 — Controller 직전

인터페이스 org.springframework.web.servlet.HandlerInterceptor

등록 방법 WebMvcConfigurer.addInterceptors()

접근 범위 DispatcherServlet이 처리하는 요청만 (정적 리소스 제외 가능)

HandlerInterceptor의 3가지 메서드
HandlerInterceptor 
public interface HandlerInterceptor {

    // [1] Controller 실행 직전
    //     false 반환 → Controller 호출 안 함, 처리 중단
    default boolean preHandle(HttpServletRequest req,
                               HttpServletResponse res,
                               Object handler) throws Exception {
        return true;
    }

    // [2] Controller 실행 후, View 렌더링 직전
    //     @RestController 환경에서는 거의 사용하지 않음
    default void postHandle(HttpServletRequest req,
                             HttpServletResponse res,
                             Object handler,
                             ModelAndView modelAndView) throws Exception {}

    // [3] View 렌더링 완료 후 (예외 발생 시에도 항상 호출)
    //     리소스 정리, 처리 시간 측정에 사용
    default void afterCompletion(HttpServletRequest req,
                                  HttpServletResponse res,
                                  Object handler,
                                  Exception ex) throws Exception {}
}
handler 파라미터란?
preHandle의 Object handler를 HandlerMethod로 캐스팅하면 실행될 Controller의 클래스, 메서드, @RequestMapping, @LoginRequired 같은 커스텀 어노테이션까지 모두 꺼낼 수 있습니다. Filter에서는 절대 불가능한 기능입니다.
2

Interceptor가 잘 맞는 상황

사용 사례 이유
로그인 세션 체크HttpSession, Spring Bean에 접근 가능, Controller 메서드 어노테이션 확인 가능
권한/역할 체크 (@LoginRequired)HandlerMethod로 커스텀 어노테이션을 읽어 특정 API만 선택적으로 제어
API 실행 시간 측정preHandle에서 시작, afterCompletion에서 종료 — MDC / 로그에 기록
공통 Model 데이터 주입postHandle에서 ModelAndView에 공통 사용자 정보, 메뉴 등을 주입 (MVC 템플릿 방식)
감사(Audit) 로깅Spring Security 컨텍스트로 현재 사용자 특정 가능, 비즈니스 맥락 포함 가능
다국어 처리 (Locale)LocaleChangeInterceptor — Spring 표준 제공
CH 04

Filter vs Interceptor — 핵심 차이 완전 비교

1

한눈에 보는 비교표

항목 Filter Interceptor
기술 표준Java EE (Servlet API)Spring MVC
관리 주체Tomcat (Servlet Container)Spring ApplicationContext
동작 위치DispatcherServlet 이전DispatcherServlet 이후, Controller 이전
Spring Bean 주입가능 (단, 주의 필요)완전 가능 (@Autowired)
Controller 정보 접근불가HandlerMethod로 접근 가능
적용 범위모든 요청 (정적 리소스 포함)DispatcherServlet 처리 요청만
예외 처리try-catch 직접 처리@ControllerAdvice와 연동 가능
Request Body 읽기직접 가능 (stream)Jackson 처리 이후 접근 (제한적)
실행 순서Filter → Interceptor 순Filter 이후 실행
2

처리 흐름 — 실행 순서 타임라인

요청  Filter.doFilter() [전처리]
  |        |
  |        +-- chain.doFilter()
  |                  |
  |        DispatcherServlet
  |                  |
  |        Interceptor.preHandle()    -- false 반환 시 이후 중단
  |                  |
  |        HandlerMapping
  |                  |
  |        ArgumentResolver
  |                  |
  |        @Controller.method()
  |                  |
  |        Interceptor.postHandle()   -- 정상 응답 시만 실행
  |                  |
  |        View Resolver
  |                  |
  |        Interceptor.afterCompletion() -- 예외 발생해도 항상 실행
  |                  |
응답  Filter.doFilter() [후처리]

Filter 예외 처리

DispatcherServlet 바깥이므로 @ControllerAdvice가 잡지 못합니다.

직접 response.sendError() 또는 ObjectMapper로 JSON 응답을 직접 써야 합니다.

Interceptor 예외 처리

preHandle에서 예외를 throw하면 DispatcherServlet이 잡아 @ControllerAdvice로 전달합니다.

일관된 에러 포맷 적용이 쉽습니다.

CH 05

코드 구현 예제

1

JWT 인증 Filter 구현

JwtAuthFilter.java 
@Component
public class JwtAuthFilter implements Filter {

    @Autowired
    private JwtProvider jwtProvider;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
                          FilterChain chain) throws IOException, ServletException {

        HttpServletRequest  req = (HttpServletRequest) request;
        HttpServletResponse res = (HttpServletResponse) response;

        String token = req.getHeader("Authorization");

        if (token == null || !jwtProvider.validate(token)) {
            res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            res.getWriter().write("{\"error\":\"Unauthorized\"}");
            return;  // chain 호출하지 않아 요청 차단
        }

        chain.doFilter(request, response);  // 정상 진행
    }
}
FilterRegistrationBean으로 등록 (순서 제어)
FilterConfig.java 
@Configuration
public class FilterConfig {

    @Bean
    public FilterRegistrationBean<JwtAuthFilter> jwtFilter() {
        FilterRegistrationBean<JwtAuthFilter> bean = new FilterRegistrationBean<>();
        bean.setFilter(new JwtAuthFilter());
        bean.addUrlPatterns("/api/*");
        bean.setOrder(1);  // 낮을수록 먼저 실행
        return bean;
    }
}
2

로그인 체크 Interceptor 구현

LoginCheckInterceptor.java 
@Component
public class LoginCheckInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res,
                               Object handler) throws Exception {

        // 정적 리소스 요청 스킵
        if (!(handler instanceof HandlerMethod method)) {
            return true;
        }

        // 커스텀 어노테이션 확인 — Filter에서는 불가능한 기능
        if (method.hasMethodAnnotation(NoLoginRequired.class)) {
            return true;
        }

        HttpSession session = req.getSession(false);
        if (session == null || session.getAttribute("USER") == null) {
            throw new UnauthorizedException("로그인 필요");  // @ControllerAdvice가 처리
        }
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                  Object handler, Exception ex) {
        MDC.clear();  // 처리 완료 후 리소스 정리
    }
}
WebMvcConfigurer로 등록
WebConfig.java 
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Autowired
    private LoginCheckInterceptor loginCheckInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginCheckInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/login", "/api/signup");
    }
}
3

API 응답 시간 측정 Interceptor

ExecutionTimeInterceptor.java 
@Slf4j
@Component
public class ExecutionTimeInterceptor implements HandlerInterceptor {

    private static final String START_TIME = "_startTime";

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res,
                               Object handler) {
        req.setAttribute(START_TIME, System.currentTimeMillis());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                  Object handler, Exception ex) {
        long elapsed = System.currentTimeMillis()
                        - (long) req.getAttribute(START_TIME);
        log.info("[{}] {} {}ms",
            req.getMethod(), req.getRequestURI(), elapsed);
    }
}

      ↓
[Controller]
      ↓
[Service]         ← AOP Pointcut 지정 가능
      ↓
[Repository]      ← AOP Pointcut 지정 가능

CH 07

Spring Container — IoC / DI 컨테이너

1

Spring Container란 무엇인가

Spring Container(ApplicationContext)는 애플리케이션의 Bean 생성, 의존성 주입, 생명주기 관리를 담당하는 핵심 인프라입니다. IoC(Inversion of Control) 원칙에 따라 객체가 스스로 의존성을 찾는 것이 아니라 Container가 필요한 Bean을 주입해 줍니다.

IoC (제어의 역전)

객체 생성 및 라이프사이클 제어권을 개발자가 아닌 Container가 담당.

new로 직접 생성하지 않고, Container가 제공하는 Bean을 사용.

DI (의존성 주입)

IoC를 구현하는 구체적인 방법.

@Autowired, 생성자 주입으로 필요한 Bean을 Container가 자동 연결.

BeanFactory vs ApplicationContext
항목 BeanFactory ApplicationContext
Bean 생성 시점Lazy (요청 시점)Eager (앱 시작 시점, 기본값)
AOP 지원제한적완전 지원
이벤트 발행미지원ApplicationEvent 지원
메시지 소스 (i18n)미지원MessageSource 지원
실무 사용거의 사용 안 함항상 ApplicationContext 사용
2

Bean 생명주기 (Lifecycle)

[1] @ComponentScan 탐색
    |  @Component / @Service / @Repository / @Controller / @Configuration 수집
    ↓
[2] BeanDefinition 생성 (설계도)
    |  클래스 정보, 스코프(Singleton/Prototype), 의존성 목록 등 메타데이터
    ↓
[3] Bean 인스턴스 생성 (new)
    |  기본 Singleton — 앱 전체에서 단 1개만 생성
    ↓
[4] 의존성 주입 (@Autowired / 생성자 주입)
    |  필요한 Bean을 Container가 자동 연결
    ↓
[5] @PostConstruct 실행
    |  초기화 로직 (DB 연결 확인, 캐시 워밍업 등)
    ↓
[6] Bean 사용 가능 (애플리케이션 실행 중)
    |  HTTP 요청마다 재사용
    ↓
[7] 애플리케이션 종료 신호
    ↓
[8] @PreDestroy 실행
    |  정리 로직 (커넥션 반납, 리소스 해제 등)
    ↓
[9] Bean 소멸
생성자 주입을 권장하는 이유
@Autowired 필드 주입은 Container 없이 테스트할 때 의존성을 주입할 수 없습니다. 생성자 주입은 final 필드 보장(불변) + 테스트 용이성을 동시에 얻습니다. Spring 공식 권장 방식입니다.
생성자 주입 예시 
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final PaymentService  paymentService;

    // 생성자가 1개일 때 @Autowired 생략 가능
    public OrderService(OrderRepository orderRepository,
                         PaymentService paymentService) {
        this.orderRepository = orderRepository;
        this.paymentService  = paymentService;
    }

    @PostConstruct
    public void init() { /* 초기화 로직 */ }

    @PreDestroy
    public void destroy() { /* 정리 로직 */ }
}
3

DelegatingFilterProxy — Filter와 Spring Container 연결

Filter는 Tomcat이 관리하므로 원래 Spring Container의 Bean을 주입받을 수 없습니다. DelegatingFilterProxy가 그 연결 다리 역할을 합니다. Spring Security가 이 방식으로 동작합니다.

Tomcat (Servlet Container)
  |
  +-- DelegatingFilterProxy        ← Servlet Filter로 등록
           |  실제 로직 위임
           ↓
      Spring Container (ApplicationContext)
           |
           +-- FilterChainProxy    ← Spring Bean (springSecurityFilterChain)
                  |
                  +-- SecurityFilter1 (JwtAuthFilter)
                  +-- SecurityFilter2 (ExceptionTranslationFilter)
                  +-- SecurityFilter3 (AuthorizationFilter)
                  +-- ...
DelegatingFilterProxy는 첫 요청이 들어올 때까지 Spring Bean 조회를 지연시킵니다. Tomcat은 앱 시작 전에 Filter 목록을 확정하므로, 이 시점에는 Spring Context가 아직 초기화되지 않았을 수 있기 때문입니다.
CH 08

Spring Security — 인증과 인가

1

Spring Security 전체 구조

Spring Security는 Filter 기반 보안 프레임워크입니다. DelegatingFilterProxy로 Servlet Container와 Spring Container를 연결하고, 내부의 FilterChainProxy가 보안 필터들을 순서대로 실행합니다.

[Tomcat]
    |
    +-- DelegatingFilterProxy      Servlet Filter (Spring 연결 다리)
              | 위임
              ↓
    FilterChainProxy               Spring Bean (springSecurityFilterChain)
              |
              +-- SecurityFilterChain  (URL 패턴별로 다른 체인 적용 가능)
                       |
                       ↓
              (1) SecurityContextHolderFilter   SecurityContext 로드/저장
              (2) UsernamePasswordAuthFilter     폼 로그인 처리
              (3) BasicAuthenticationFilter      HTTP Basic 처리
              (4) JwtAuthenticationFilter        커스텀 JWT 처리
              (5) ExceptionTranslationFilter     인증/인가 예외 → 401/403 변환
              (6) AuthorizationFilter            최종 인가 결정
                       |
                       ↓
              [DispatcherServlet]
SecurityFilterChain이 일반 Filter와 다른 점
일반 Filter는 모든 URL에 적용됩니다. SecurityFilterChain은 URL 패턴별로 다른 체인을 적용할 수 있습니다. 예: /api/** 는 JWT 체인, /admin/** 은 세션+권한 체인.
2

Authentication vs Authorization

Authentication (인증) — 누구인가?

신원을 확인하는 과정 (로그인).

성공 시 Authentication 객체가 SecurityContextHolder에 저장됨.

구현체: UsernamePasswordAuthenticationToken, JwtAuthToken 등.

Authorization (인가) — 무엇을 할 수 있는가?

인증된 사용자가 해당 리소스에 접근 권한이 있는지 확인.

ROLE_USER, ROLE_ADMIN 같은 GrantedAuthority 기반.

URL 레벨: SecurityFilterChain, 메서드 레벨: @PreAuthorize.

SecurityContext 구조
ThreadLocal
  |
  +-- SecurityContextHolder
            |
            +-- SecurityContext
                      |
                      +-- Authentication
                                |
                                +-- Principal    (UserDetails — 사용자 정보)
                                +-- Credentials  (비밀번호, 인증 후 null 처리)
                                +-- Authorities  ([ROLE_USER], [ROLE_ADMIN] ...)
주의

SecurityContextHolder는 ThreadLocal 기반으로 요청 스레드에 바인딩됩니다. @Async 비동기 환경에서는 SecurityContext가 자식 스레드로 전파되지 않으므로 DelegatingSecurityContextExecutor 또는 MODE_INHERITABLETHREADLOCAL 설정이 필요합니다.

3

JWT + Spring Security 통합 구현

SecurityConfig.java 
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Autowired
    private JwtAuthenticationFilter jwtAuthFilter;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .addFilterBefore(jwtAuthFilter,
                             UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
JwtAuthenticationFilter — OncePerRequestFilter
JwtAuthenticationFilter.java 
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Autowired private JwtProvider       jwtProvider;
    @Autowired private UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest  req,
                                       HttpServletResponse res,
                                       FilterChain chain) throws Exception {

        String token = req.getHeader("Authorization");

        if (token != null && jwtProvider.validate(token)) {
            String      username = jwtProvider.getUsername(token);
            UserDetails user     = userDetailsService.loadUserByUsername(username);

            // SecurityContext에 Authentication 저장 — 이후 @PreAuthorize에서 사용
            UsernamePasswordAuthenticationToken auth =
                new UsernamePasswordAuthenticationToken(
                    user, null, user.getAuthorities());
            SecurityContextHolder.getContext().setAuthentication(auth);
        }

        chain.doFilter(req, res);
    }
}
OncePerRequestFilter를 쓰는 이유
일반 Filter는 Forward, Include 등에서 한 요청에 여러 번 실행될 수 있습니다. OncePerRequestFilter는 요청당 정확히 1회만 실행되도록 보장합니다. JWT 검증 필터, 로깅 필터에 반드시 사용합니다.
CH 09

관계 정리 — Container · Security ↔ Filter · Interceptor

1

Security Filter + Interceptor 협력 흐름

Spring Security(Filter)와 Interceptor는 경쟁 관계가 아닌 협력 관계입니다. Security가 Filter에서 인증을 완료하면, Interceptor는 그 결과를 이어받아 비즈니스 맥락의 추가 처리를 담당합니다.

[요청]
    ↓
[SecurityFilterChain]
    |  JwtAuthFilter: 토큰 검증 → SecurityContextHolder에 Authentication 저장
    |  AuthorizationFilter: URL 레벨 인가 판단 (permitAll / hasRole)
    ↓
[DispatcherServlet]
    ↓
[Interceptor.preHandle()]
    |  SecurityContextHolder.getContext().getAuthentication() 으로 현재 사용자 조회 가능
    |  HandlerMethod 어노테이션 기반 추가 비즈니스 권한 체크
    |  감사(Audit) 로그 — 누가, 언제, 어떤 API 호출했는지 기록
    ↓
[@Controller → @Service]
    |  @PreAuthorize: AOP Proxy가 Authentication의 Authorities 확인
    ↓
[응답]
2

역할 분담 — 무엇을 어디서

처리 내용 Security Filter Interceptor AOP (@PreAuthorize)
JWT 토큰 검증담당——
URL 레벨 인가 (ROLE)담당——
커스텀 어노테이션 기반 제어—담당 (HandlerMethod)—
API 실행 시간 / 감사 로그—담당—
메서드 단위 비즈니스 인가—가능 (보통 미사용)담당
현재 사용자 정보 조회저장 주체SecurityContextHolder로 읽기authentication 파라미터
중요

@PreAuthorize는 Spring Container가 Service Bean에 씌운 AOP Proxy가 처리합니다. Interceptor를 통하지 않으므로, URL 매핑이 없는 내부 서비스 직접 호출에도 인가가 적용됩니다. Interceptor에서 인가 로직을 짜면 내부 호출에서 우회될 수 있으니 주의가 필요합니다.

CH 10

연습 문제

1

O / X 퀴즈

O/X

Q1. Filter는 DispatcherServlet보다 먼저 실행된다.

O — 정답

Filter는 Tomcat(Servlet Container) 레이어에서 동작하며, DispatcherServlet 진입 이전에 실행됩니다. 실행 순서: Filter Chain → DispatcherServlet → Interceptor → Controller

O/X

Q2. Interceptor.preHandle()이 false를 반환하면 postHandle()도 실행된다.

X — 오답

preHandle()이 false를 반환하면 Controller 호출이 중단되고, postHandle()도 실행되지 않습니다.

afterCompletion() 또한 preHandle이 true를 반환한 인터셉터에 한해서만 호출됩니다.

O/X

Q3. Filter 안에서 발생한 예외는 @ControllerAdvice가 처리한다.

X — 오답

@ControllerAdvice는 DispatcherServlet 내부에서만 동작합니다. Filter는 DispatcherServlet 외부(앞)이므로 예외가 전파되지 않습니다.

Filter에서 예외 처리 시 response.setStatus() + ObjectMapper로 직접 JSON 응답을 작성해야 합니다.

O/X

Q4. afterCompletion()은 Controller에서 예외가 발생해도 항상 실행된다.

O — 정답

afterCompletion은 예외 발생 여부와 관계없이 항상 호출됩니다. 예외 정보는 4번째 파라미터 Exception ex로 전달됩니다 (정상이면 null).

MDC 클리어, 리소스 반납 같은 정리 로직에 적합합니다.

O/X

Q5. Spring Security는 Interceptor를 기반으로 인증 처리를 한다.

X — 오답

Spring Security는 Filter 기반 보안 프레임워크입니다.

DelegatingFilterProxy → FilterChainProxy → SecurityFilterChain 구조로, DispatcherServlet 이전 Filter 레이어에서 인증을 처리합니다.

O/X

Q6. @Component만 붙인 Filter는 Spring Boot가 자동으로 모든 URL(/*)에 등록한다.

O — 정답

Spring Boot Auto-Configuration이 @Component Filter를 발견하면 자동으로 FilterRegistrationBean을 생성하고 /* 패턴으로 Tomcat에 등록합니다.

특정 URL에만 적용하려면 FilterRegistrationBean.addUrlPatterns()로 명시 등록해야 합니다.

O/X

Q7. Interceptor는 HandlerMethod를 통해 Controller 메서드의 어노테이션을 읽을 수 있다.

O — 정답

preHandle의 Object handler를 HandlerMethod로 캐스팅하면 실행될 Controller의 클래스, 메서드, 어노테이션 정보를 모두 읽을 수 있습니다.

이것이 Filter와의 결정적 차이이며, @LoginRequired 같은 커스텀 어노테이션 기반 제어에 활용합니다.

O/X

Q8. @PreAuthorize는 Interceptor가 호출한다.

X — 오답

@PreAuthorize는 Spring Container가 Service Bean에 씌운 AOP Proxy가 처리합니다.

Interceptor와는 완전히 별개이며, URL 매핑 없는 내부 서비스 직접 호출에도 인가가 적용됩니다. Interceptor는 URL 기반이므로 내부 호출에서는 우회될 수 있습니다.

O/X

Q9. DelegatingFilterProxy가 JWT 검증 등 보안 로직을 직접 처리한다.

X — 오답

DelegatingFilterProxy는 이름 그대로 위임(Delegate)만 하는 Proxy입니다.

실제 로직은 Spring Container에서 관리하는 FilterChainProxy Bean이 처리합니다. DelegatingFilterProxy는 Tomcat과 Spring Container 사이의 연결 다리 역할만 합니다.

2

단답형

단답

Q1. Filter의 doFilter() 안에서 다음 Filter 또는 DispatcherServlet으로 요청을 전달하기 위해 호출하는 코드는?

정답

chain.doFilter(request, response)

이 호출을 생략하면 요청이 그 자리에서 차단됩니다. JWT 검증 실패 시 의도적으로 생략해 401을 반환하는 패턴에 사용합니다.

단답

Q2. Interceptor를 DispatcherServlet에 등록할 때 오버라이드하는 인터페이스와 메서드는?

정답

WebMvcConfigurer 인터페이스의 addInterceptors(InterceptorRegistry registry) 메서드

registry.addInterceptor(interceptor).addPathPatterns("/api/**") 형태로 URL 패턴도 지정합니다.

단답

Q3. Spring Container에서 Bean의 기본 스코프(Scope)는 무엇인가? 그리고 이것이 의미하는 바는?

정답

Singleton — 애플리케이션 전체에서 Bean 인스턴스가 딱 1개만 생성됩니다.

모든 HTTP 요청이 동일한 Bean 인스턴스를 공유하므로, Bean에 상태(인스턴스 변수)를 저장하면 동시성 문제가 발생할 수 있습니다.

단답

Q4. Interceptor에서 현재 로그인한 사용자의 인증 정보(Authentication)를 가져오는 코드를 작성하라.

정답

SecurityContextHolder.getContext().getAuthentication()

Spring Security가 Filter 레이어에서 SecurityContextHolder에 Authentication을 저장해 두었기 때문에, 이후 단계인 Interceptor에서 이렇게 읽을 수 있습니다.
