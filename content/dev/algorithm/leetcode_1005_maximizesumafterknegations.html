Maximize Sum Of Array After K Negations

손으로 잡은 그리디 방향은 맞았고, 이후엔 계산량을 줄이는 재구성이었다

언어: Java 분류: 그리디 핵심 기법: 정렬 + 홀짝 트릭

문제

배열 nums와 정수 k가 주어진다. 원소 하나를 골라 부호를 뒤집는 연산을 정확히 k번 수행한다 (같은 원소를 여러 번 골라도 됨). k번 수행한 뒤 배열 합의 최댓값을 구한다.

2

손으로 먼저 잡은 알고리즘

코드를 짜기 전에 종이에 정리한 핵심 관찰은 두 가지였다.

관찰 1 - 음수 영역에 갇혀있는 경우

음수가 남아있으면 양수 영역이 아니라 음수 영역에서 제일 작은 값(가장 음수인 값)을 뒤집는 게 이득이다.

관찰 2 - 음수가 모두 사라진 경우

더 이상 음수가 없으면 양수 영역에서 제일 작은 값을 뒤집는다.

핵심 두 관찰을 합치면 결국 "매 스텝마다 전체에서 최솟값 하나를 뒤집는다"는 하나의 규칙으로 정리된다. minus가 비어있지 않으면 그 최솟값이 항상 전체 최솟값이고, 비어있으면 plus의 최솟값이 전체 최솟값이기 때문이다.

코드로 옮기기 전에 잡은 스케치:

손으로 잡은 스케치 (pseudo) 
int[] plus, int[] minus
int minPlus, int minMinus

for (n : arr) {
    if (n > 0) plus.add(n)
    else minus.add(n)
}

while (k > 0) {
    if (minus.size() > 0) {
        minM = min(minus)
        minus.remove(minM)
        plus.add(-1 * minM)
    } else {
        minP = min(plus)
        plus.remove(minP)
        plus.add(-1 * minP)   // minus로 옮기는 걸 빠뜨린 부분, 구현 때 수정
    }
    k--
}

1차 구현 - 정확하지만 O(k·n)

Solution.java — 1차 구현 
public int largestSumAfterKNegations(int[] nums, int k) {
    int sum = 0;
    List<Integer> plus = new ArrayList<>();
    List<Integer> minus = new ArrayList<>();

    for (int n : nums) {
        if (n >= 0) plus.add(n);
        else minus.add(n);
    }

    while (k > 0) {
        if (minus.size() > 0) {
            int minM = Collections.min(minus);
            minus.remove(Integer.valueOf(minM));
            plus.add(-minM);
        } else {
            int minP = Collections.min(plus);
            plus.remove(Integer.valueOf(minP));
            minus.add(-minP);
        }
        k--;
    }

    for (int n : plus) sum += n;
    for (int n : minus) sum += n;
    return sum;
}

로직 자체는 정확하다. 매 스텝 "전체 최솟값을 뒤집는다"는 원래 그리디와 동일하게 동작하기 때문에, {3, -1, 0, 2}, k=3 같은 0 포함 케이스로 직접 추적해도 정답 6이 나온다.

문제점 Collections.min과 list.remove(Integer.valueOf(...))가 매 반복 O(n)이라, k번 도는 전체가 O(k·n)이다. 제약이 n, k ≤ 10^4라 최악의 경우 10^8 연산 + ArrayList<Integer> 오토박싱 오버헤드까지 겹쳐서 시간초과 위험이 있다.

최적화 - 정렬 + 홀짝 트릭, O(n log n)

핵심 관찰은 "같은 원소를 짝수 번 뒤집으면 원상복구된다"는 것이다. 그러므로 누구를 몇 번 뒤집었는지는 중요하지 않고, 결과적으로 몇 개가 홀수 번 뒤집혔는지만 중요하다.

STEP 1 - 음수부터 순서대로 제거

정렬 후 앞에서부터 음수를 순서대로 양수로 뒤집으면서 k를 소진한다.

STEP 2 - k가 홀수로 남았을 때만 처리

k가 남았을 때 홀수면 절댓값이 가장 작은 원소 딱 하나만 한 번 더 뒤집는다. 짝수로 남으면 서로 상쇄되므로 그대로 둔다.

Solution.java — 최적화 
public int largestSumAfterKNegationsOptimized(int[] nums, int k) {
    int[] sorted = nums.clone();
    Arrays.sort(sorted);

    int idx = 0;
    while (idx < sorted.length && k > 0 && sorted[idx] < 0) {
        sorted[idx] = -sorted[idx];
        idx++;
        k--;
    }

    if (k % 2 == 1) {
        int minIdx = 0;
        for (int i = 1; i < sorted.length; i++) {
            if (sorted[i] < sorted[minIdx]) minIdx = i;
        }
        sorted[minIdx] = -sorted[minIdx];
    }

    int sum = 0;
    for (int n : sorted) sum += n;
    return sum;
}

두 메서드 모두 {4, 2, 3}, k=1 입력에서 동일하게 5를 반환함을 확인했다.

Takeaway

  • "매 스텝 최솟값을 찾아 뒤집는다"는 방향이 맞더라도, 그 탐색 자체를 O(1)/O(log n)으로 줄일 수 있는지, 혹은 반복 시뮬레이션 자체가 필요한지부터 점검해야 한다.
  • "짝수 번 연산은 취소된다"는 성질이 보이면, 반복 시뮬레이션을 홀짝 판정 문제로 치환할 수 있는지 검토한다 - 토글/부호 뒤집기 계열 그리디에서 자주 나오는 패턴이다.
  • 손으로 먼저 잡은 방향(매 스텝 최솟값 뒤집기)은 그 자체로 틀리지 않았다. 이후 최적화는 로직 교체가 아니라 같은 로직의 계산량을 줄이는 재구성이었다.
