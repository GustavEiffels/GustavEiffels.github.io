Ch 1

JVM 메모리 구조

1. Method Area (Metaspace)
  • 클래스 정보(메서드, 필드, 상수풀), static 변수가 저장되는 곳
  • 클래스 로더가 클래스를 읽어들일 때 여기에 적재됨
  • Java 8부터 PermGen이 사라지고 Metaspace로 대체됨 — 네이티브 메모리 사용, OS 메모리 한도까지 확장 가능
2. Heap
  • new로 생성한 객체가 실제로 저장되는 공간
  • 모든 스레드가 공유
  • GC가 관리하는 핵심 대상 — Stack과 달리 자동 해제되지 않으므로
3. Stack
  • 스레드마다 1개씩 생성 (스레드 개별 소유, 공유 안 됨)
  • 메서드 호출 시 스택 프레임이 쌓임 — 지역변수, 매개변수, 연산 중간값 저장
  • 메서드 종료 시 프레임 pop으로 자동 해제 (GC 대상 아님)
4. PC Register
  • 스레드마다 하나씩 존재, 현재 실행 중인 명령어 주소를 가리킴
5. Native Method Stack
  • Java가 아닌 네이티브 코드(C/C++) 호출 시 사용하는 스택
핵심 정리
GC가 실제로 관리하는 영역은 Heap 하나뿐이다. Stack의 지역변수는 메서드 종료 시 자동으로 사라지므로 GC 대상이 아니다.
Ch 2

GC (가비지 컬렉션)

Heap 내부 구조 — Young / Old Generation (공통 기초 개념)

Heap은 세대(Generation) 별로 나뉘어 있다. "대부분의 객체는 생성된 직후 금방 죽는다(weak generational hypothesis)"는 경험칙 때문 — 오래 살아남는 객체와 금방 죽는 객체를 같은 방식으로 검사하면 비효율적이라 영역을 나눠서 관리한다.

Young/Old 개념은 G1만의 것이 아니라 Serial GC 시절부터 내려온 HotSpot의 공통 모델이며, GC 종류마다 이를 물리적으로 구현하는 방식만 다르다.

영역설명
Eden새로 생성된 객체가 최초로 할당되는 영역
Survivor (S0, S1)Eden에서 살아남은 객체가 옮겨지는 곳. 둘 중 하나는 항상 비어 있고, GC 때마다 살아남은 객체가 한쪽 Survivor로 모이고 역할이 서로 교대됨
Old GenerationYoung에서 일정 횟수(age threshold) 이상 살아남은 객체가 승격(promotion)되는 곳. 검사 빈도가 낮음

GC 수거 대상 기준

수거 대상 기준은 하나다 — GC Root에서 도달 불가능(unreachable)한 객체.

GC Root란?

Mark 단계의 시작점. 아래 항목들이 GC Root에 해당한다.

  • Stack의 지역변수 (현재 실행 중인 메서드의 변수)
  • Method Area의 static 변수
  • JNI(Native) 참조
  • 실행 중인 스레드 자체

GC Root에서 출발해 참조를 따라갈 수 있는 객체 = reachable = 살아있는 객체. 어떤 경로로도 닿지 않는 객체 = unreachable = 수거 대상.

Java는 참조 카운팅 방식이 아니다

"이 객체를 가리키는 참조가 0개면 수거"하는 방식(Python 등)을 쓰지 않는다. 이유는 순환 참조 문제 때문이다.

순환 참조 문제 
A -> B
B -> A  (서로 참조)

두 객체 모두 GC Root에서 닿지 않아도
참조 카운트는 각각 1 -> 참조 카운팅 방식으로는 영원히 수거 못 함

Java는 GC Root에서의 도달 가능성으로 판단하므로, 순환 참조여도 GC Root에서 닿지 않으면 둘 다 수거한다.

참조가 끊기는 대표 케이스
참조 해제 예시 
void method() {
    Object obj = new Object();  // GC Root(Stack 지역변수)에서 참조
    obj = null;                 // 참조 끊김 -> 다음 GC 때 수거 대상
}                               // 메서드 종료 -> 지역변수 사라짐 -> 수거 대상
참조 종류에 따른 수거 시점 차이
참조 종류선언 방식수거 시점
Strong ReferenceObject obj = new Object()GC Root에서 닿는 한 절대 수거 안 됨 (일반적인 참조)
Soft Referencenew SoftReference<>(obj)메모리 부족 시 수거. 캐시 구현에 활용
Weak Referencenew WeakReference<>(obj)다음 GC 때 무조건 수거. WeakHashMap에서 사용

GC 동작 방식

  • STW Minor GC: Young Generation(Eden+Survivor)만 청소. 자주 일어나지만 대상 영역이 작아서 빠름. Minor GC도 STW다 — 대상 영역이 작아 짧을 뿐, 그 순간 모든 애플리케이션 스레드는 멈춤
  • STW Major GC / Full GC: Old Generation까지 포함해서 청소. 대상 영역이 크고 빈도는 낮지만 STW가 훨씬 오래 걸림
  • Stop-the-world(STW): GC가 동작하는 동안 GC 스레드를 제외한 모든 애플리케이션 스레드가 멈춤. 객체 그래프가 GC 도중 바뀌면 안 되기 때문에 발생
핵심: G1/ZGC가 concurrent 방식으로 일부 단계(marking 등)의 STW를 없앤 것이지, GC 자체가 STW 없이 동작하는 건 아니다. GC 튜닝의 핵심 목표는 결국 "STW 시간을 얼마나 줄이느냐"

System.gc()
  • 빈번 Eden 꽉 참 → Minor GC: 가장 흔한 케이스. 객체 생성 속도(allocation rate)에 따라 빈도가 결정됨
  • STW 김 Old Gen 임계치 초과 → Full GC: Minor GC보다 훨씬 드물지만 STW가 훨씬 길어 실질적 영향이 큼
  • Promotion Failure: Minor GC 중 Young→Old 승격할 공간이 Old Gen에 없으면 Minor GC가 Full GC로 격상
  • Metaspace 가득 참: 클래스 로딩이 과도하게 발생해 Metaspace가 꽉 차면 Full GC 유발 가능
  • System.gc() 명시 호출: 코드에서 직접 GC 요청. JVM이 반드시 따를 의무는 없지만 대부분 Full GC 실행
  • G1 주의 Evacuation Failure: concurrent 진행 중 살아있는 객체를 옮길 빈 Region이 없으면 STW Full GC로 fallback — G1 환경에서 갑작스러운 Full GC의 주요 원인
튜닝 방향: "Minor GC를 줄이려면 Eden을 키워라" / "Full GC를 줄이려면 Old Gen이 차는 속도를 늦춰라"

GC 알고리즘 기본기

Mark 단계는 GC Root에서 출발해 reachable 객체를 표시하는 것이다. Mark 안 된 객체(unreachable)가 아래 단계의 처리 대상이 된다.

단계설명주로 사용
Mark살아있는(reachable) 객체를 GC Root부터 따라가며 표시전체 공통
SweepMark 안 된(unreachable) 객체를 메모리에서 제거Old Generation
CompactSweep 후 남은 객체들을 메모리 한쪽으로 모아 단편화(fragmentation) 방지Old Generation
Copying살아있는 객체를 다른 영역(Eden→Survivor)으로 복사하고 기존 영역은 통째로 비움. 살아남는 객체가 적을 때 효율적Young Generation

GC 종류

Serial GC
  • 가장 단순한 형태 — Minor GC, Major GC 모두 단일 스레드로 수행
  • Young(Eden + Survivor)은 Copying, Old는 Mark-Sweep-Compact 알고리즘 사용
  • GC 도중 애플리케이션 스레드는 전부 멈춤(STW) — 힙이 크면 STW 시간이 그만큼 길어짐
  • 실제 사용 환경: 임베디드 JVM, 단일 CPU 환경, CLI 도구. 현대 서버 애플리케이션에서는 거의 사용하지 않음
  • 옵션: -XX:+UseSerialGC
Serial GC 동작 
[Minor GC - Eden full]
  App thread 1  |---STOPPED---|
  App thread 2  |---STOPPED---|
  GC thread 1   |mark->copy->sweep| (혼자 전부 처리)
  App threads   |resumed|

[Major GC - Old Gen full]
  App thread 1  |----------STOPPED----------|
  App thread 2  |----------STOPPED----------|
  GC thread 1   |mark->sweep->compact| (혼자 전부 처리, 더 오래 걸림)
  App threads   |resumed|
  • 멀티코어 CPU를 전혀 활용하지 못함 — 코어가 몇 개든 GC는 스레드 1개만 동작
  • 힙이 클수록 STW 시간이 무제한으로 길어짐, 제어 불가
  • 수백 MB 이하 소형 힙 환경에서만 선택할 것
Parallel GC
  • Heap 구조와 알고리즘은 Serial GC와 동일 — 차이는 여러 스레드로 GC를 병렬 수행한다는 점뿐
  • 목표는 지연시간이 아니라 처리량(throughput) 최대화. Java 8 기본값
  • -XX:MaxGCPauseMillis, -XX:GCTimeRatio로 처리량 vs 지연시간 조정 가능
  • 실제 사용 환경: 배치 서버, Spark/Hadoop 데이터 파이프라인, Java 8 기반 레거시 서버
  • 옵션: -XX:+UseParallelGC
Parallel GC 동작 
[Minor GC - Eden full]
  App thread 1  |---STOPPED---|
  App thread 2  |---STOPPED---|
  GC thread 1   |mark+copy: 힙 1/4|  -+
  GC thread 2   |mark+copy: 힙 2/4|   | 병렬 수행
  GC thread 3   |mark+copy: 힙 3/4|   |
  GC thread 4   |mark+copy: 힙 4/4|  -+
  App threads   |resumed|
  -> Serial 대비 STW 시간이 짧아짐 (GC 스레드 수만큼 단축)
  • STW 자체는 힙 전체 대상 — Full GC 시 힙이 클수록 pause가 수 초에 달할 수 있음
  • pause 시간을 예측하거나 제어할 수 없음 (G1처럼 목표치 설정 없음)
  • 저지연이 필요한 API 서버에는 부적합. 배치/데이터 파이프라인처럼 처리량 우선 환경에서만 사용
G1 GC (Garbage First)
  • Java 9+ 기본 GC. Region 기반 구조 — Heap을 동일 크기의 작은 Region(보통 1~32MB, 총 2048개 내외)으로 쪼개고, 각 Region에 Eden/Survivor/Old/Humongous 역할을 동적으로 부여. Region 하나는 반드시 하나의 역할만 담당
  • "Garbage First" — 쓰레기가 가장 많은 Region부터 골라서 회수 → 같은 노력으로 가장 많은 메모리 확보
  • Concurrent Marking: Old Region의 쓰레기 비율을 애플리케이션을 멈추지 않고 백그라운드에서 계산
  • Evacuation: 선택된 Region의 live 객체를 새 Region으로 복사 — 기존 Region은 통째로 Free Region이 됨
  • Mixed GC: Young Region + 쓰레기 많은 Old Region을 함께 청소
  • -XX:MaxGCPauseMillis=200: G1이 목표 안에 맞게 처리할 Region 개수를 스스로 조절. 예측 가능한 것이 핵심
  • Evacuation Failure 시 Full GC로 fallback
  • 실제 사용 환경: Spring Boot API 서버, 현대 Java 웹 서비스. 힙 4GB 이상에서 유리
G1 GC 동작 
[백그라운드 - STW 없음]
  App threads   |running|
  GC thread     |concurrent marking: Region별 쓰레기 비율 계산|

[Young GC (Evacuation pause) - STW]
  App threads   |--STOPPED--|
  GC threads    |live 객체를 선택된 Young Region -> 새 Region으로 복사|
  App threads   |resumed|

[Mixed GC (Evacuation pause) - STW]
  App threads   |--STOPPED--|
  GC threads    |Young Region + 쓰레기 많은 Old Region 선택해서 복사|
  App threads   |resumed|
  -> pause 시간 목표 안에 맞게 Region 수를 자동 조절, 나머지는 다음으로 미룸
G1 GC 작동 주기 순서
G1 GC 주기 
[1] Young GC (반복)
    Eden Region 가득 참
    STW: Eden + Survivor Region에서 live 객체 복사
    - age 낮은 객체 -> 새 Survivor Region
    - age >= threshold -> Old Region (승격)
    - 기존 Eden/Survivor Region -> Free Region

[2] Concurrent Marking 시작
    Old Region 점유율이 IHOP(기본 45%) 초과 시

    a. Initial Mark   (STW, 짧음)  : Old GC Root 표시. Young GC에 piggybacked
    b. Root Scanning  (concurrent) : Survivor -> Old 참조 스캔
    c. Marking        (concurrent) : 전체 Heap live 객체 표시
    d. Remark         (STW)        : 마킹 마무리. concurrent 중 변경된 참조 처리
    e. Cleanup        (STW+con)    : 빈 Region 즉시 회수, Region별 쓰레기 비율 계산

[3] Mixed GC (반복)
    쓰레기 많은 Old Region 선정 후 Young + Old Region 함께 Evacuation
    MaxGCPauseMillis 목표 안에 맞게 Region 수 자동 조절
    여러 번 반복하며 Old Region 점진적으로 정리

[4] Full GC (Fallback - 피해야 함)
    Evacuation 중 빈 Region이 없을 때 발생
    전체 Heap 대상 Mark-Sweep-Compact (STW, 매우 오래 걸림)
객체 입장에서 G1 GC 처리 순서
객체 생명 주기 (G1) 
[1] 생성
    new Object() -> Eden Region에 할당

[2] Young GC 발생 (Eden 가득 참, STW)
    죽은 객체: Eden Region 통째로 버려짐 (Free Region으로 전환)
    살아있는 객체: Survivor Region으로 복사, age = 1

[3] Survivor에서 반복 생존
    Young GC 때마다 다른 Survivor Region으로 복사, age 증가
    age < threshold(기본 15): 계속 Survivor
    age >= threshold: Old Region으로 승격(Promotion)

[4] Old Region 안착
    Young GC 대상에서 제외됨
    Concurrent Marking이 백그라운드에서 live/dead 판별

[5] Old Region에서 죽음 (GC Root 도달 불가 판정)
    Concurrent Marking에서 unreachable로 표시
    Mixed GC 때 해당 Region 선택 -> live 객체만 새 Region으로 복사
    기존 Old Region -> Free Region으로 반환

[예외] Humongous 객체 (Region 크기의 50% 이상)
    Eden/Survivor 건너뛰고 바로 연속된 Old Region에 직접 할당
    Concurrent Marking에서 unreachable 확인 즉시 회수
G1 GC — 단점 및 고려사항
  • Concurrent Marking이 CPU를 나눠 씀 — 백그라운드에서 계속 돌기 때문에 Parallel GC 대비 처리량(throughput)이 낮을 수 있음
  • 힙이 작으면 오히려 역효과 — Region 관리 오버헤드로 수백 MB 소형 힙에서는 Serial/Parallel이 더 나음
  • Evacuation Failure 시 Full GC fallback — 예방 못 하면 갑자기 수 초짜리 STW 발생. 힙을 여유 있게 설정해야 함
  • 튜닝 파라미터가 많아(IHOP, MaxGCPauseMillis 등) 잘못 건드리면 오히려 성능 저하

ZGC
  • 수십~수백 GB, TB급 힙에서도 STW를 1ms 미만으로 유지하는 게 목표 (힙 크기에 비례하지 않음)
  • Region 기반이지만 Region 크기가 가변적(ZPage)
  • Marking, Relocation, Reference 업데이트까지 거의 전부 애플리케이션과 동시에(concurrent) 수행
  • Colored Pointer: 객체 참조(포인터) 자체에 별도 비트를 심어서, 객체 이동 여부/marking 상태를 포인터만 보고 파악
  • Load Barrier: 애플리케이션이 참조를 읽을 때마다 실행되는 짧은 코드 — 객체가 GC 도중 이동했어도 즉시 새 위치로 포인터를 고쳐줌
  • STW는 root 스캔처럼 아주 짧은 동기화 지점에만 발생
  • JDK 21부터 Young/Old를 나누는 generational 모드를 지원해 처리량까지 개선됨
  • 실제 사용 환경: 금융 거래 시스템(수 ms 응답 SLA), 실시간 광고 입찰(RTB), 대용량 인메모리 캐시(수백 GB 힙)
ZGC 동작 
[대부분 concurrent - STW 거의 없음]
  App threads   |running ------------------------------------>|
  GC threads    |concurrent mark|concurrent relocate|ref upd.|
                 colored pointer + load barrier로 포인터 실시간 보정

[STW는 root 스캔 구간만 - 수 ms]
  App threads   |STOP|resumed|         |STOP|resumed|
  GC threads        |root scan|             |root scan|
  -> 힙 크기(수백 GB)와 무관하게 pause 시간이 일정하게 유지됨
  • Load Barrier 비용 — 모든 참조 읽기마다 barrier 코드가 실행되므로 참조를 많이 읽는 코드에서 CPU 오버헤드 발생
  • Java 15 이상 필요 — 이전 버전에서는 experimental 상태
  • JDK 21 이전까지 Generational 미지원 — 단명 객체가 많은 앱에서 처리량 불리. Java 21+ 사용 시 Generational ZGC 권장
  • 실전 운영 사례가 G1보다 적어 튜닝 레퍼런스/노하우 부족

Ch 3

확인 문제

Q1. JVM 메모리 구조 중 GC가 관리하는 영역은?

Stack은 메서드 종료 시 자동 pop 해제, Method Area는 클래스 로더가 관리한다. Heap에 할당된 객체만 명시적 해제 주체가 없어 GC가 담당한다.

Q2. Minor GC와 STW의 관계로 올바른 것은?

Minor GC도 STW는 반드시 발생한다. Young Generation만 대상이라 멈추는 시간이 짧을 뿐이다. "Minor GC = STW 없음"은 흔한 오해다.

Q3. Java GC가 참조 카운팅 방식을 채택하지 않는 이유는?

A→B, B→A 순환 참조 시 GC Root에서 도달 불가해도 카운트가 0이 되지 않아 영원히 수거 못 한다. Java는 GC Root 도달 가능성(reachability)으로 판단해 순환 참조도 수거한다.

Q4. Serial GC vs Parallel GC — 핵심 차이는?

Serial은 단일 스레드, Parallel은 멀티스레드로 GC 작업을 처리한다. Heap 구조(Eden/S0/S1/Old)와 알고리즘(Copying + Mark-Sweep-Compact)은 동일하다.

Q5. G1 GC에서 MaxGCPauseMillis 옵션의 역할은?

G1은 목표 pause 시간 내에 처리할 Region 수를 스스로 결정한다. 처리 못 한 Region은 다음 Mixed GC로 미룬다. "빠른" GC가 아니라 "예측 가능한" GC가 목표다.

Q6. G1 GC에서 갑작스러운 Full GC의 주요 원인은?

Evacuation = 선택 Region의 live 객체를 빈 Region으로 복사. 복사 중 Free Region 소진 → 복사 포기 → STW Full GC fallback. 예방: -Xmx 충분히, IHOP 낮게 설정.

Q7. G1 GC Region의 특징으로 올바른 것은?

G1 Heap은 동일 크기 Region으로 나뉘고 각 Region은 Eden/Survivor/Old/Humongous/Free 중 하나의 역할만 담당한다. GC 완료 후 역할은 재배정된다.

Q8. ZGC가 STW를 1ms 미만으로 유지하는 핵심 메커니즘은?

Colored Pointer: 참조 포인터 자체에 GC 상태 비트를 심어 객체 이동 여부 파악. Load Barrier: 참조 읽을 때마다 실행, 이동된 객체 포인터 즉시 보정. 이 둘로 marking과 relocation을 애플리케이션과 동시에 수행한다.

Q9. G1 GC에서 Humongous 객체(Region 크기 50% 이상)의 처리 방식은?

Humongous 객체는 Eden/Survivor를 건너뛰고 연속된 Old Region에 직접 할당된다. unreachable 확인 시 Concurrent Marking에서 즉시 회수 가능. 연속 Region이 필요해 단편화 위험이 있다.

Q10. STW 발생 빈도 — Serial GC vs Parallel GC 비교는?

STW 빈도는 "Eden이 얼마나 빨리 차느냐"(allocation rate)에 달려 있다. 스레드 수가 달라도 allocation rate가 같으면 빈도는 동일하다. 차이는 STW 지속 시간 — Parallel이 멀티스레드라 짧게 끝난다.

Q11. 새로 생성된 일반 객체가 G1 GC 안에서 처리되는 순서로 올바른 것은?

일반 객체(Region 크기 50% 미만) 기준:
Eden Region 할당 → Eden 가득 참 → Minor GC 발동
→ live 객체 Survivor Region 이동, age+1
→ Minor GC 반복 → Survivor 간 이동하며 age 누적
→ age >= 15(기본값) → Old Region으로 Promotion
→ Old Region이 IHOP 임계값 초과 → Concurrent Marking → Mixed GC → 수거
