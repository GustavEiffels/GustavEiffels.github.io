실시간 작업 상태 모니터링, 어떤 방식을 선택해야 했나

SSE vs Polling+Cache vs SSE+SharedWorker — 운영 화면에 작업 진행 상태를 띄우면서 실제로 부딪힌 고민과 검토 기록

CH 01

왜 이 고민이 시작됐나 — 배경

1

요구사항: 작업 상태를 실시간으로 보여줘야 했다

배치로 도는 작업(Job)들을 PENDING → RUNNING → COMPLETED/FAILED 흐름으로 운영 화면에서 추적하는 기능이 필요했다. 처음엔 새로고침이면 충분하다고 봤는데, 화면을 켜놓고 계속 지켜보는 사람이 생기면서 "새로고침 없이 자동으로 갱신됐으면 좋겠다"는 요청이 들어왔다. 여기서부터 고민이 시작됐다.

선택지는 결국 셋이었다. 서버가 변경을 감지해서 바로 밀어줄지(Push), 클라이언트가 주기적으로 물어볼지(Pull), 아니면 그 중간 절충안을 찾을지. 이걸 정리하면서 내 언어로 다시 한 번 짚고 넘어가보려고 한다.

📌 자기 교정:
처음엔 "서버가 변경되는 순간 바로 밀어주면 끝이지" 하고 SSE(Server-Sent Events)부터 붙였다. 그런데 운영 화면 특성상 같은 대시보드를 여러 탭으로 띄워놓고 보는 사람들이 있다는 걸 뒤늦게 알았고, 거기서 예상 못한 벽에 부딪혔다.
2

실제로 마주친 문제 — 탭을 여러 개 열면 멈춘다

같은 도메인에서 모니터링 화면을 6개 넘게 열어두면 7번째 탭부터 연결이 응답 없이 멈췄다. 처음엔 서버 쪽 에미터(Emitter) 누수라고 의심해서 로그부터 뒤졌는데, 원인은 서버가 아니라 브라우저의 HTTP/1.1 동시 연결 제한이었다. 

[localhost:8080 | Chrome / Firefox / Safari 공통]

Tab 1 --SSE--> [연결 1 점유, 탭이 닫힐 때까지 유지]
Tab 2 --SSE--> [연결 2 점유]
Tab 3 --SSE--> [연결 3 점유]
Tab 4 --SSE--> [연결 4 점유]
Tab 5 --SSE--> [연결 5 점유]
Tab 6 --SSE--> [연결 6 점유]   <-- 도메인당 한도 도달
Tab 7 --SSE--> [요청이 큐에서 대기 -> 화면이 그대로 멈춤]
이 시점에서 알게 된 것 HTTP/1.1은 브라우저가 같은 출처(origin)에 동시에 맺을 수 있는 TCP 연결을 6개로 제한한다. 이 한도는 탭 단위가 아니라 브라우저 프로세스 전체에서 공유된다. SSE, WebSocket, Long Polling처럼 "연결을 계속 들고 있는" 방식은 전부 이 한도의 영향을 받는다.

그래서 질문이 바뀌었다. "SSE를 어떻게 고칠까"가 아니라 "실시간성, 연결 한도, 구현 난이도를 같이 만족시키는 방법이 뭘까"로. 아래는 그 과정에서 SSE / Polling+Cache / SSE+SharedWorker를 중심으로 따져보고, 겸사겸사 Long Polling과 WebSocket 계열까지 들여다본 기록이다. 잘못 짚었던 부분은 자기 교정 박스로 따로 표시한다.

CH 02

본격적으로 저울질한 세 가지 — SSE / Polling+Cache / SSE+SharedWorker

1

왜 이 셋으로 좁혔는가

실시간 갱신을 구현하는 방법은 생각보다 여러 갈래였지만, 결국 우리 상황(운영자가 직접 화면을 켜놓고 보는 대시보드, 수 초 정도의 지연은 허용 가능, 서버 → 클라이언트 단방향 전달이면 충분)에 맞춰 고민의 무게를 둔 것은 다음 세 가지였다. 

[1] SSE (per-tab)        서버가 변경 시 즉시 Push   |  탭마다 연결 1개 점유   |  6탭 한도에 걸림
[2] Polling + Cache      클라이언트가 주기적으로 Pull |  요청 후 연결 즉시 반환 |  탭 수 영향 없음
[3] SSE + SharedWorker   탭들이 연결 1개를 공유      |  브라우저 전체 1개 점유 |  Push 유지 + 한도 해결

SSE는 "이미 만들어 둔 것을 살릴 수 있는가"라는 관점에서, Polling+Cache는 "당장 가장 안전하고 빠르게 적용할 수 있는가"라는 관점에서, SSE+SharedWorker는 "구조를 크게 바꾸지 않으면서 한도 문제만 해결할 수 있는가"라는 관점에서 각각 후보에 올랐다. 아래에서 하나씩 어떤 기준으로 따져봤는지 정리한다.

CH 03

1순위 후보 — SSE (per-tab)

SSE
서버가 변경되는 순간 즉시 Push
가장 먼저 손이 간 방식. 실시간성은 좋지만 연결을 계속 점유한다는 게 발목을 잡았다.

각 탭이 GET /api/sse/stream으로 구독하면 서버는 SseEmitter를 만들어 레지스트리에 등록하고, 스케줄러가 주기적으로 상태를 조회해서 등록된 에미터 전체에 브로드캐스트하는 구조다. 구현 자체는 어렵지 않았고, 변경이 생기면 지연 없이 화면에 바로 반영되는 게 가장 큰 장점이었다.

SseController.java 
@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter subscribe() {
    String id = UUID.randomUUID().toString().substring(0, 8);
    SseEmitter emitter = new SseEmitter(1_800_000L);

    emitters.put(id, emitter);

    Runnable cleanup = () -> emitters.remove(id);
    emitter.onCompletion(cleanup);
    emitter.onTimeout(cleanup);
    emitter.onError(e -> cleanup.run());

    return emitter; // 응답이 열린 채로 유지 = 연결 슬롯을 계속 점유
}

문제는 마지막 줄 주석에 다 있다. return emitter 이후에도 응답 스트림이 닫히지 않고 계속 열려 있다는 것. 이 "계속 열려 있음"이 브라우저의 동시 연결 한도를 그대로 잡아먹는 원인이었다.

항목검토 결과
실시간성변경 즉시 반영, 체감 지연 거의 없음
브라우저 연결 한도HTTP/1.1 기준 도메인당 6개 — 7번째 탭부터 블로킹
서버 자원연결을 유지하는 만큼 에미터 레지스트리가 계속 메모리를 점유
스케일아웃인스턴스마다 에미터가 따로 존재 — Redis Pub/Sub 같은 별도 처리 필요
왜 그대로 못 썼나 실시간성 자체는 마음에 들었지만, 여러 탭을 동시에 열어두는 사용 패턴과 정면으로 부딪혔다. "탭은 6개까지만 열어주세요"라고 안내하는 건 답이 될 수 없었다.
CH 04

가장 현실적인 대안 — Polling + Cache

Polling
클라이언트가 주기적으로 물어보고, 서버는 캐시로 받아넘긴다
한도 문제에서 완전히 자유롭고, 구현도 가장 단순했다 — 결국 가장 먼저 적용한 방식.

SSE의 한도 문제를 알고 나서 가장 먼저 떠올린 대안이 Polling이었다. "주기적으로 다시 물어보면 되는 거 아닌가" 정도의 단순한 아이디어였는데, 걸리는 부분은 하나였다. "탭이 여러 개면 그만큼 DB도 자주 조회하게 되지 않나?" 그래서 스케줄러가 한 번만 조회해서 캐시에 적재하고, 클라이언트 요청은 캐시에서만 응답하는 구조로 다듬었다.

JobService.java 
// 스케줄러가 5초마다 한 번 호출 — DB 조회는 여기서 끝
public void refreshCache() {
    Cache cache = cacheManager.getCache("activeJobs");
    if (cache != null) cache.put("list", getActiveJobs());
}

// 탭이 몇 개든 이 메서드는 캐시만 보고 즉시 반환
public List<Job> getCachedActiveJobs() {
    Cache.ValueWrapper w = cacheManager.getCache("activeJobs").get("list");
    return (w != null) ? (List<Job>) w.get() : List.of();
}

캐시 TTL은 스케줄러 주기(5초)의 6배인 30초로 잡았다. 갱신되기 전에 만료돼버리는 일을 막기 위한 여유값이다. 적용해보니 탭을 몇 개 열든 DB 조회 횟수는 그대로였고, 응답도 1ms 안쪽으로 충분히 빨랐다.

항목검토 결과
브라우저 연결 한도해당 없음 — 탭 100개를 열어도 정상 동작
DB 부하탭 수와 무관하게 스케줄러가 1회만 조회, 캐시가 흡수
실시간성폴링 주기(5초)만큼의 지연은 감수해야 함
구현 난이도캐시 적재 + 캐시 조회, 단 두 메서드로 끝남
스케일아웃Caffeine을 Redis로 바꾸면 다중 인스턴스에도 그대로 대응
지금 당장의 답으로 채택한 이유 수 초 단위 지연은 운영 모니터링 화면에서 충분히 허용되는 수준이고, 한도 문제와 DB 부하 우려를 동시에 해소했다. 구현도 단순해서 리스크 없이 바로 적용할 수 있었다. 그래서 1차로는 이 방식으로 정했다.
CH 05

절충안으로 떠올린 — SSE + SharedWorker

SSE + SW
탭들이 SSE 연결 하나를 같이 쓴다
"실시간성을 포기하지 않으면서 한도 문제만 없앨 수는 없을까"에 대한 답으로 떠올린 방식.

Polling+Cache로 일단 문제는 풀었지만 "나중에 더 빠른 반영이 필요해지면 어떡하지"라는 물음표는 남아 있었다. 그러다 찾은 게 SharedWorker다. 같은 출처의 탭들이 JS 워커 하나를 공유할 수 있고, 그 워커가 대표로 SSE 연결을 1개만 맺으면 — 탭이 몇 개든 서버 입장에서는 연결 1개로만 보인다. 이 구조가 꽤 마음에 들었다. 

Tab A --MessagePort--> |              |
Tab B --MessagePort--> | SharedWorker |--SSE 연결 1개-- Server
Tab C --MessagePort--> |              |
Tab N --MessagePort--> |              |

탭이 N개여도 서버로 가는 SSE 연결은 항상 1개
브라우저가 점유하는 연결 슬롯도 1개 -> 6개 한도와 무관해짐
shared-worker.js (개념 검증용 스케치) 
const ports = new Set();
let es = null;

function connect() {
    es = new EventSource('/api/sse/stream');
    es.addEventListener('jobs', e => {
        ports.forEach(p => p.postMessage(e.data)); // 받은 걸 모든 탭에 그대로 전달
    });
}

self.onconnect = e => {
    const port = e.ports[0];
    ports.add(port);
    port.start();
    if (!es) connect(); // 최초 연결만 워커가 대표로 수행
};
가장 끌렸던 지점 이건 순수하게 클라이언트 측 변경이라 서버의 SseController는 손댈 필요가 없다. "서버는 그대로 두고 클라이언트만 감싸면 한도 문제가 사라진다"는 점에서 가장 깔끔한 절충안으로 보였다.
📌 자기 교정:
처음엔 "클라이언트만 바꾸면 되니까 사실상 공짜 아닌가" 하고 너무 쉽게 봤는데, 확인해보니 Safari가 SharedWorker를 지원한 게 16버전(2022년)부터다. 구형 환경을 완전히 배제할 수 없다면 적용 전에 반드시 짚고 넘어가야 할 변수였다. 그래서 "지금 당장"보다는 "실시간성이 정말 필요해지는 시점"의 카드로 남겨두기로 했다.
항목검토 결과
브라우저 연결 한도해결 — 탭이 몇 개든 SSE 연결은 1개
실시간성SSE의 즉시 Push 그대로 유지
서버 변경불필요 — 기존 SseController를 그대로 재사용
브라우저 호환성Safari 16+ 필요 — 구형 환경에서는 주의
스케일아웃서버 쪽 에미터 분리 문제는 그대로 남음 (Redis Pub/Sub 별도 검토 필요)
CH 06

겸사겸사 살펴본 것들 — Long Polling과 WebSocket 계열

1

"이것도 후보가 될 수 있을까?" 하고 짚어본 것들

위 세 가지로 결론을 좁혀가는 와중에 "혹시 더 나은 방식을 놓치고 있는 건 아닐까" 싶어서 Long Polling과 WebSocket 계열도 같이 들여다봤다. 결과적으로 둘 다 채택하지는 않았는데, 왜 아닌지를 적어두면 나중에 비슷한 고민을 또 할 때 시간을 아낄 수 있을 것 같다.

Long Poll
서버가 변경이 생길 때까지 응답을 들고 있는 방식
SSE보다 구현은 더 복잡한데, 한도 문제는 똑같이 가지고 있었다.

클라이언트가 요청을 보내면 서버가 DeferredResult로 응답을 보류하고 있다가, 변경이 감지되면 그제서야 응답을 내려주는 방식이다. 그런데 이 "보류하는 동안"에도 결국 HTTP 연결은 유지된 상태라서, SSE와 똑같이 6개 한도에 걸린다. 게다가 타임아웃 처리, 대기 큐 동시성 관리까지 신경 쓸 게 더 많아져서 "SSE보다 복잡한데 얻는 게 없다"는 결론으로 빠르게 정리됐다.

WebSocket
양방향 통신 — 그런데 우리에게 양방향이 필요했나?
클라이언트 -> 서버로 보낼 데이터가 없는 모니터링 화면에는 과한 선택지였다.

WebSocket은 서버와 클라이언트가 서로 메시지를 주고받을 수 있는 양방향 연결이다. 강력한 만큼 핸드셰이크, ping/pong, 세션 관리 등 신경 쓸 게 늘어난다. 그런데 우리가 만들던 화면은 "서버 상태를 보여주기만 하면 되는" 단방향 모니터링이었고, 클라이언트가 서버로 보낼 데이터 자체가 없었다. 거기다 연결을 유지한다는 점에서 한도 문제도 SSE와 동일하게 가지고 있었으니, 굳이 더 무거운 도구를 쓸 이유가 없었다.

같은 맥락에서 WebSocket + SharedWorker 조합도 살펴봤는데, 양방향이 필수인 채팅이나 공동 편집 같은 서비스에는 어울리겠지만, 우리 케이스에는 구현 복잡도만 가장 높은 선택지였다. "양방향이 필요해지는 완전히 다른 서비스를 만들 때"를 위해 알아만 두기로 했다.

이 둘을 들여다보고 얻은 것 Long Polling과 WebSocket 모두 "연결을 유지한다"는 점에서 SSE와 같은 한계를 공유한다는 걸 확인했다. 덕분에 "연결을 계속 들고 있을 것인가, 아닌가"가 이 고민 전체를 가르는 진짜 기준이라는 게 더 명확해졌다.

최종적으로 정리한 우선순위

돌이켜보면 이 고민의 핵심은 결국 두 가지였다. "연결을 계속 들고 있을 것인가, 매번 새로 물어볼 것인가", 그리고 "실시간성을 어디까지 양보할 수 있는가". 이 기준으로 정리한 우선순위는 다음과 같다.

1st
Polling + Cache
지금 바로 적용 가능. 탭 수 제한 없음. 구현이 단순해서 리스크가 가장 적었다. 1차로 이 방식을 채택했다.
현재 적용 / 단기
2nd
SSE + SharedWorker
"5초 지연도 아쉽다"는 요구가 커지면 그때 전환할 카드. 서버 변경 없이 클라이언트만 바꾸면 된다.
실시간성 요구 시 / 중기
3rd
WebSocket(+SharedWorker)
양방향 통신이 정말 필요해지는, 지금과는 다른 종류의 화면을 만들 때를 위해 기억해두는 선택지.
양방향 필수 시에만
이번 검토에서 남은 결론 "실시간"이라는 말을 듣자마자 SSE나 WebSocket부터 떠올렸는데, 정작 따져봐야 했던 건 연결을 계속 들고 있는 방식이 우리 사용 패턴(다중 탭)과 맞는지였다. 당장은 Polling+Cache로 안전하게 풀고, SSE+SharedWorker는 다음 단계 카드로 남겨두는 것 — 이번 고민 끝에 내린 가장 현실적인 답이다.
CH 08

관련 문제 + 해설 (Self Quiz)

먼저 질문 박스(파란 라인)만 보고 스스로 답해본 다음, 노란 해설 박스와 맞춰보면 기억이 더 단단해진다.

Q1. — 원인 진단

같은 도메인에서 SSE 모니터링 화면을 7개 이상 열었더니 7번째 탭부터 응답이 없다. 서버 로그에는 에러가 없다. 가장 먼저 의심해야 할 원인은 무엇이고, 왜 서버가 아니라 거기인가?

💡 해설: 브라우저의 HTTP/1.1 도메인당 동시 연결 제한(6개)을 의심해야 한다. 이 한도는 탭 단위가 아니라 브라우저 프로세스 전체에서 공유되며, SSE처럼 응답을 계속 열어두는 연결은 탭이 닫힐 때까지 슬롯 하나를 영구히 점유한다. 서버 로그가 깨끗한 이유도 여기 있다 — 요청이 서버에 도달하기 전, 브라우저 단계에서 대기 큐에 걸려 있는 상태이기 때문이다.

Q2. — 공통점 찾기

SSE, Long Polling, WebSocket — 이 세 방식은 구현 방법이 전혀 다른데도 모두 "HTTP/1.1 환경에서 탭 6개 한도"라는 같은 문제를 안고 있다. 공통적으로 어떤 성질을 가지고 있기 때문인가?

💡 해설: 셋 다 요청-응답이 한 번으로 끝나지 않고 연결을 계속 유지한다는 공통점이 있다. SSE는 Push를 위해, Long Polling은 응답을 보류하기 위해, WebSocket은 양방향 통신을 위해 각각 연결을 붙잡아 둔다. 반면 일반 GET 요청(Polling)은 응답을 받는 즉시 연결을 반환하므로 이 한도와 무관하다.

Q3. — 설계 의도

Polling+Cache 구조에서 refreshCache()와 getCachedActiveJobs()를 굳이 분리한 이유는 무엇인가? 하나로 합쳐서 매 요청마다 DB를 조회하면 안 되는가?

💡 해설: 합치면 탭 수만큼 DB 조회가 늘어난다. 분리해두면 DB 조회는 스케줄러가 주기적으로 한 번만 수행하고, 클라이언트 요청은 캐시에서 즉시 응답을 받는다 — 탭이 100개여도 DB 부하는 동일하게 유지된다. "갱신"과 "조회"의 책임을 나누는 것이 핵심이다.

Q4. — 캐시 설정

스케줄러 주기가 5초인데 캐시 TTL을 30초(6배)로 잡은 이유는 무엇인가? TTL을 5초로 똑같이 맞추면 어떤 문제가 생길 수 있는가?

💡 해설: TTL을 갱신 주기와 똑같이 맞추면, 스케줄러 실행이 아주 살짝만 지연돼도 캐시가 먼저 만료되어 빈 응답이 나가거나, 그 순간 요청이 몰리면 DB로 직접 떨어질 위험이 생긴다. 주기보다 넉넉한 여유값(여기서는 6배)을 둬서, 스케줄러가 살짝 늦어도 캐시가 끊기지 않도록 완충 구간을 만들어 둔 것이다.

Q5. — 절충안의 한계

SSE + SharedWorker는 "서버 코드 변경이 필요 없는" 깔끔한 절충안으로 소개됐다. 그런데도 즉시 전면 적용하기엔 망설여지는 이유 두 가지를 들어보시오.

💡 해설: ① 브라우저 호환성 — Safari가 SharedWorker를 지원한 건 16버전(2022년)부터라 구형 환경에서는 동작하지 않을 수 있다. ② 스케일아웃 한계는 그대로 — SharedWorker는 브라우저-서버 간 연결 개수만 줄여줄 뿐, 서버 인스턴스마다 에미터 레지스트리가 따로 존재하는 구조적 문제(다중 인스턴스 환경에서 Redis Pub/Sub 같은 보완이 필요한 점)는 그대로 남는다.

Q6. — 선택 기준

"서버 → 클라이언트 단방향 알림만 필요한 화면"에 WebSocket을 적용하는 게 왜 과한 선택인지, 그리고 그 대신 점검해야 할 더 근본적인 질문은 무엇인지 한 문장으로 정리해보시오.

💡 해설: WebSocket의 핵심 가치는 양방향 통신인데, 단방향 알림에는 그 능력이 그대로 버려지고 핸드셰이크·세션 관리 같은 복잡도만 추가된다. "어떤 프로토콜을 쓸까"보다 먼저 "이 화면은 연결을 계속 들고 있어야 하는가, 아닌가"를 따지는 게 더 근본적인 질문이다 — 그 답에 따라 SSE 계열과 Polling 계열로 갈라지고, 그 다음에야 양방향 필요 여부로 WebSocket을 검토하면 된다.
