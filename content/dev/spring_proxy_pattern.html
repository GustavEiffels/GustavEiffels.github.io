Proxy Pattern — Static · JDK Dynamic · CGLIB 완전 이해

Design Pattern Java JDK Dynamic Proxy CGLIB 2026-05-08

순수 Java 코드로 처음부터 — 왜 CGLIB까지 왔는지 이해한다

1

Proxy란 무엇인가

Proxy는 진짜 객체 앞에 서서 호출을 가로채는 대리인이다. 클라이언트는 대리인인지 진짜인지 알 필요가 없다.

Proxy 핵심 구조 
클라이언트  →  [Proxy]  →  [진짜 객체]

              ↑ 여기서 가로채서
              앞뒤로 로직을 끼워 넣는다

핵심은 "같은 타입으로 위장"하는 것이다. 클라이언트가 인터페이스(타입)로만 소통하기 때문에 Proxy로 바꿔치기해도 눈치채지 못한다.

Proxy가 필요한 상황 진짜 객체를 수정하지 않고 — 로깅, 캐싱, 권한 체크, 트랜잭션 등을 앞뒤에 끼워 넣어야 할 때.
2

Static Proxy — 손으로 직접 만들기

Proxy 패턴은 세 요소로 구성된다. 인터페이스를 공유하기 때문에 클라이언트 코드는 바꿀 필요가 없다.

Static Proxy — 인터페이스 · 진짜 객체 · Proxy 
// ① 공통 인터페이스 — 클라이언트는 이것만 안다
interface UserRepository {
    void   save(String name);
    String findById(int id);
}

// ② 진짜 객체 — 비즈니스 로직만
class RealUserRepository implements UserRepository {
    @Override
    public void save(String name) {
        System.out.println("DB에 저장: " + name);
    }
    @Override
    public String findById(int id) {
        return "User_" + id;
    }
}

// ③ Proxy — 같은 인터페이스 구현, 진짜 객체를 품음
class LoggingUserProxy implements UserRepository {

    private final UserRepository target;  // 진짜 객체

    public LoggingUserProxy(UserRepository target) { this.target = target; }

    @Override
    public void save(String name) {
        System.out.println("[LOG] save 시작");
        target.save(name);                  // 진짜 호출
        System.out.println("[LOG] save 완료");
    }

    @Override
    public String findById(int id) {
        System.out.println("[LOG] findById 시작");
        String result = target.findById(id);  // 진짜 호출
        System.out.println("[LOG] findById 결과: " + result);
        return result;
    }
}
사용 — 클라이언트는 Proxy인지 모른다 
// 진짜 객체를 Proxy로 감싸서 주입
UserRepository repo = new LoggingUserProxy(new RealUserRepository());

repo.save("홍길동");
repo.findById(1);
클라이언트 코드 변경 없음 UserRepository 타입으로 받기 때문에, 내부가 Proxy든 Real이든 클라이언트 코드는 동일하다.
3

Static Proxy의 문제 — 반복이 폭발한다

로깅 로직은 똑같은데, 메서드마다 @Override를 반복해야 한다.

메서드 수만큼 반복 
class LoggingUserProxy implements UserRepository {

    @Override
    public void   save(...)     { log; target.save(...);     log; }  // 반복
    @Override
    public void   update(...)   { log; target.update(...);   log; }  // 반복
    @Override
    public void   delete(...)   { log; target.delete(...);   log; }  // 반복
    @Override
    public String findById(...) { log; return target.findById(...); log; }  // 반복
    // 메서드 100개면 100번 반복...
}
두 가지 문제 1. 메서드마다 같은 코드 반복 — DRY 위반 2. 인터페이스에 메서드가 추가되면 Proxy도 반드시 수정해야 함

이 문제를 해결하기 위해 JDK Dynamic Proxy가 등장했다.

4

JDK Dynamic Proxy — 런타임에 동적 생성

Java 내장 API. Proxy 클래스를 직접 작성하지 않아도 된다. 모든 메서드 호출이 invoke() 하나로 들어온다.

InvocationHandler — 모든 메서드를 한 곳에서 
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

// 핸들러 — 모든 메서드 호출이 invoke() 하나로 집결
class LoggingHandler implements InvocationHandler {

    private final Object target;  // Object로 받음 — 어떤 타입이든 OK

    public LoggingHandler(Object target) { this.target = target; }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // save(), findById(), update() ... 어떤 메서드든 여기로 들어옴
        System.out.println("[LOG] " + method.getName() + " 시작");

        Object result = method.invoke(target, args);  // Reflection으로 진짜 메서드 호출

        System.out.println("[LOG] " + method.getName() + " 완료");
        return result;
    }
}
Proxy.newProxyInstance() — Proxy 생성 
UserRepository real = new RealUserRepository();

UserRepository proxy = (UserRepository) Proxy.newProxyInstance(
    real.getClass().getClassLoader(),       // 클래스로더
    new Class[]{ UserRepository.class },   // 구현할 인터페이스 목록
    new LoggingHandler(real)               // 가로챌 핸들러
);

proxy.save("홍길동");    // → invoke(proxy, save메서드, ["홍길동"])
proxy.findById(1);    // → invoke(proxy, findById메서드, [1])
런타임 흐름 
proxy.save("홍길동")
    ↓
LoggingHandler.invoke()    ← save, findById, update 전부 여기로
    → method.getName()  =  "save"
    → method.invoke(target, args)   ← Reflection으로 진짜 호출
        → RealUserRepository.save("홍길동")
    ← 반환
    ↓
결과 반환

Static Proxy

메서드 3개 → Override 3번

메서드 100개 → Override 100번

인터페이스 변경 시 Proxy도 수정

JDK Dynamic Proxy

메서드 몇 개든 → invoke() 1개

인터페이스 변경 시 Proxy 수정 불필요

핸들러 하나로 여러 타입에 재사용 가능

5

JDK Dynamic Proxy의 한계 — 인터페이스 필수

JDK Dynamic Proxy는 인터페이스를 구현하는 방식으로 Proxy를 생성한다. 인터페이스가 없으면 동작하지 않는다.

인터페이스 없는 클래스 → JDK Proxy 불가 
// 인터페이스 없는 일반 클래스
class OrderService {   // implements 없음
    public void order(String item) {
        System.out.println(item + " 주문 완료");
    }
}

OrderService real = new OrderService();

// JDK Dynamic Proxy 시도 → 실패
Object proxy = Proxy.newProxyInstance(
    real.getClass().getClassLoader(),
    new Class[]{ ??? },   // 인터페이스가 없음 → 넣을 게 없다
    new LoggingHandler(real)
);
// 결과: IllegalArgumentException 발생
실무 한계 Spring에서 모든 Service에 인터페이스를 강제하는 것은 번거롭다. 그래서 CGLIB이 등장했다.
6

CGLIB — 상속으로 Proxy 생성

CGLIB(Code Generation Library)은 원본 클래스를 상속한 자식 클래스를 바이트코드로 런타임에 생성한다. 자식이 부모 메서드를 @Override해서 가로챈다.

CGLIB이 런타임에 자동 생성하는 Proxy (개념적 표현) 
// 원본 클래스 — 인터페이스 없어도 된다
class OrderService {
    public void order(String item) {
        System.out.println(item + " 주문 완료");
    }
}

// CGLIB이 런타임에 자동 생성하는 Proxy (개념적 표현)
class OrderService$$CGLIB extends OrderService {  // 상속

    @Override
    public void order(String item) {
        System.out.println("[LOG] order 시작");  // Before
        super.order(item);                          // 진짜 메서드 호출
        System.out.println("[LOG] order 완료");    // After
    }
}
순수 Java에서 CGLIB 사용
Enhancer — CGLIB Proxy 생성 
import net.sf.cglib.proxy.Enhancer;
import net.sf.cglib.proxy.MethodInterceptor;

Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(OrderService.class);   // 상속할 클래스 지정
enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
    System.out.println("[LOG] " + method.getName() + " 시작");
    Object result = proxy.invokeSuper(obj, args);  // 부모(진짜) 메서드 호출
    System.out.println("[LOG] " + method.getName() + " 완료");
    return result;
});

OrderService proxy = (OrderService) enhancer.create();
proxy.order("노트북");
CGLIB의 제한 상속 방식이기 때문에 final 클래스와 final 메서드에는 적용 불가. Override 자체가 불가능하기 때문이다.

3가지 방식 완전 비교

Static Proxy

수동 직접 작성

인터페이스 필요

메서드마다 Override 반복

가장 이해하기 쉬움

JDK Dynamic Proxy

Java 내장 런타임 생성

인터페이스 필수

invoke() 하나로 처리

인터페이스 없으면 불가

CGLIB

외부 라이브러리 런타임 생성

인터페이스 불필요

클래스 상속으로 Override

final 클래스/메서드 불가

기준 Static Proxy JDK Dynamic CGLIB
Proxy 생성 직접 작성 런타임 자동 런타임 자동
인터페이스 필요 필요 필수 불필요
동작 방식 직접 구현 인터페이스 구현 클래스 상속
final 클래스 가능 가능 불가
Spring 사용 X Spring 4.x 이전 기본 Spring Boot 기본

진화 흐름 — 왜 CGLIB까지 왔나

Static Proxy

직접 손으로 Proxy 작성

개념은 명확하지만 메서드마다 같은 코드 반복 → DRY 위반

JDK Dynamic Proxy

invoke() 하나로 반복 제거

모든 메서드 호출이 한 곳으로. 단, 인터페이스가 없으면 사용 불가

CGLIB

상속으로 인터페이스 제약 돌파

클래스를 직접 상속해 Override → 인터페이스 없는 클래스도 Proxy 생성 가능

Spring Boot

CGLIB을 기본으로 채택

@Transactional, @Cacheable 등 → 서버 시작 시 자동으로 CGLIB Proxy 생성하여 Bean으로 등록

전체 흐름 한눈에
진화 흐름 다이어그램 
Static Proxy          → 직접 만드는 것, 개념 가장 명확
       ↓ (반복 문제)
JDK Dynamic Proxy     → 반복 제거, 단 인터페이스 필요
       ↓ (인터페이스 없는 클래스 문제)
CGLIB                  → 인터페이스 없어도 됨 (상속 방식)
       ↓ (Spring이 자동으로 사용)
Spring @Transactional  → CGLIB Proxy를 자동으로 생성·주입

핵심 요약

  • Proxy = 진짜 객체와 같은 타입으로 위장한 대리인 — 클라이언트 코드 변경 없음
  • Static Proxy = 직접 작성, 메서드마다 Override → 메서드 수만큼 반복
  • JDK Dynamic Proxy = invoke() 하나로 모든 메서드 처리, 단 인터페이스 필수
  • CGLIB = 클래스 상속으로 Override → 인터페이스 없어도 되지만 final 불가
  • Spring Boot = CGLIB 기본 채택, @Transactional 등이 붙으면 자동으로 Proxy Bean 등록
  • 기억법: 비서(Proxy)가 사장님(진짜 객체) 앞에 서서, 외부는 비서를 사장님으로 안다

퀴즈 — 직접 확인해보자

Q1. Proxy 패턴의 핵심 조건은?
A 진짜 객체보다 반드시 더 빠르게 동작해야 한다
B 클라이언트가 Proxy인지 진짜 객체인지 알 수 없도록 같은 타입으로 위장한다
C 진짜 객체를 상속받아야 한다
D 반드시 인터페이스를 사용해야 한다
정답: B
Proxy의 핵심은 "같은 타입으로 위장"이다. 클라이언트가 인터페이스(타입)로만 소통하기 때문에 Proxy로 바꿔치기해도 눈치채지 못한다. 인터페이스가 아닌 상속으로도 같은 효과를 낼 수 있으므로 D는 틀렸다.
Q2. Static Proxy의 가장 큰 단점은?
A 런타임에 Proxy를 만들어야 해서 느리다
B 인터페이스 없이는 사용할 수 없다
C 메서드마다 같은 코드를 반복해서 Override해야 한다
D final 클래스에 적용할 수 없다
정답: C
Static Proxy는 인터페이스의 모든 메서드를 직접 Override해야 한다. 로깅 로직은 똑같은데 메서드 100개면 100번 반복해야 하는 DRY 위반이 핵심 문제다. B는 CGLIB의 장점이 필요한 이유, D는 CGLIB의 제한이다.
Q3. JDK Dynamic Proxy에서 모든 메서드 호출이 집결하는 곳은?
A InvocationHandler의 invoke() 메서드
B MethodInterceptor의 intercept() 메서드
C Enhancer의 create() 메서드
D Proxy.newProxyInstance() 메서드
정답: A
JDK Dynamic Proxy에서는 InvocationHandler를 구현하면 되고, save(), findById() 등 어떤 메서드를 호출하든 invoke() 하나로 집결한다. B는 CGLIB의 콜백, C와 D는 Proxy 생성 API다.
Q4. CGLIB이 Proxy를 만들 수 없는 경우는?
A 인터페이스가 없는 클래스
B 메서드가 100개 이상인 클래스
C @Service 어노테이션이 없는 클래스
D final로 선언된 클래스 또는 메서드
정답: D
CGLIB은 원본 클래스를 상속해서 자식 클래스를 만드는 방식이다. final 클래스는 상속이 불가하고, final 메서드는 Override가 불가하므로 CGLIB Proxy를 만들 수 없다. A는 오히려 CGLIB의 강점이다.
Q5. Spring Boot가 @Transactional이 붙은 Service에 CGLIB을 기본으로 선택한 이유는?
A CGLIB이 JDK Dynamic Proxy보다 항상 빠르기 때문
B 인터페이스 기반 설계가 복잡하기 때문
C 인터페이스 없이도 Proxy를 만들 수 있어 Service 클래스에 항상 적용 가능하기 때문
D CGLIB이 Java 표준 라이브러리에 포함되어 있기 때문
정답: C
실무에서 Service 클래스가 항상 인터페이스를 구현하는 것은 아니다. CGLIB은 인터페이스 없이도 클래스 상속만으로 Proxy를 생성할 수 있기 때문에 Spring Boot가 기본값으로 채택했다. CGLIB은 외부 라이브러리이지만 Spring Boot에 포함되어 있다.
