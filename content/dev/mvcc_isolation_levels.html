MVCC와 격리 수준 — xmin/xmax부터 READ COMMITTED까지

기술 면접 대비 중 "MVCC 기반 읽기/쓰기 비블로킹" 주장을 파고들며 정리한 노트. Q&A로 개념을 다지는 방식으로 진행됨

1

배경 — 왜 필요한가

DB 락을 통해 동시성 제어를 수행할 때, 어떤 행에 대해 UPDATE 트랜잭션이 진행 중이면 다른 트랜잭션이 그 행을 조회하려면 UPDATE 트랜잭션이 끝날 때까지 기다려야 한다. 즉, 수정이 끝나기 전까지는 조회를 하지 못하게 된다.

MVCC의 해법 — 덮어쓰기가 아니라 버전 추가 MVCC(Multi-Version Concurrency Control)는 이 문제를 튜플로 해결한다. 하나의 행에 지속적으로 덮어쓰는 방법이 아니라, 하나의 행에 여러 개의 튜플을 두어 수정할 때마다 수정 버전을 새롭게 생성하는 방식이다. 이전 버전을 제거하지 않기 때문에, 수정 트랜잭션이 진행되더라도 다른 트랜잭션이 해당 행을 읽을 수 있다.
2

튜플(tuple)이란 — 행(row)과의 관계

튜플은 행과 별개의 것이 아니라 행이 디스크에 물리적으로 저장된 실체를 가리키는 내부 용어다.

논리적 관점 (SQL 사용자)테이블 안에 행(row)이 있다
물리적 관점 (Postgres 엔진)테이블 파일(페이지들의 집합) 안에 튜플이 있다

평소엔 행 : 튜플 = 1 : 1이라 구분할 필요가 없지만, UPDATE를 N번 하면 물리적으로 튜플이 총 N+1개까지 쌓일 수 있다. 논리적으로는 여전히 행 1개지만, 물리적으로는 그 행에 대한 튜플이 여러 개 존재하게 되는 것 — 그중 유효한 건 항상 1개뿐이고 나머지 N개는 죽은 튜플이다.

3

xmin / xmax — 정의

행마다 붙는 숨겨진 시스템 컬럼이다. x는 트랜잭션(transaction)을 뜻하는 Postgres 내부 접두사다.

컬럼뜻언제 찍히나
xmin 이 튜플을 만든 트랜잭션 ID INSERT할 때, 또는 UPDATE가 새 버전을 만들 때
xmax 이 튜플을 무효화한 트랜잭션 ID UPDATE가 이 버전을 밀어낼 때, 또는 DELETE할 때 (비어있으면 아직 안 지워짐)
암기xmin = 태어난 시점, xmax = 죽은 시점
xminINSERT 또는 UPDATE로 튜플이 새로 생성되는 시점에, 그 트랜잭션 ID가 xmin에 할당된다
xmaxUPDATE(또는 DELETE) 트랜잭션이 그 튜플을 밀어낼 때 xmax에 트랜잭션 ID가 할당된다
4

UPDATE는 내부적으로 INSERT + 표시

users 테이블 예시 
INSERT INTO users VALUES (1, 'A');    -- T1이 실행
UPDATE users SET name='B' WHERE id=1; -- T2가 실행

T2 실행 후 테이블 파일 안에는 물리적으로 튜플이 2개 남는다:

물리적 상태 
튜플#1(옛 버전): name='A', xmin=T1, xmax=T2   // 무효화됨(죽은 튜플)
튜플#2(새 버전): name='B', xmin=T2, xmax=없음  // 지금 유효(살아있는 튜플)
핵심 UPDATE는 "그 자리 수정"이 아니라 "새 튜플 INSERT + 옛 튜플에 xmax 표시"로 동작한다.
5

가시성 규칙(Visibility Rule)

어떤 튜플이 사용자에게 보이려면, 아래 두 조건을 모두 만족해야 한다.

  1. xmin에 트랜잭션 ID가 할당돼 있고, 그 트랜잭션이 커밋됨
  2. 그리고 xmax에 트랜잭션 ID가 할당 안 됐거나, 할당됐어도 그 트랜잭션이 아직 커밋 안 됨
트랜잭션 커밋 여부로 가시성이 판단된다 xmax는 UPDATE 시 트랜잭션 ID가 할당되지만, 커밋되기 전까지 다른 트랜잭션에게는 아직 유효한 튜플이라고 인식된다.

UPDATE가 아직 커밋 안 됐을 때 다른 트랜잭션이 조회하면

튜플상태다른 트랜잭션에서
보임
옛 튜플(name='A')		 xmax=T2 있지만 T2 아직 미커밋 여전히 보임
안 보임
새 튜플(name='B')		 xmin=T2인데 T2 아직 미커밋 안 보임
T2가 커밋되는 순간 새 튜플이 보이기 시작하고 옛 튜플이 안 보이기 시작한다. UPDATE가 커밋 전이든 후든, 조회하는 쪽은 락에 걸려 대기하는 게 아니라 그 순간에 해당하는 버전을 즉시 읽고 종료된다.
6

물리적으로 겹쳐도 유니크 제약이 안 깨지는 이유

동일한 PK를 가진 튜플 여러 개가 동시에 존재해도, 중복 키 에러가 발생하지 않는 이유다.

유니크 제약도 "보이는 것"만 검사한다 Postgres가 중복 키 위반을 검사할 때, MVCC 가시성 규칙을 동일하게 적용하여 visible한 튜플이 2개 이상이면 위반으로 판단한다. 이전 버전의 튜플은 죽은 것으로 취급하여 중복 판정에서 벗어난다. 그래서 물리적으로 PK가 일치해도 논리적으로 충돌이 발생하지 않는다.

HOT(Heap-Only Tuple) update

일반적인 UPDATE가 비싼 이유: UPDATE는 새 튜플을 물리적으로 다른 위치에 생성한다. 문제는 인덱스가 물리적 위치를 매핑하고 있는데, 튜플이 변경되었으니 해당 테이블에 걸린 인덱스 전부 새 위치로 다시 가리키도록 갱신해야 한다. 바뀐 컬럼이 인덱스와 무관해도 튜플 자체가 이동했으니 이 비용은 똑같이 든다.

HOT이 하는 일: 아래 두 조건이 맞으면 이 인덱스 갱신을 통째로 생략한다.

  1. UPDATE가 건드린 컬럼이 어떤 인덱스에도 안 걸려있음
  2. 새 튜플을 같은 페이지(디스크의 같은 8KB 블록) 안에 넣을 공간이 있음

이 두 조건이 맞으면, 이전 튜플 위치에 내부 포인터만 남겨두어 인덱스 수정이 발생하지 않는다. 인덱스로 조회 시 이전 튜플 위치에서 체인을 따라서 최신 버전을 찾는다.

HOT 적용 여부 비교 
-- users(id PK/인덱스, name 인덱스, last_login 인덱스 없음)

UPDATE users SET last_login = now() WHERE id = 1;
-- last_login엔 인덱스가 없음 -> HOT 적용, id/name 인덱스 둘 다 안 건드림

UPDATE users SET name = 'B' WHERE id = 1;
-- name엔 인덱스가 있음 -> HOT 불가, name 인덱스에 새 항목 추가 필요
왜 중요한가 인덱스가 여러 개 걸린 테이블에서, 자주 바뀌지만 인덱스는 안 걸린 컬럼(updated_at, last_login, 카운터 등)을 UPDATE할 때마다 모든 인덱스를 갱신하면 쓰기 비용이 커진다. HOT은 그 낭비를 막아준다.
7

부수 효과 — 죽은 튜플 누적과 VACUUM

INSERT 1번 + UPDATE N번을 하면, 튜플이 총 N+1개 생기고 그중 살아있는 건 1개뿐이다. 나머지 N개는 xmin·xmax가 둘 다 채워진 죽은 튜플로 테이블 파일 안에 그대로 남는다.

튜플 누적 과정 
T1: INSERT       -> 튜플A(xmin=T1, xmax=없음)              [살아있음]
T2: UPDATE       -> 튜플A(xmin=T1, xmax=T2) [죽음]         튜플B(xmin=T2, xmax=없음) [살아있음]
T3: UPDATE       -> 튜플B(xmin=T2, xmax=T3) [죽음]         튜플C(xmin=T3, xmax=없음) [살아있음]
T4: UPDATE       -> 튜플C(xmin=T3, xmax=T4) [죽음]         튜플D(xmin=T4, xmax=없음) [살아있음]
T5: UPDATE       -> 튜플D(xmin=T4, xmax=T5) [죽음]         튜플E(xmin=T5, xmax=없음) [살아있음]

최종: 튜플 5개 물리적 존재, 살아있는 건 E 1개뿐, A~D는 죽은 튜플
죽은 튜플은 테이블 파일 자체 용량에 포함된다 같은 테이블 안에 포함되기 때문에 방치하면 테이블 스캔 범위가 커진다. VACUUM(보통 autovacuum)이 죽은 튜플을 제거하여 공간을 회수한다.
8

격리 수준(Isolation Level)과의 관계

MVCC 자체는 항상 동작한다 "스냅샷을 얼마나 자주 새로 뜨느냐"가 격리 수준의 차이일 뿐이다.
격리 수준스냅샷 갱신 시점동작
READ COMMITTED
PostgreSQL 기본값		 문장(statement)마다 같은 트랜잭션 안에서도 SELECT할 때마다 최신 커밋 내용이 반영됨
REPEATABLE READ 트랜잭션 시작 시 1번 트랜잭션이 끝날 때까지 처음 본 데이터로 계속 봄 (그 사이 남이 커밋해도 안 보임)

READ COMMITTED 예시

동일 트랜잭션, 두 번의 SELECT 
BEGIN;
SELECT name FROM users WHERE id=1;  -- 'A' 조회 (이 시점 스냅샷)

-- (다른 세션에서 UPDATE name='B' 실행 후 커밋)

SELECT name FROM users WHERE id=1;  -- 'B' 조회 (문장마다 새 스냅샷이라 반영됨)
COMMIT;
REPEATABLE READ였다면 두 번째 SELECT도 여전히 'A'를 봤을 것이다 — 트랜잭션 시작 시점 스냅샷을 끝까지 고정해서 쓰기 때문.

MVCC가 못 막는 것 — Writer 간의 충돌

읽기-쓰기만 비블로킹, 쓰기-쓰기는 여전히 막힌다 MVCC는 읽기 vs 쓰기 블로킹만 제거하지, 쓰기 vs 쓰기는 여전히 막아야 한다. 두 writer 트랜잭션이 같은 행을 동시에 수정하려면, 하나의 트랜잭션이 종료될 때까지 다른 트랜잭션은 대기해야 한다.
9

tl;dr

튜플행이 디스크에 물리적으로 저장된 실체. 평소엔 행=튜플이지만 UPDATE 직후엔 한 행에 튜플이 여러 개 존재할 수 있음
xmin / xmaxxmin=만들어진 트랜잭션, xmax=무효화한 트랜잭션. 가시성은 필드 존재 여부가 아니라 그 트랜잭션의 커밋 여부로 결정
UPDATE의 실체내부적으로 "새 튜플 INSERT + 옛 튜플에 xmax 표시" — 그래서 읽는 쪽이 락을 기다릴 필요가 없음
유니크 제약가시성 규칙을 그대로 적용해서, 물리적으로 겹쳐도 논리적 충돌은 안 남
비용죽은 튜플이 쌓이는 게 MVCC의 비용 — VACUUM이 청소
격리 수준READ COMMITTED(문장마다 스냅샷 갱신) vs REPEATABLE READ(트랜잭션 시작 시 1번 고정) — MVCC는 항상 동작하고, 격리 수준은 "스냅샷을 얼마나 자주 새로 뜨느냐"의 차이일 뿐
한계MVCC는 쓰기-쓰기 충돌까지는 못 막음 — 그건 여전히 락/재시도가 필요
